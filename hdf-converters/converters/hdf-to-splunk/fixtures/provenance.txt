# hdf-to-splunk fixtures — provenance

## `input/negzero.json`

**Adapted** from this repository's `hdf-to-ocsf/fixtures/input/scalartag.json`,
itself a Nessus-derived HDF Results document. Structure, tool identity, component
and CVE are carried over unchanged; only the two numeric fields under test were
altered — `impact` and `cvss[0].baseScore` are both set to the raw JSON token
`-0`, and the result status was changed to match a zero-impact finding.

**Schema-validated**, as the fixture policy requires for adapted input. Proof:

```
$ hdf validate converters/hdf-to-splunk/fixtures/input/negzero.json
✓ ... is a valid HDF results file
```

`-0` satisfies the schema's `minimum: 0` on `impact` because JSON Schema
compares numbers mathematically and `-0 == 0`; no keyword can reject it while
accepting `0`.

**Why this is a file rather than test-constructed input.** The negative zero must
reach the converter as raw JSON *text*. Building the document with the testhdf
builders and serializing it destroys the distinction — `JSON.stringify({impact: -0})`
yields `{"impact":0}` — so a test-generated input would pass against the very
bug this fixture exists to catch. The file is also the channel that lets the Go
golden and the TypeScript byte-identity check run on identical input.

## Shared SIEM corpus — `cve.json`, `compliance.json`, `override.json`, `riskadjust.json`, `negzero.json`

These are byte-identical across `hdf-to-ecs`, `hdf-to-ocsf` and `hdf-to-splunk`
(`cve.json` and `compliance.json` also under `hdf-to-asff`), and that is deliberate: the same HDF
document fed to every SIEM exporter is what makes their outputs comparable. The 2026-09-14 fixture
audit decided to keep the copies in place rather than promote them. The fixture policy's promotion
rule speaks of "two or more workspace packages", and these are several converters inside one
package, so the rule does not decide it; and the duplication is about 140 KB in total, not worth a
new shared location. The risk that decision leaves is silent drift — one copy edited, the others
not — so `shared/go/siem_corpus_test.go` pins every copy byte-identical. Change all of them or none.

Origins: `negzero.json` is documented above. `compliance`, `cve`, `override` and `riskadjust`
predate the per-directory provenance convention; their origin is not yet recorded here.

## Tool and version, read from the file itself (2026-09-20)

A version below is what the fixture *says about itself*; where a format carries no producer version, that is stated rather than guessed.

- `compliance.json` — an HDF document produced by `xccdf-results-to-hdf` 0.1.0 (tool=XCCDF None).
- `cve.json` — an HDF document produced by `nessus-to-hdf` 0.1.0 (tool=Nessus None).
- `negzero.json` — an HDF document produced by `nessus-to-hdf` 0.1.0 (tool=Nessus None).
- `override.json` — an HDF document with no `generator` block; `generator; tool=None None`.
- `riskadjust.json` — an HDF document with no `generator` block; `generator; tool=None None`.

## Schema

The inputs are HDF documents; their schema is this repository's own (`hdf-schema`), and every input is validated by the converter tests through `hdf-validators`. The exporter's target-format schema, where one is vendored, lives under this converter's `schemas/` directory with its own `provenance.json`.

## Bundle integration expectation correction (2026-11-07)
The override and riskadjust inputs now carry the schema's Integrity object. Their legacy NDJSON
goldens remove only baseline_checksum, which previously described the obsolete
checksum input member; every other byte remains unchanged. New TS/Go bundle
readback tests verify the complete original integrity object through source.json.
No converter default was changed to reinterpret Integrity as Checksum.
