# CycloneDX VEX fixture provenance

## Inputs

All five inputs are **verbatim copies** of the official CycloneDX
bom-examples repository:
https://github.com/CycloneDX/bom-examples/tree/master/VEX

- `case1-vex-not_affected.json` — CISA Use Case 1, `not_affected` status
  with `code_not_present` justification. Exercises the standard
  not_affected + justification + product@version path.
- `case1-vex-fixed.json` — CISA Use Case 1, `resolved` status. Imported
  as an open POA&M pinned to `failed` pending real-system re-scan
  (supplier-claim vs assessed-system invariant).
- `case1-vex-affected.json` — `exploitable` status. Produces no override
  (informational only); exercises the empty-actionable-statements
  error path.
- `case1-vex-under_investigation.json` — `in_triage` status. Same error
  path; the consumer creates an amendment later if they decide to act.
- `cyclonedx-vex-example.json` — the spec repo's flagship example with
  the publisher metadata, tooling, and multiple references populated.
  Exercises richer envelope handling.

These are the canonical CycloneDX VEX examples used by the
specification's documentation, so fixture provenance is route #1
(real-world publisher data from a public repo) per build-converter.md
Step 2.

## CycloneDX justification passthrough

CycloneDX defines justifications beyond the HDF Justification enum's
vocabulary (`requires_configuration`, `requires_dependency`,
`requires_environment`, `protected_by_compiler`, `protected_at_runtime`,
`protected_at_perimeter`). These do NOT silently drop — the raw label
appears in the reason field with a `VEX justification:` prefix so
auditors and downstream consumers see what the upstream publisher
actually said. The structured `justification` field on the override
remains unset on the HDF enum until a value normalizes.

## Auto-detect collision with cyclonedx-to-hdf

A CycloneDX BOM that carries VEX analysis statements would, by default,
match both `cyclonedx-to-hdf` (SBOM → HDF Results) and
`cyclonedx-vex-to-hdf` (VEX → HDF Amendments). The SBOM fingerprint now
returns 0.8 when `vulnerabilities[].analysis` is present so VEX wins.
Plain SBOMs without analysis still get 1.0 and route to the SBOM
converter as before.

## Expected

`expected/*.json` are regenerated by the CLI for visual diff review.
They do not gate the test suite — the in-memory Go and TS tests are
authoritative.
