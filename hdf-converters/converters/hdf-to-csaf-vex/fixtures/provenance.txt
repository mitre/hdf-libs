# hdf-to-csaf-vex fixture provenance

## Inputs

Both inputs are the **HDF Amendments expected outputs of csaf-vex-to-hdf**
on the corresponding upstream CSAF spec examples. This pairing makes the
round-trip test natural: convert CSAF → HDF (via csaf-vex-to-hdf) → CSAF
(via this converter) and assert that consumer-action-bearing fields
survive.

- `sec-vex-amendments.json` — HDF form of `sec-vex-2022-0001.json`
  (Secvisogram's Log4Shell statement). Three CVEs, all `not_affected`
  with `component_not_present` justification flags. Exercises the
  multi-CVE known_not_affected export path.
- `uc-01-fixed-amendments.json` — HDF form of `2022-evd-uc-01-f-001.json`
  (an open POA&M imported from a VEX `fixed` statement). Exercises the
  "supplier said fixed, system not yet verified" path: the export must
  NOT emit `fixed`, only `known_affected` with a remediation hint.
  **Lives in `@mitre/hdf-fixtures` (`amendments/`), not in `input/`** —
  hdf-to-oscal-poam consumes the same file for its golden, so per the
  fixture boundary rule it is shared, not duplicated. The tests here load
  it from the corpus.

## Partial-fidelity contract

Round-trip preservation by field:

| HDF override field | CSAF VEX shape | Survives round-trip? |
|---|---|---|
| `requirementId` (CVE-shaped) | `vulnerabilities[].cve` | yes |
| `type=falsePositive` + `justification` | `product_status.known_not_affected` + `flags[].label` | yes |
| `type=poam` (open, milestones pending) | `product_status.known_affected` + `remediations[category=workaround]` | yes; lossy on the "vendor claimed fix" provenance (intentional — see below) |
| `type=poam` (all milestones completed) | `product_status.fixed` + `remediations[category=vendor_fix]` | yes |
| `affectedPackages[].purl` / `.cpe` / `.name@version` | `product_status[...]` product ids + `product_tree.full_product_names` | yes — preferred source of structured product identity |
| `componentRef` OR legacy `Products: …` reason line (pre-v3.2.x inputs) | `product_status[...]` product ids + `product_tree.full_product_names` | yes — backward-compat fallback; default `HDFPID-0001` synthesized when no source carries product identity |
| `evidence[type=url]` | `vulnerabilities[].references[]` | yes |
| `reason` free text | `vulnerabilities[].threats[category=impact].details` (for `affected` cases) or dropped (for `not_affected` — justification + flag carry the structured payload) | partial |
| `appliedBy.identifier` | `document.publisher.name` | yes |
| `appliedAt` | `flags[].date` (when justification present); document tracking uses generation time | partial |
| `requirementId` (non-CVE, e.g. NIST AC-2) | — (dropped — CSAF VEX is vulnerability-keyed) | NO (by design) |
| `amendmentId` | `document.tracking.id` | yes |
| `version` | `document.tracking.version` | yes |
| `description` | `document.notes[category=summary]` | yes |
| `previousChecksum`, full amendment chain | — (collapsed) | NO (partial-fidelity boundary) |
| HDF `Result_Status` exact value | inferred via VEX status mapping | partial |

## Real-system vs abstract-vuln invariant

**An open POA&M never round-trips to `fixed`.** VEX `fixed` is a supplier
claim about a product version; HDF describes an assessed system. The
import converter pins status to `failed` on the POA&M; the export
converter only emits `fixed` when every milestone is in `completed`
state AND the override is the latest in its chain. Lacking either, the
export emits `known_affected` with the remediation surfacing as a
workaround. This is deliberate — claiming `fixed` based on the
amendment alone would lie to downstream consumers.

## Expected

`expected/*.json` are regenerated by the CLI for visual diff review.
They do not gate the test suite — the round-trip and shape assertions in
the Go and TS tests are authoritative.
