# XCCDF 1.2 XSD — provenance

Used to validate `hdf-to-xccdf` output against the NIST XCCDF 1.2 schema in its
tests, in both languages: Go via `shared/go/xsdvalidate` (libxml2 through cgo)
and TypeScript via `shared/typescript/xsd-validation.ts` (libxml2 compiled to
WASM by `xmllint-wasm`). The converter emits
`xmlns="http://checklists.nist.gov/xccdf/1.2"`.

Retrieved 2026-07-30. The **local SHA-256** column is the hash of the file as it
sits here, which for the two rewritten files necessarily differs from upstream.
It is what the provenance test asserts, so an unintended edit to any of these
fails rather than passing quietly.

**schemaLocation rewrites (offline validation):** `xccdf_1.2.xsd` and
`cpe-language_2.3.xsd` `<xsd:import>` companions by absolute URL / server-root
path. Those `schemaLocation`s were rewritten to the local relative filenames
(all four XSDs sit in this directory) so libxml2 compiles the schema without
network access. Only the `schemaLocation` attribute values were changed; the
schema definitions are otherwise upstream-identical (see original SHAs above).

**Import graph:** `xccdf_1.2.xsd` → `xml.xsd`, `cpe-language_2.3.xsd`;
`cpe-language_2.3.xsd` → `cpe-naming_2.3.xsd`, `xml.xsd`.

**Each language gates its own output.** An earlier revision of this file claimed
the TypeScript output was covered transitively by Go↔TS golden parity. That was
false: the golden comparison runs both sides through `NormalizeXMLForGolden`,
which decodes entities and collapses whitespace, so output that differs in
escaping or newline encoding compares equal and never reaches an XSD. The
TypeScript suite therefore validates its own output against this XSD rather than
relying on the Go result.

**Windows:** the Go validator is a skipping stub on Windows
(`xsdvalidate_windows.go`, no cgo libxml2), so Go XSD validation runs only on
non-Windows CI legs. The WASM validator has no native dependency and runs on
every leg.

CKL was evaluated and excluded — DISA publishes no authoritative `.ckl` XSD.
