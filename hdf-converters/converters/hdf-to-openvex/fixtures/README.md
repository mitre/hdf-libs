# hdf-to-openvex fixture provenance

## Inputs

Both inputs are the HDF Amendments expected outputs of openvex-to-hdf
on the corresponding upstream OpenVEX examples. This pairing makes the
round-trip test natural: convert OpenVEX → HDF (via openvex-to-hdf) →
OpenVEX (via this converter) and assert that consumer-action-bearing
fields survive.

- `spring-boot-log4j-amendments.json` — HDF form of
  `spring-boot-log4j.openvex.json` (the OpenVEX spec's canonical
  example). One CVE, `not_affected`, justification
  `vulnerable_code_not_in_execute_path`. Exercises the
  not_affected + justification + product-PURL export path.
- `multi-status-amendments.json` — HDF form of the multi-status
  synthesized fixture. Exercises the open-POA&M-stays-affected path
  alongside not_affected.

## Partial-fidelity contract

Round-trip preservation by field:

| HDF override field | OpenVEX field | Survives round-trip? |
|---|---|---|
| `requirementId` (CVE-shaped) | `statements[].vulnerability.name` (+ NVD `@id`) | yes |
| `type=falsePositive` + `justification` | `status=not_affected` + `justification` | yes |
| `type=poam`, all milestones completed | `status=fixed` + `action_statement` from milestone | yes |
| `type=poam`, open | `status=affected` + `action_statement` from milestone | yes (status stays affected — supplier-claim invariant) |
| `affectedPackages[].purl` / `.cpe` / `.name@version` | `statements[].products[].@id` | yes — purl preferred; cpe and name@version fall back in that order |
| `componentRef` OR legacy `Products: …` reason line (pre-v3.2.x inputs) | `statements[].products[].@id` | yes — backward-compat fallback when no structured `affectedPackages` present |
| `reason` (free text) | `impact_statement` (for not_affected) or `action_statement` (for affected when no milestones) | partial — first non-empty wins |
| `appliedBy.identifier` | `author` | yes |
| `appliedBy.description` | `role` | yes |
| `appliedAt` (earliest override) | document `timestamp` | yes |
| `appliedAt` (per-override) | `statements[].timestamp` | yes |
| `requirementId` (non-CVE) | — (dropped — OpenVEX is vulnerability-keyed) | NO (by design) |
| `evidence[type=url]` | — (no native OpenVEX field for arbitrary references) | NO (dropped; round to CSAF VEX exporter to preserve them) |
| `previousChecksum`, amendment chain | — (collapsed) | NO (partial-fidelity boundary) |

## Real-system vs abstract-vuln invariant

An open POA&M never round-trips to `fixed`. The export emits `affected`
with the planned remediation as `action_statement` unless every
milestone is in `completed` state. This is the same supplier-claim
guard the import side enforces (`fixed` → POA&M pinned to `failed`); a
single-shot export honors it by checking milestone state only — no
amendment-chain confirmation required for the obvious closed-POA&M case.

## Expected

`expected/*.json` are regenerated by the CLI for visual diff review.
They do not gate the test suite — the round-trip and shape assertions in
the Go and TS tests are authoritative.
