# hdf-to-cyclonedx-vex fixture provenance

## Inputs

Both inputs are the HDF Amendments expected outputs of
cyclonedx-vex-to-hdf on the corresponding upstream CycloneDX VEX
examples. This pairing makes the round-trip test natural: convert
CycloneDX → HDF (via cyclonedx-vex-to-hdf) → CycloneDX (via this
converter) and assert that consumer-action-bearing fields survive.

- `case1-not_affected-amendments.json` — HDF form of CISA Use Case 1
  `vex-not_affected.json`. One CVE, `not_affected`, justification
  `code_not_present`. Exercises the canonical not_affected + product
  passthrough path.
- `case1-fixed-amendments.json` — HDF form of CISA Use Case 1
  `vex-fixed.json` (open POA&M pinned to `failed` on import).
  Exercises the open-POA&M-stays-exploitable invariant.

## Partial-fidelity contract

Round-trip preservation by field:

| HDF override field | CycloneDX VEX target | Survives round-trip? |
|---|---|---|
| `requirementId` (CVE-shaped) | `vulnerabilities[].id` | yes |
| `type=falsePositive` + `justification` | `analysis.state=not_affected` + `analysis.justification` | yes |
| `type=poam`, all milestones completed | `analysis.state=resolved` + `analysis.response=["update"]` | yes |
| `type=poam`, open | `analysis.state=exploitable` + `analysis.response=["workaround_available"]` | yes (status invariant — see below) |
| `componentRef` OR `Products: …` in reason | `affects[].ref` + matching `components[]` entry | yes |
| `reason` free text (with annotations stripped) | `analysis.detail` | partial — annotation tail lines (`Products: …`, `VEX justification: …`, `Response: …`) are stripped to avoid duplication; the prose survives |
| Raw CycloneDX-specific justification preserved in reason (e.g. `requires_configuration`) | `analysis.justification` | yes — recovered from the `VEX justification:` reason line |
| `evidence[type=url]` | `vulnerabilities[].references[]` | yes |
| `appliedBy.identifier` | `metadata.authors[0].name` (or `.email` if Email identity) | yes |
| earliest `appliedAt` | `metadata.timestamp` | yes (whole-document granularity) |
| `amendmentId` | `serialNumber` as `urn:uuid:<id>` | yes |
| `requirementId` (non-CVE — e.g. NIST control) | — (dropped — CycloneDX VEX is vulnerability-keyed) | NO (by design) |
| `previousChecksum`, amendment chain | — (collapsed) | NO (partial-fidelity boundary) |
| CVSS / EPSS / KEV / CWE on the override | — (no current mapping; orthogonal to brfj) | NO (deferred to noeq scope) |

## Real-system vs abstract-vuln invariant

**An open POA&M never round-trips to `resolved`.** CycloneDX `resolved`
implies the fix was applied; the export only emits it when every
milestone is in `completed` state. Otherwise the override surfaces as
`exploitable` with `response=["workaround_available"]` and the
remediation in `detail`. This mirrors the OpenVEX `affected` / CSAF
`known_affected` exports for the same reason.

## Justification passthrough

CycloneDX-specific justification labels (`requires_configuration`,
`requires_dependency`, `requires_environment`, `protected_by_compiler`,
`protected_at_runtime`, `protected_at_perimeter`) do NOT normalize to
the HDF Justification enum on import — the shared VEX helper preserves
the raw label in the override's reason field as a
`VEX justification: <label>` line. This converter recovers that label
back into `analysis.justification` on export, so CycloneDX-shaped
documents round-trip the full vocabulary.

## Expected

`expected/*.json` are regenerated by the CLI for visual diff review.
They do not gate the test suite — the round-trip and shape assertions
in the Go and TS tests are authoritative.
