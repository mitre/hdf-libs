# gitlab-vulnerabilities-to-hdf fixtures — provenance

Recorded 2026-09-20 from a self-managed GitLab 18.9.1-ee instance running an
Ultimate trial, through the GraphQL API as a project Owner (non-admin) token.
The GraphQL Vulnerability Report has no published sample corpus and no static
export that preserves triage history, so every file here is a live response
from that instance. Nothing was hand-assembled.

Each `input/` envelope is the fetcher's deterministic assembly of raw
responses: the probe response (instance metadata + project block) plus every
page of `project.vulnerabilities`, with the latest default-branch pipeline
taken from page 1 and `fetchedAt` set to the recording time. The raw responses
themselves are committed unchanged (apart from the scrub below) as the fetcher
test corpus in `hdf-converters/fetchers/gitlab-vulnerabilities/go/testdata/`.

Scrub applied to every file, and nothing else: the recording account's
username and display name were replaced with `sec-reviewer` / `Security
Reviewer`, every `publicEmail` was nulled, and the instance URL scheme was
normalized to https on the `gitlab.example.com` placeholder host. Ids, uuids, timestamps, comments and
structure are as GitLab returned them.

## `input/`

### `triaged.json`
Project `security-demo/juice-shop`, fetched with `--report-type
SAST,SECRET_DETECTION`: the OWASP Juice Shop source at v20.2.0 scanned on its
default branch by the GitLab SAST template (Semgrep 1.145.0) and Secret
Detection template (Gitleaks 8.30.0), 100 vulnerabilities ingested.
Triaged through the GitLab API to cover every state and dismissal reason:
3 CONFIRMED, 2 RESOLVED (one whose finding the scanner no longer reports, so
`resolvedOnDefaultBranch` is true, and one it still reports, so it is false),
one DISMISSED per reason (FALSE_POSITIVE, ACCEPTABLE_RISK,
MITIGATING_CONTROL, USED_IN_TESTS, NOT_APPLICABLE), one finding dismissed,
reverted and re-dismissed (three state transitions), two findings reverted
and re-confirmed, two whose resolution GitLab itself reverted when a later
scan re-detected them, and one severity override (MEDIUM to LOW). Every
decision carries its own statement.

### `dependency-scanning.json`
The same project fetched with `--report-type DEPENDENCY_SCANNING`, first page
only (25 of 77). Its npm lockfile was committed so the Gemnasium analyzer
could resolve the tree. These are the findings that carry CVSS vectors and
scores, CVE and GHSA identifiers, and the dependency-scanning location shape;
the SAST and secret-detection findings above carry none of those.

### `clean.json`
Project `security-demo/web-goat`: an otherwise empty repository whose Secret
Detection job ran and was ingested with zero findings. `vulnerabilityStatistic`
is present with a total of 0 and the scan status is SUCCEEDED — the
"genuinely clean" shape.

### `report-error.json`
Project `security-demo/unscanned-app`: a job named `custom-sast` uploads a
SAST report artifact that is not a valid security report, so the scanner
counts as enabled and run (`securityScanners.pipelineRun` lists SAST) but
ingestion fails (scan status REPORT_ERROR) and `vulnerabilityStatistic` is
null. This is the shape `securityScanners` alone would mislabel as clean.

### `empty.json`
Project `security-demo/empty-app`: a README-only project with no CI
configuration, no pipeline and no statistic.

## `expected/`

Generated by this repository's converters, not sourced. Regenerate with
`go test ./converters/gitlab-vulnerabilities-to-hdf/... -run TestSnapshots -update`.
