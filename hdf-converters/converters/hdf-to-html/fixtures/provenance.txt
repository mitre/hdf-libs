# hdf-to-html fixtures — provenance

Recorded 2026-10-02. The base document was checked against this repository's
shared corpus at commit 537505a0; no other upstream was searched, because no
published HDF results document carries the fields this fixture exists for (see
"Why a schema-confirmed fixture" below).

## `input/`

### `rich.json`
Schema-confirmed, NOT real. Adapted from `hdf-fixtures/results/merge-zap.json`
(real `zap-to-hdf` output for OWASP ZAP 2.7.0; sha256 of the base as read on
2026-10-02: `1609750d6b5a107a3e99cb3a6924714bf4baecc5c9edea24a308cbcf16eaa72d`).

Trim, whole elements dropped, no string edited:
- baselines: kept `OWASP ZAP Scan: code.jquery.com` (its 1 requirement) and
  `OWASP ZAP Scan: mymac.com`; dropped the other 2 of 4.
- `OWASP ZAP Scan: mymac.com` requirements: kept the first requirement at each
  distinct impact in document order (`90028`, `10095`, `42`); dropped the other
  22 of 25.
- components: kept `code.jquery.com` and `mymac.com`; dropped the other 2 of 4.

Edits, made with this repository's CLI built from this branch (`hdf` dev build):
- `hdf label set <file> system=Portal environment=production`
- `hdf label set <file> --external-id cmdb=CI0012345 --external-id emass=1234 --component-name mymac.com`
- `hdf label set <file> --external-id cmdb=CI0067890 --component-name code.jquery.com`
- `hdf label set <file> --generate-component-id`
  These re-serialize the document (object keys sorted, two-space indent); no
  string value from the base changed.

Edits made by hand, which is why the file is schema-confirmed and not real:
- the two generated `componentId` values were replaced with the two example
  UUIDs from `hdf-schema/src/schemas/primitives/component.schema.json`, so the
  fixture does not change on regeneration;
- top-level `systemRef` added (`systems/portal.hdf-system.json`);
- top-level `runner` added (`name`, `hostname`, `architecture`, `release`);
- one `statusOverrides` entry (a `waiver` to `passed`, expiring
  `2099-12-31T00:00:00Z`) added to requirement `90028` of
  `OWASP ZAP Scan: mymac.com`. Its `reason` is two lines.

### `finding-detail.json`
Schema-confirmed, NOT real. Built for the case on 2026-10-02: one baseline with
one requirement that carries every optional field the report renders beyond the
basics (`sourceLocation`, `cwe`, `cvss`, `epss`, `kev`, `affectedPackages`,
`evidence`, `refs` in all three of its forms, non-control `tags`, the v3.2
classification fields, a result with `resource`, `exception`, `backtrace` and
`runTime`, a `statusOverrides` entry with `impact` and `justification`, a
`poams` entry with a milestone, the baseline's descriptive fields, and
`externalReferences` at the document, baseline, requirement and override
levels). The four `externalReferences` entries taken from the published schema
are the `examples` of `External_Reference` in
`hdf-schema/src/schemas/primitives/common.schema.json`, verbatim. Its
identifiers and prose follow the shape of a Brakeman mass-assignment finding
but describe no real scan. No real document carries all of these fields at once.

### Why a schema-confirmed fixture
A search of every HDF results document in this repository on 2026-10-02 found
none that carries `systemRef`, and none of established real origin that carries
component `labels` and `externalIds` on more than one component. The report
exists to show exactly those fields, so the case has to be covered. The file
proves that the shape is one the HDF schema admits, nothing more.

Real-data coverage does not rest on this file: the converter tests also run the
unmodified shared fixture `hdf-fixtures/results/merge-zap.json` (four baselines,
four components, 28 requirements) through both languages and pin the output by
digest (`expected/real-digests.json`), and count its components, baselines and
requirements against the report (`TestConvertHDFToHTML_OutputCountAnchor`). The
embedded-enrichment path is likewise run on the enrich pass's golden output,
`results-enriched.golden.json`, in both languages.

## `expected/`

Generated by this repository's converters, not sourced. Regenerate with
`go test ./converters/hdf-to-html/go/ -update`; Go owns regeneration and the
TypeScript tests verify against the same files.

Each HTML golden embeds the report's stylesheet and script in full, including the
vendored third-party stylesheet; that artifact's own record — package, version,
sha256, licence, retrieval date — is `../go/assets/provenance.txt`.

- `rich.executive.html`, `rich.manager.html`, `rich.administrator.html` — the
  report for `input/rich.json` at each report type.
- `finding-detail.administrator.html` — the report for
  `input/finding-detail.json`.
- `aggregate.executive.html`, `aggregate.manager.html`,
  `aggregate.administrator.html` — the combined report for `input/rich.json`
  and `input/finding-detail.json`, in that order, under those names.
- `corpus-outputs.json` — the report body for every case of the shared
  adversarial results corpus (`hdf-converters/internal/corpus`), or `REJECTED`.
- `real-digests.json` — sha256 of the report for `merge-zap.json` at each report
  type, and for `hdf-converters/shared/enrich-fixtures/results-enriched.golden.json`
  (the enrich pass's own golden: results carrying STIX 2.1 objects from the
  poison-ivy bundle), read in place and not copied; and of the combined report
  for those two documents together.

## Schema

The input is an HDF document; its schema is this repository's own
(`hdf-schema`). `rich.json` validated as hdf-results with `hdf validate --type
results` on 2026-10-02, and stays validated by
`TestRichFixture_IsValidHDFAndCarriesWhatItIsFor` (Go, `hdf-validators`) and the
"holds rich.json to the HDF schema" test (TypeScript). `finding-detail.json`
validated the same way on 2026-10-02 and stays validated by
`TestConvertHDFToHTML_FindingDetail` (Go) and its TypeScript counterpart. The target format, HTML,
has no schema to vendor; the tests check the output is well-formed and
self-contained instead.
