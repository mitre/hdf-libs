# CSAF VEX fixture provenance

## Inputs

All five inputs are **verbatim copies** of the official OASIS CSAF spec
repository's `csaf_2.0/examples/csaf/csaf_vex/` directory:
https://github.com/oasis-tcs/csaf/tree/master/csaf_2.0/examples/csaf/csaf_vex

- `2022-evd-uc-01-na-001.json` — Use Case 1, "Not Affected" status.
  Produces one `falsePositive` override.
- `2022-evd-uc-01-f-001.json` — Use Case 1, "Fixed" status. Produces one
  POA&M override pinned to `failed` pending re-scan.
- `2022-evd-uc-01-a-001.json` — Use Case 1, "Affected" status. Produces
  no override (informational); exercises the empty-actionable-statements
  error path.
- `2022-evd-uc-01-ui-001.json` — Use Case 1, "Under Investigation"
  status. Also produces no override; same error path.
- `sec-vex-2022-0001.json` — Secvisogram's own VEX statement asserting
  no exposure to Log4Shell. Three CVEs, each with `flags[]` carrying
  `component_not_present` — exercises the flag-derived justification path.

## Spec schema

The CSAF 2.0 JSON Schema and the three FIRST.org CVSS schemas it `$ref`s are
vendored ONCE for this format, under the exporter that is gated on them:
`../../hdf-to-csaf-vex/schemas/`, with sources, the pinned OASIS `csaf-2.0-os`
ref and SHA-256s in that directory's `provenance.json` and `provenance.txt`.

The fixtures here are verbatim spec-repo examples (route #1 "documented
provenance" per `build-converter.md` Step 2), so re-validating them is not
required to demonstrate fixture integrity. If it is wanted anyway, the
exporter's Go and TypeScript harnesses both compile that schema offline; the
official OASIS CSAF Python validator (`csaf-validator`) is the out-of-repo
alternative.

## Product identity via product_tree

CSAF product references in `product_status.{known_not_affected,fixed,...}`
are opaque document-local strings (`CSAFPID-XYZ`). The importer walks
the document's `product_tree` to resolve each id into structured
`Standalone_Override.affectedPackages[]` entries:

1. Prefer `product_identification_helper.purl`
2. Else `product_identification_helper.cpe`
3. Else assemble name+version from ancestor `product_name` /
   `product_version` branches (ecosystem stays `generic` since CSAF does
   not disambiguate package managers)
4. Else drop the entry — the schema forbids fabricating identity

**Known partial-fidelity boundary:** CSAF documents that scope by
`product_version_range` (e.g. `<=1.14.0`) carry only a range expression,
not a concrete version. The walker correctly skips these rather than
emit a version-range-string as a version. The `sec-vex-2022-0001.json`
fixture exercises this case; its overrides intentionally have no
`affectedPackages`, and the exporter falls back to the `HDFPID-0001`
placeholder on re-export. Round-trip is idempotent (round 1 and round 2
produce the same HDF state).

## Expected

`expected/*.json` are regenerated by the CLI on every run — they record
the round-trip HDF Amendments output for visual diff review. They do not
gate the test suite; the in-memory Go and TypeScript tests are
authoritative.
