## Context

HDF's **eight** document types (results, baseline, system, plan, amendments, evidence-package, comparison, requirement-change-event) are published as JSON Schema 2020-12 bundles (`hdf-schema/dist/schemas/`, tracked copy in `hdf-validators/go/schemas/`, hosted on the project site), with generated TS/Go/Python types. Anyone building an HTTP service over HDF needs those shapes as OpenAPI components; without a published set, every builder hand-translates the schemas and drifts.

**What this ADR was, and what it is now.** Revisions 1–11 made this package two things: the components document, and a **reference API generated from the MCP contract** — a hand-authored binding table mapping each MCP tool to a route, a Go test reflecting the tools' schemas into a golden, and a generator producing `hdf-api.oas.json`. The platform's server generated its route schemas from that document and proved by a projection that what it served matched. Three decisions on 2026-10-12, **agreed by both deciders** (as reported by the owner), end the second half: the API document moves to `hdf-data-platform`, beside the server that implements it (its ADR-0018); the API is designed on its own and written as route declarations in TypeScript, with the OpenAPI document generated from them (committing it is ADR-0018 §6's choice); and the MCP server becomes one client of that API (ADR-0007's proposed bullet of 2026-10-13, on this branch). What remains here is the half that belongs to the format repository: **the HDF schemas as OpenAPI components**. The reasons, in brief, from `hdf-data-platform`'s research note of 2026-10-12: every API addition was an MCP tool, then a binding, then an `hdf-libs` release before the platform could implement it — the loop §6 of revision 8 named and listed as its challenge (l); the generated API inherited the tools' shapes (ten operations with no response schema, `422` on reads, `200` on creation, tool names in paths); and agent tools and HTTP operations are not meant to mirror each other. Measured there: all 18 operations of this package's last generated document, rebuilt as declarations, compared value for value with none of 263 differences changing meaning, and 127 of 127 of these components passed through byte-identical — so the components document is exactly what the new arrangement needs from this repository, and nothing more.

Forces that still shape the components document (counts re-measured against the tracked embed at schema v3.7.0 in revision 9; the v3.8.0 re-count is Phase 1a's first acceptance criterion):

- **The bundles are compound documents, not drop-in components.** The bundler (`@hyperjump/json-schema`, `definitionNamingStrategy: 'uri'`) embeds each primitive resource as a URL-keyed `$defs` entry carrying its own `$id`/`$schema`. Across the eight bundles: 115 named definitions plus 19 URL-keyed resource wrappers; 411 absolute `$ref`s and 348 local pointers that resolve against the enclosing resource's `$id`; the `hdf-results` resource is itself embedded inside comparison and change-event. Zero same-name/different-definition collisions. OpenAPI component keys must match `^[a-zA-Z0-9.\-_]+$`, and pointer-based codegens resolve by JSON pointer, not `$id`. Schema 3.8.0 adds `Raw_Source_Artifact`, the closed `extensions` object with `extensions.passthrough`, and new members on `External_Reference` and `results[]` (ADR-0017), so the definition count rises; the transform's guards count, they do not assume.
- **2020-12 features in play** — in the bundles, 282 `unevaluatedProperties` sites; in source, 77 `unevaluatedProperties`, 8 `if`, 3 boolean-`false` subschemas (the `Bom` else-branches), 1 `dependentRequired`, 38 `$comment`, `examples` on 46 definitions and 7 roots. Also present: `contains`+`const`, `type: [string, null]` enums, `$ref` with sibling `description`. No `$dynamicRef`/`$anchor`/`patternProperties`/`prefixItems`. All OpenAPI-3.1-legal; tool support is uneven and is measured (§5).
- **The repo's validators do not enforce `unevaluatedProperties`** (draft-07 engines), so "validates with hdf-validators" is weaker than "conforms to the schema text". Conformance tests here use a 2020-12 engine; the validator gap is carded under `hdf-data-platform`'s ADR-0009 as an `hdf-libs` prerequisite.
- **The schema `$id` embeds the schema version** (`v3.8.0` on `main` while the package is `3.7.2`); patch releases leave `$id` unchanged. The components document's `info.version` is the `$id` version.
- **Zod cannot be derived from these schemas** (verified 2026-09-02; unchanged): `z.fromJSONSchema()` throws on `unevaluatedProperties`, `if/then/else`, `dependentRequired` and external `$ref`. That is why every consumer passes the components through untouched and validates documents with a 2020-12 engine (ADR-0018 §3).

**Open pull requests touched by this revision.** #414 (`feat/hdf-openapi-components`) is the components document and lands as Phases 1a, 1b and 4. #438 (`feat/mcp-contract-enums-and-shapes`) is prerequisites (a) and (b) of revisions 2–11: the twelve closed vocabularies reaching `tools/list` as real `enum` arrays stand on their own merit and land; the `internal/mcp/contract` package reflecting response shapes into `mcp-contract.golden.json` was built for the generator and now has no consumer outside `hdf-cli` — challenge (e). #457 (`feat/hdf-openapi-reference-api`) carries the components work, the generator, Go and utilities fixes, and an `hdf-schema` change — a root example for `hdf-comparison` with its tracked embed in `hdf-validators/go/schemas/` and the examples-valid test (against the merge-base; `result.schema.json` and the Go types differ only because `main` moved on) — which is kept and is `hdf-schema`'s. #438's head is already an ancestor of #457, so the two are one landing; #414 diverges from #457 on the same files, so one of them is the base and the other is rebased or closed. #457 also carries **this ADR at revision 20** (2026-10-12; the "Revisions 12–20" bullet in the history lists what they added). Of revision 20's additions, the contract digest with its tracked baseline, the release-time archive-immutability check, the "no `servers`" rule and the lowerCamelCase operationId convention carried to `hdf-api-contract` (ADR-0018 §2, §6, §7); revision 13's `ValidationProblem` and per-operation problem responses, and revision 18's `Retry-After` HTTP-date form and `components.{headers,parameters}`, are **not yet carried** and are listed in ADR-0018 §4 for the platform to adopt or reject; the binding-table, rewrite-map, enum-sourcing and generated-example text is retired with the generator (`generate-api.ts`, `bindings.yaml`, `bindings.ts`, `parity.ts`, the goldens and their sync, the rewrite maps, the synthetic-operation conventions). The conventions, problem catalogue, lint configuration, contract-digest test and response examples carry over to `hdf-api-contract` **from this repository's history at `9416fdfb`**, not from a published package, so nothing in the platform waits on this package to publish before Phase 2 can run. **Landing order.** Two tests in #457, both absent from `main`, read ADR files: `problem-types.test.ts` parses ADR-0010 §6, which the stub commit on this branch replaces with a pointer; `rewrite-map.test.ts` parses this ADR's §2 for the fixed rewrite map, which this revision removes. So this revision and the stub commit each break one of #457's tests, in either order, and the only green sequence is one pull request that carries this text, the stubs and Phase 2's test deletions together, on top of #457's components half. The owner and the maintainer agree that sequence before anything merges. `hdf-data-platform` has been **private** since 2026-10-12: until it is public, every ADR-0018 and research-note reference in this file and in the stubs does not resolve for this repository's readers, and ADR-0018 has no history here to fall back on — a reason this revision does not merge before visibility is settled.

## Decision

Keep **`@mitre/hdf-openapi`** as a leaf package in `hdf-libs` that derives from `@mitre/hdf-schema`; nothing in the repo imports it, and it publishes **one** document.

### 1. The components document (generated)
`dist/hdf-components.oas.json` + `.yaml`, OpenAPI 3.1, `jsonSchemaDialect: https://json-schema.org/draft/2020-12/schema`, produced by an explicit transform over the eight bundles read from the tracked embed (`hdf-validators/go/schemas/`) — never a glob of the gitignored `dist/`, and hard-failing if the file set differs from the bundler's `MAIN_SCHEMAS`. Steps: **unwrap** the URL-keyed resource wrappers (they are not components); **hoist** every named `$defs` entry to `#/components/schemas/<Name>`; **rewrite** `$ref`s resource-scoped (a local pointer is resolved against its enclosing resource's `$id` before rewriting — never a global string replace); **strip** embedded `$id`/`$schema`; **deduplicate** by deep-equality after stripping, recognizing the embedded `hdf-results` resource as the `HdfResults` root; **name** the eight roots (`HdfResults`, `HdfBaseline`, `HdfSystem`, `HdfPlan`, `HdfAmendments`, `HdfEvidencePackage`, `HdfComparison`, `HdfRequirementChangeEvent`); **pass through untouched** every 2020-12 feature listed in Context; retain `examples` and `$comment`. Guards: a same-name/different-definition collision fails the build; a count mismatch against the recorded golden fails the build; an `info.version` that differs from the `$id` version fails the build. The document carries no `paths`, no `securitySchemes`, no `servers`.

### 3. Placement, packaging, name
**This package stays in `hdf-libs`** (ADR-0012 §2 invariant 11; follows from the agreed decision that the components document stays here): it derives from this repository's schemas and nothing else, and it is consumed by `hdf-data-platform` as a published, pinned package — the first of the five things ADR-0012 lists as crossing the repository boundary. The loop revision 8 described (an operation the server needs is first a binding here, released, then implementable there) no longer exists, because this package publishes no operations. Separate from `@mitre/hdf-schema` (Alternative E) so lint and codegen tooling never enter the schema package's dependency tree. Exports: `.` (TS: `components`, `validateExample`) plus the two document files; `files: ["dist"]`; `publint` + `attw` clean. The exports `./hdf-api.oas.json` and `./problems.json` of #457 would not be published (they go with the generator). **Name — proposed, challenge (b)**: by the vendor convention (`stripe/openapi`, `digitalocean/openapi`) a package called `hdf-openapi` reads as "the OpenAPI description of the HDF API", which since 2026-10-12 it is not; `@mitre/hdf-openapi-components` would say what it holds. Renaming is cheap while only a placeholder (`0.0.1-reserve.0`, deprecated "Use >=3.8.0") is published and the two pull requests are open; it is the maintainer's call. The components document's one consumer, `hdf-api-contract`, registers the components by name and guards against a declared shape colliding with a component name (ADR-0018 §3); this package guards the other side (§1).

### 4. Versioning and layout
`info.version` of the components document is the schema `$id` version (`3.8.0`), asserted against the embed at build. The document is self-contained: no file refs, no network refs (Alternative G). Site archive under `openapi/hdf-components/v<version>/`, immutable once published (a release step asserts no archived path changes — revision 20 moved this check from the generator to release time for the API archive, and the components archive follows the same rule). The archive paths `openapi/hdf-api/v1.0.0/` and `v2.0.0/` of the retired generator would stay as published, with an index note that they describe a superseded contract and that the API document now lives with `hdf-data-platform` (proposed; ADR-0018 §7 challenge (k)).

### 5. Tooling compatibility is measured
- **Redocly CLI alone lints the components document.** The Spectral rules of revisions 5–11 were written for operations and security schemes and move with them to `hdf-api-contract`; on a components document the OWASP API ruleset has almost nothing to say (measured in the Phase 1b spike: of 746 findings, 735 were resource-consumption rules bounding a request surface this document does not have, 9 were operation-less-document rules, 1 was `info-contact`, and exactly one was genuine — `Input_Constraints.allowedValues` declaring no `items`, carded separately). The waivers, each with its reason inline in `redocly.yaml`: `no-empty-servers` and `no-unused-components` (it is a components library); `no-invalid-schema-examples` and `no-required-schema-properties-undefined` — a reproduced Redocly defect: when a taken `if`/`then`/`else` branch carries its own `properties`, Redocly replaces the parent's `properties` annotations with the branch's instead of unioning them, so `unevaluatedProperties: false` then rejects every declared property (328 false warnings at 2.54; reproduced in seven lines with two controls; contradicted by ajv 8 and `@hyperjump/json-schema`, which accept all affected examples). The waiver counts are tracked in `test/baseline/keywords.json` and re-measured on every Redocly bump (2.63.0 as of 2026-10-13; #457 pins `^2.54.3` and the baseline was recorded at 2.55.0). Revision 11 counted five waivers; `redocly.yaml` in #457 carries four, the `additionalProperties` waiver having been dropped as `oas3_0`-only.
- **`openapi-typescript` loads this document; `oapi-codegen` 2.8.0 does not** — kin-openapi fails with `json: cannot unmarshal bool into field Schema.properties` on the boolean subschemas of the three-tier BOM rule (`else.properties.model: false`), a load-bearing constraint, so the refusal is recorded in `test/baseline/keywords.json` rather than worked around. This is why `hdf-cli`'s Go client is generated from a projection that excludes every HDF definition and carries document bodies as `json.RawMessage` (`hdf-data-platform` ADR-0010 §3).
- **Both generators discard every validation keyword** — `minimum`, `maximum`, `minLength`, `pattern`, `contains`, `not`, `dependentRequired`, `if`/`then`/`else`, `unevaluatedProperties`. Generated types are shape-only; validation of a document is always a 2020-12 engine's job, never a generated type's.
- A tracked per-keyword honoured/ignored baseline that CI diffs, measured differentially (generate with the keyword, generate without it, compare bytes), published on the site. `REDOCLY_TELEMETRY=off`.
- Node floor: Redocly ≥ 22.12; this package documents the repository's floor and adds no requirement of its own. (The `@hey-api/openapi-ts` floor of ≥ 22.18 and its incompatibility with TypeScript 7 are `hdf-data-platform`'s concern now.)

## Reviewer challenge points

Will's review — and any agent review he runs — should specifically challenge or verify: (a) **the reduction itself** (§2) — agreed by both deciders on 2026-10-12, retained so the record shows where revisions 1–11's challenge letters (a) generating the API from the MCP contract, (b) the binding-table grammar, (c) HTTP as the canonical full shape, (f) the convention-owned problem types, (g) the derivation pipeline, (h) parity by projection, (i) the synthetic-operation rule, (j) the HTTP conventions, (k) the companion document and (l) keeping the package here were decided: (a), (b), (g), (h), (i) and (l) are retired with the generator; (c), (f), (j) and (k) carried to ADR-0018 and `hdf-data-platform` ADR-0011; (d) the identity model and (e) the jobs contract carried to ADR-0018 §4; (m) the DOCTYPE rule carried to ADR-0018 §4 with its helper staying in `hdf-utilities`; (b) **the package name** (§3) — `hdf-openapi` or `hdf-openapi-components`, while renaming is cheap; (c) **the components-only waiver set** (§5) and whether the Redocly defect waiver should be re-tested on 2.63; (d) **recording the `oapi-codegen` refusal rather than working around it** (§5), which commits `hdf-cli`'s client to `json.RawMessage` bodies; (e) **what becomes of #438's reflected-shapes golden** (Context) — reduce it to what the eval harness needs, or drop it.

## Alternatives Considered

### A. Hand-authored OpenAPI components
Why rejected: drift across 115-plus definitions; the schemas are the only authored source of document shapes (ADR-0012 §2 invariant 1).

### B. Hand-authored reference API (revision 1) · C. Defer the API to a server ADR · I. Zod-first routes generating the document · J. Zod derived from the bundles · K. Parity by validating the running server · L. Fold auth management into the API document
Moved: these were alternatives to the API half of this ADR and are now ADR-0018's (its Alternatives A–E) and `hdf-data-platform` ADR-0011's. Of them, the one that is now the decision is the one revision 1–11 called I: route declarations are the source and the document is generated from them, with the three reasons it was rejected here lapsed or handled (ADR-0018 Context).

### D. Content-hash document ids
Carried to ADR-0018 §4 (opaque uuid plus `sha256` as `ETag`), unchanged.

### E. Ship inside `@mitre/hdf-schema`
Why rejected: dependency and release coupling on the ecosystem's most-consumed package.

### F. OpenAPI 3.0 with down-converted schemas
Why rejected: lossy (no `if`/`then`, `unevaluatedProperties`, type arrays).

### G. Components that `$ref` hosted schema URLs
Why rejected: network-dependent documents break air-gapped use, codegens and CI determinism.

### H. Do nothing
Why rejected: `hdf-api-contract` references these components by name and would otherwise restate the schemas, which ADR-0012 §2 invariant 1 forbids.

## Consequences

Easier: one document, one transform, one set of guards; API builders — `hdf-api-contract` first — `$ref` HDF types and never restate them; the package has no opinion about operations, so it never gates an API change; schema bumps are one regeneration with recorded counts.

Harder: this package no longer guarantees anything about the API; the MCP and the API agree by `hdf-data-platform`'s parity suite, not by construction; the generator work of #457 is retired after it was written; the `hdf-api` archive on the site carries two superseded versions; the reflected-shapes golden of #438 needs a decision.

Risks and mitigations: tool lag → the measured baseline; components drift from the bundles → the count and collision guards, and the semantic conformance tests with negatives; a schema bump changes definitions silently → the `$id` version assertion and the recorded counts; the consumer collides a name with a component → both sides guard (§3); an archived version is overwritten → the release-step assertion restored in §4.

## Implementation Plan
