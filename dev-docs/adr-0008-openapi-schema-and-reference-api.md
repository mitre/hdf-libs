## Context

HDF's **eight** document types (results, baseline, system, plan, amendments, evidence-package, comparison, requirement-change-event) are published as JSON Schema 2020-12 bundles (`hdf-schema/dist/schemas/`, tracked copy in `hdf-validators/go/schemas/`, hosted at `https://mitre.github.io/hdf-libs/schemas/`), with generated TS/Go/Python types. There is no OpenAPI artifact, so anyone building an HTTP service over HDF — an `hdf-serve` mode of the CLI, Heimdall-class viewers, SAF pipeline services, partner tooling — hand-translates the schemas and hand-invents an API, and both drift.

The HDF MCP server (ADR-0007) already defines a typed operation surface: nine tools (`hdf_open`, `hdf_inspect`, `hdf_query`, `hdf_compliance`, `hdf_diff`, `hdf_validate`, `hdf_convert`, `hdf_author`, `hdf_apply_amendment`), five resource families (`hdf://schema/{docType}`, `hdf://schema/{docType}/{def}{?view}`, `hdf://enum/{name}`, `hdf://catalog/converters`, `hdf://session/transcript`), and a closed 12-code error taxonomy (`hdf-cli/internal/mcp/mcperr`). `tools/list` returns both `inputSchema` and `outputSchema` for every tool, and the repo already byte-compares that output against a tracked golden (`hdf-cli/internal/mcp/evalharness/testdata/tools-list.golden.json`).

Forces established by the reviews (counts re-measured against the tracked embed):

- **The bundles are compound documents, not drop-in components.** The bundler (`@hyperjump/json-schema`, `definitionNamingStrategy: 'uri'`) embeds each primitive resource as a URL-keyed `$defs` entry carrying its own `$id`/`$schema`. Across the eight bundles: 115 named definitions plus 19 URL-keyed resource wrappers; 408 absolute `$ref`s and 348 local pointers that resolve against the enclosing resource's `$id`; the `hdf-results` resource is itself embedded inside comparison and change-event. Source has 129 definitions, 14 (`target`/`platform` primitives) unreferenced and never bundled. Zero same-name/different-definition collisions today. OpenAPI component keys must match `^[a-zA-Z0-9.\-_]+$`, and pointer-based codegens resolve by JSON pointer, not `$id`.
- **2020-12 features in play**: 282 `unevaluatedProperties` sites in the bundles (77 in source), 7 `if`, 3 boolean-`false` subschemas (`Bom` else-branches), 1 `dependentRequired`, `contains`+`const`, `type: [string, null]` enums, `$ref` with sibling `description`, 74 `$comment`, `examples` on 45 definitions and 7 roots. No `$dynamicRef`/`$anchor`/`patternProperties`/`prefixItems`. All OpenAPI-3.1-legal; tool support is uneven and must be measured.
- **The MCP schemas are not a complete contract source.** Go SDK `jsonschema` tags become descriptions only — enums appear as prose (`"passed|failed|..."`, `"concise (default) or full"`, `"schema, checksums, or completeness"`), never `enum` arrays; the full row/summary shapes for query, diff, compliance, inspect, and convert-batch live in unexported Go types (some built as `map[string]any` per docType or per mode×verbosity) or in `hdf-engine`; MCP inputs are filesystem-shaped (`source.path`, `output`, `outputDir`, `overwrite`, `directory`, `dryRun`); MCP pagination is token-budgeted `page`/`nextPage`/`notice`/`truncated`; write tools are gated by `HDF_MCP_ENABLE_WRITES` and return a success-shaped `writesDisabled` preview. A generator must handle each of these explicitly or it is hand-authoring in disguise.
- **The repo's validators do not enforce `unevaluatedProperties`** (draft-07 engines in both languages), so "validates with hdf-validators" is weaker than "conforms to the schema text". Conformance tests here must use a 2020-12 engine; the validator gap is carded under ADR-0009 §5.
- The schema `$id` embeds the schema version (`v3.5.0`) while the package is `3.5.1`; patch releases leave `$id` unchanged. The OpenAPI artifacts need their own version axis.
- The CLI/MCP boundary already enforces input gates (50 MB caps, symlink/regular-file checks, XML entity checks that today only scan the first 4 KB for `<!ENTITY`, `SafePath`, per-tool timeouts, output redaction). An HTTP boundary is strictly more hostile and must carry equivalent gates in the contract.
- **The producer is now decided** (revision 5): ADR-0011 builds `hdf-serve` as a **TypeScript (Hono) service** over ADR-0010's data layer. That closes the "semantic drift not caught without a producer" risk of revision 4 — but only if the service and this document cannot diverge. Zod-first frameworks (`@hono/zod-openapi` 1.6.x, `fastify-type-provider-zod` 7.x, oRPC 1.15) *generate* OpenAPI from Zod routes; combined with this ADR's generator that would be two contracts.
- **Zod facts** (verified 2026-09-02): zod 4.5.x; `z.toJSONSchema()` targets 2020-12/draft-07/draft-04/OpenAPI 3.0; `z.fromJSONSchema()` (since 4.2, experimental) **throws** on `unevaluatedProperties`, `if/then/else`, `dependentRequired`, external `$ref`, and returns an untyped `ZodType` — the HDF bundles carry 77 `unevaluatedProperties` and 7 `if` in source, so Zod cannot be derived from the document schemas; `json-schema-to-zod` was archived 2026-06-30. `@hey-api/openapi-ts` 0.99 generates Zod v4 schemas, a typed client, and response validators from an OpenAPI 3.1 document. No workspace package depends on `zod` today (hdf-schema uses ajv 8 + quicktype).

## Decision

Create a new workspace package **`@mitre/hdf-openapi`** — a leaf package that derives from `@mitre/hdf-schema` and from the CLI's MCP contract; nothing in the repo imports it.

### 1. Components document (generated)
`dist/hdf-components.oas.json` + `.yaml`, OpenAPI 3.1, `jsonSchemaDialect: https://json-schema.org/draft/2020-12/schema`, produced by an explicit transform over the eight bundles read from the tracked embed (`hdf-validators/go/schemas/`) — never a glob of the gitignored `dist/`, and hard-failing if the file set differs from the bundler's `MAIN_SCHEMAS`. Steps: **unwrap** the 19 URL-keyed resource wrappers (they are not components); **hoist** every named `$defs` entry to `#/components/schemas/<Name>`; **rewrite** `$ref`s resource-scoped (a local pointer is resolved against its enclosing resource's `$id` before rewriting — never a global string replace); **strip** embedded `$id`/`$schema`; **deduplicate** by deep-equality after stripping, recognizing the embedded `hdf-results` resource as the `HdfResults` root; **name** the eight roots (`HdfResults`, `HdfBaseline`, …); **pass through untouched** every 2020-12 feature listed in Context; retain `examples` and `$comment`. Guards: a same-name/different-definition collision fails the build; a count mismatch fails the build.

### 2. Reference API document (generated from the MCP contract)
`dist/hdf-api.oas.json` + `.yaml`, generated from one **MCP contract golden** plus one hand-authored **binding table**.

- **The golden.** The existing `tools-list.golden.json` is extended by the same Go test into a single `mcp-contract.golden.json` holding `tools/list`, `resources/list`, `resources/templates/list`, `mcperr.Codes`, and **reflected full shapes** (`fullShapes`) of exported Go types. The build syncs it into `hdf-openapi/src/` (validators-embed pattern); a CI step regenerates and fails on diff. Three prerequisite cards in `hdf-cli`/`hdf-utilities` precede Phase 2: **(a)** tool input schemas carry real `enum` arrays for `hdf_query.status`/`severity`, `hdf_compliance.groupBy`, `verbosity` (query/inspect/diff), `hdf_diff.mode`, `hdf_validate.mode`, `hdf_author.docType`, `hdf_convert.from` (sourced from the schema enums and the converter registry); **(b)** full shapes exported and reflected: the query concise/full rows, the four diff row types registered under `diff.temporal.concise|full` and `diff.system-drift.concise|full` (the two `hdf_diff.mode` values), the convert batch entry, per-docType open summaries (or listed as `absent` with reason), and `hdf-engine`'s `StatusCounts`/`ThresholdConfig`; the reflection has a **registration hook** so other Go modules can contribute shapes — ADR-0010's precedent rows (`PrecedentRow`, `SimilarSystemRow`, `SimilarRow`) are registered by the ADR-0007 amendment that adds the precedent tools, and that amendment card also carries this package's `bindings.yaml` entries for them; **(c)** the XML helper is created for TS and hardened in Go to scan to the root element and reject any `<!DOCTYPE`, so the contract's rule cites a helper that satisfies it.
- **The binding table** (`src/bindings.yaml`) has a closed grammar: per tool — `method`, `path`, per-field `placement ∈ {path, query, body}`, `bodyRef: <components key | fullShapes key>` (name only), `drop: [{name, reason}]`, `enumFrom: <schema enum | registry>`, `items: <output field that becomes the envelope's items>`, `fullResponse: <fullShapes key or discriminated list of keys>`; `class` is derived from the tool's `readOnlyHint`, never hand-set (`hdf_diff` is read-only; its `output`/`overwrite` inputs are dropped, which is why the derived class is correct); per resource — `method`, `path`; one `synthetic` section for the **four** operations MCP lacks, each with its `class` and scopes **hand-set** (synthetic operations have no `readOnlyHint`; this is the documented exception to derivation): ingest (`hdf:write`; document body → id; body `bodyRef`-only, the eight roots as `oneOf`), delete (`hdf:admin`; `DELETE /documents/{id}` → 204, 409 `delete-restricted` when a citing document restricts it per ADR-0009 §5, 409 `held` under an ADR-0013 legal hold), and two **`documentOnly`** token-issuing operations served by the authorization server rather than by service routes — `POST /api/auth/oauth2/token` (RFC 6749 `client_credentials` form body with RFC 8707 `resource` **required** → `{access_token, token_type, expires_in, scope}`) and `POST /api/auth/api-key/exchange` (ADR-0011 §3; key in the body, same response shape) — both with `security: []` (Spectral's `operation-security-defined` accepts the empty array); each `bodyRef`-only or a fixed conventions component, never an inline schema. **The synthetic-operation rule**, which keeps this section a mapping rather than a hand-authored API: a synthetic operation's request and response shapes are either a conventions component or a **reflected type registered through prerequisite (b)'s hook** (Go types from `hdf-cli`/`hdf-data`; a TypeScript twin hook in `hdf-serve` registers the service's own shapes into the same golden), referenced by `bodyRef`/`fullResponse` name only; class and scopes are hand-set; one card per operation; the no-fragment AC applies. Under that rule ADR-0013's phases add every HDF-owned route it defines (`GET /audit`, the `202`/`GET /jobs/{id}`/`GET /jobs/{id}/result` group, evidence `PUT`/`GET`, hold, export, usage, webhooks), and the companion document of §7 stays strictly `/api/auth/*`; an `absent: [{tool|resource|field, reason}]` allowlist (the session transcript; MCP-only fields; components with no Go type). The generator **hard-fails** on any input property whose description mentions `HDF_MCP_ROOT` or whose name is one of `path`, `output`, `outputDir`, `overwrite`, `directory`, `pattern`, `failFast`, `sources`, `dryRun` unless it is in `drop`. A **fixed rewrite map** applies to every operation: inputs `page` (int) → cursor `next`, `limit` count-based; outputs `handle` → `id`, `page`/`nextPage`/`notice`/`truncated`/`returned` → the envelope's `next` (or dropped), `total` kept, `writesDisabled` and `outputPath` stripped; the table's `items` key names the row array. Go nil semantics (`["null","array"]`) are normalized to non-null. The **no-fragment AC is mechanical**: every leaf in `bindings.yaml` is a scalar from the closed key set; any `type`, `properties`, `$ref`, `items` (as a schema), `oneOf`, or `allOf` key anywhere in the file fails the build.
- HTTP responses are the **canonical full shapes**; MCP payloads stay the token-budgeted subset (this inverts ADR-0007's framing for the HTTP surface only — reviewer challenge (c)).

### 3. Contract conventions (shared components applied to every operation)
- **Identity**: the wire id is a server-issued opaque `uuid` per ingest (matching ADR-0009's `documents.id`); `sha256` of the ingested bytes is exposed as `ETag` and as `integrity.sourceSha256`; `If-Match` gates write operations (on `hdf_apply_amendment` it gates the results target), so `412` is meaningful and maps `HANDLE_STALE`. Within one tenant, re-ingesting identical bytes returns the existing id (`200`); across tenants the same bytes are distinct documents. All lookups are tenant-scoped: an id owned elsewhere is a uniform `404`, never `403`/`409`. Ids are never filesystem paths.
- **Bodies and limits**: inline JSON or multipart for conversion inputs; every operation with a `requestBody` MUST declare `413` and `415` (custom Spectral rule, planted-omission test); the effective size cap is advertised on the catalog operation and defaults to the CLI's 50 MB; content-type allowlist; XML inputs MUST be rejected on any `<!DOCTYPE` before the root element; `from`/`to` are enums from the converter registry (`to` is CLI-only and listed in `absent` with reason as a synthetic addition).
- **Pagination**: HTTP envelope `{items, next, total?, limit}` with an opaque cursor `next` and a `limit` that carries an OpenAPI `maximum`; an over-limit value is coerced down and the effective `limit` echoed (the AIP-158 convention); MCP's token budget never surfaces.
- **Load and errors on every operation**: `429` and `503` with `Retry-After`, plus the IETF `RateLimit` and `RateLimit-Policy` structured-field headers on every response (draft-ietf-httpapi-ratelimit-headers-11: `RateLimit-Policy: "default";q=600;w=60` and `RateLimit: "default";r=599;t=42` — quota, window seconds, remaining, seconds to reset — the shape the OWASP API ruleset checks for); a declared `500` with a problem body on every operation (`type` `…/problems/internal-error`, no detail beyond a request id). `413`, `415`, `429`, and `503` carry site-hosted types (`…/problems/payload-too-large`, `unsupported-media-type`, `rate-limited` for the rate limiter and `quota-exceeded` for ADR-0013's quotas — two `429` types, distinguished by `type` and the `quota` member —, `store-unavailable` when the data layer raises it); `400` and `401` stay `about:blank`. **Jobs** (ADR-0013 §2): a job-producing operation returns `202` with `Location: /jobs/{id}`, `Retry-After`, and the job body; `GET /jobs/{id}` returns `200` with `Retry-After` while the job runs and `result: {ref}` when it completes — no `303`; `GET /jobs/{id}/result` streams an export as `application/x-tar` with `Content-Disposition: attachment`, `Content-Length`, and RFC 9110 ranges (`206`/`416`), and answers `410` after its lifetime — `410` is reserved in the conventions for that purpose. One conventions component, **`Binary`** (`application/octet-stream`, `type: string`, `contentMediaType`), carries evidence bytes; `binary` is the one `format` outside the §7 allowlist, permitted only on that component.
- **Evolution**: no version segment in paths; `info.version` and the `x-hdf-schema-version` response header carry versions; a deprecated operation carries `deprecated: true`, `x-hdf-deprecation` and `x-hdf-sunset` dates (deprecation never after sunset), and the service emits RFC 9745 `Deprecation: @<unix-seconds>` (a structured-field date), RFC 8594 `Sunset: <HTTP-date>`, and `Link: <https://mitre.github.io/hdf-libs/openapi/deprecations>; rel="deprecation"; type="text/html"` — a custom Spectral rule fails a deprecated operation missing either date (no built-in rule exists for this). The break policy is one line: a removed or reshaped operation is a major of this document. Idempotent ingest uses the document's `sha256` as the secondary key (Zalando #231), not an `Idempotency-Key` header (that draft expired in 2025). Property names stay camelCase as the schemas define them — a recorded deviation from Zalando #118.
- **Security**: one `http`/`bearer` scheme (`bearerFormat: JWT`) whose `description` points at the deployment's RFC 9728 protected-resource metadata (`/.well-known/oauth-protected-resource`), and the closed scope vocabulary **`hdf:read`, `hdf:write`, `hdf:admin`** listed as `x-hdf-scopes` on the scheme. Per-operation scopes are expressed as the **requirement-array role names** OpenAPI 3.1 permits for non-OAuth schemes ("the array MAY contain a list of role names which are required for the execution" — 3.0 forbade this, so 3.0-era Spectral rules that flag it are overridden in the tracked ruleset). The document does not describe issuance, flows, or an authorization server (ADR-0011 §3 owns those; MCP clients discover the authorization server through RFC 9728, not through this document) and no `oauth2` scheme is added because its URLs vary per deployment. A `security` requirement on **every** operation (Spectral `operation-security-defined`; the two `documentOnly` token operations carry `security: []`); read-class operations require `hdf:read`; write-class operations (`readOnlyHint: false`) additionally require `hdf:write`; delete and organization routes require `hdf:admin`. **Every scope failure is one shape**: `403` with the site-hosted `type` `…/problems/insufficient-scope`, title `Insufficient scope`, an extension member `scope` naming the missing scope, and the RFC 6750 header `WWW-Authenticate: Bearer error="insufficient_scope", scope="…", resource_metadata="…"`; `401` is `about:blank` with `WWW-Authenticate: Bearer resource_metadata="…", scope="hdf:read"` (the MCP 2026-07-28 revision asks for `scope` on the 401 challenge). A token that carries no resolvable organization is not a scope failure — no re-authorization satisfies it — so it is the **second** convention-owned type, `…/problems/no-active-organization`, title `No active organization`, `403`, **no** `WWW-Authenticate`. MCP's success-shaped `writesDisabled` preview does not transfer to HTTP and no `writes-disabled` title exists (revision 4's `about:blank` + custom title violated RFC 9457 §4.2.1). These two `type` URIs beyond the `mcperr` mapping are owned by the conventions, not a taxonomy extension — challenge (f).
- **Errors**: RFC 9457. Domain errors carry `type` URIs hosted on the site, mapped one-to-one onto the closed `mcperr` taxonomy: `DOCUMENT_NOT_FOUND`→404, `TOO_LARGE`→413, `SCHEMA_INVALID`→422 (+ `errors[]` of `{path,line,message}`), `HANDLE_STALE`→412, `NO_CONVERTER`/`AMBIGUOUS_FORMAT`/`WRONG_DOC_TYPE`→422; intentionally absent: `CACHE_MISS` (authored documents are persisted by `put`, so the code is unreachable on HTTP), `OUTPUT_EXISTS`, `PATH_DENIED`, `WRITE_FAILED` (filesystem-only), `TRUNCATED` (dead in MCP too). `400` (the code-less `mcperr.Arg` class) and `401` use `about:blank`; every other status carries a site-hosted `type` (Security and Load above). The complete code → status → `type` table — every `mcperr` code plus the data-layer codes — is **owned by ADR-0010 §6** and consumed by this generator's conventions; a test in both packages asserts the two agree. `nextCall` is carried as an extension member after rewriting by the generator; a test asserts no `HDF_MCP_` substring or MCP tool name appears in any problem example; `detail` MUST NOT contain paths, host configuration, or raw upstream error strings.
- **Vocabulary**: HTTP uses the schema status vocabulary; the compliance component keeps the threshold vocabulary (`skipped`/`no_impact`) because it *is* the threshold contract, and says so.

### 4. Versioning and layout
Components inline into the API document at build (self-contained; no file refs). `info.version` of the components document is the schema `$id` version; the API document has its own semver from `1.0.0`; `info` carries `x-hdf-schema-version` and `x-hdf-mcp-golden-sha`. Rules: components minor → API minor; components major → API major; golden change → API bump. Site archive under `openapi/<name>/v<version>/`.

### 5. Tooling compatibility is measured
Redocly CLI **and** Spectral for lint — Spectral with the **OWASP API Security ruleset** added to the tracked ruleset, with two waivers recorded in it: the `additionalProperties` and array-limit rules for the HDF `$ref` components (the schemas own those properties) and the 3.0-era scope rule for role names on the `http` scheme; openapi-typescript **and** oapi-codegen for codegen; a tracked per-keyword honored/ignored baseline that CI diffs; published on the site. `REDOCLY_TELEMETRY=off`. Node floor: the strictest tool in the set (`@hey-api/openapi-ts` 0.99 requires ≥ 22.18; Redocly ≥ 22.12) and Node 22's maintenance status mean the repo moves its `engines.node` to **≥ 24** (Active LTS) — carded in ADR-0011 Phase 0; this package documents the same floor.

### 6. Packaging
Separate package (not inside `@mitre/hdf-schema`) so lint/codegen tooling never enters the schema package's dependency tree and release cadence decouples; ADR-0009 §1 adopts the same decision. Exports: `.` (TS: `components`, `apiSpec`, `validateExample`) plus explicit file subpaths; `files: ["dist"]`; `publint` + `attw` clean. Vendor extensions `x-hdf-mcp-tool` / `x-hdf-resource` on every generated operation.

### 7. This document is the contract; Zod and the SDK are derived from it
- **Direction of generation is unchanged**: JSON Schema bundles + the MCP contract golden + the binding table → this document. The service (ADR-0011) **implements** the document; it never authors it.
- **Zod is derived, never hand-written, and never covers HDF documents.** ADR-0011's build runs `@hey-api/openapi-ts` over `dist/hdf-api.oas.json` with the `zod` plugin to produce Zod v4 schemas for every *non-document* shape — path/query parameters, the envelope, problem details, the reflected `fullShapes` responses — which the Hono routes consume as their request/response schemas. One generator setting is load-bearing and measured: Hono hands path and query parameters to the validator as strings, so the run configures the plugin's `~resolvers` for `number`/`integer`/`boolean` to wrap schemas whose `~ref` path contains a `query` or `path` segment in `z.preprocess(…)`; `z.coerce` is forbidden because zod-to-openapi renders it as `type: [T, 'null']` and breaks P. HDF document bodies (the eight roots, `oneOf` on ingest) have **no Zod at all**: the raw component schemas are registered on the route registry as components (`OpenAPIHono.openAPIRegistry.registerComponent('schemas', 'HdfResults', schema)` returns `{name, ref: {$ref}}`), the media-type schema is the resulting `{ $ref }` (or `{ oneOf: [refs] }` on ingest) — a non-Zod schema, which `@hono/zod-openapi` 1.6 skips in its validator (`if (!isZod(schema)) continue`) and passes through to the generator — and validation is an **ajv 2020** middleware registered before the route, against the same component (the engine the conformance tests use). No root carries a discriminating field, so the middleware dispatches with `hdf-engine`'s detector and validates one root while the document keeps `oneOf`. Nothing is hand-written here.
- **Producer parity is a defined projection, not naive equality.** The service emits OpenAPI 3.1 through `getOpenAPI31Document`; ADR-0011's contract test applies one tracked projection **P** to both that document and this package's `apiSpec`. P is defined by what `zod-to-openapi` 9 can never emit or emits differently: dereference every `$ref`; strip `description`, `title`, `summary`, `examples`, `example`, `$comment`, `deprecated`, `operationId`, `tags`, `readOnly`, `writeOnly`, `default`, `multipleOf`, `uniqueItems`, parameter `style`/`explode`/`allowReserved`/`allowEmptyValue`, and every `x-*` member; drop `additionalProperties` entirely and drop empty `required` arrays; treat an absent parameter `required` as `false`; sort object keys and the `required`/`enum` arrays; canonicalise `nullable: true` and `anyOf/oneOf: [X, {type: 'null'}]` to `type: [T, 'null']`, and `enum: [v]` to `const`; keep `format` only from the tracked allowlist `{uuid, date-time, date, email, uri}` (plus `binary` on the `Binary` component alone); replace each document-body media schema with its `$ref` string — and asserts `P(emitted) ≡ P(apiSpec)`. What P strips is guarded elsewhere: this generator **hard-fails** on any `format` outside the allowlist and on any non-document schema without `additionalProperties: false`, so strictness and formats are properties of the document, not of the comparison. A second, **un-projected** assertion covers what P must not hide: the route inventory (method + path), every parameter's `name`/`in`/`required`, each operation's response status set, and its `security` requirement; the two `documentOnly` token operations are expected in the document and absent from the emitted inventory. P ignores non-`paths` top-level keys (`getOpenAPI31Document` adds empty `components.parameters` and `webhooks`). **Measured (round-6 spike)**: on a sample document with the listed features, `P(emitted) ≡ P(sample)` held with zero residual and the inventory assertion held — the projection is the tracked one, not an aspiration. Service-only paths (`/healthz`, `/readyz`, `/.well-known/*`, and the rest of `/api/auth/*`, which is mounted outside the registry) are listed in the service's `extraPaths: [{path, reason}]` — a service-side list, distinct from this package's MCP-facing `absent`. If P proves brittle, the recorded fallback is Alternative K.
- **SDK**: `@mitre/hdf-client` (ADR-0011 owns the package, at the workspace root) is generated from this document by the same `@hey-api/openapi-ts` run (`zod` + `@hey-api/sdk { validator: true }` + the bundled `@hey-api/client-fetch` plugin — a plugin name, not a package), so the client validates responses against the same Zod the server used, and the service's contract tests call the service through it. One measured caveat: Hey API also emits Zod for the HDF roots, and that Zod is **lossy** (`unevaluatedProperties` and `if/then` are dropped) while the SDK's validator switch is all-or-nothing — so the client wraps every document operation to validate request bodies and response documents with `@mitre/hdf-validators` (ajv 2020), making the client exactly as strict as the server (ADR-0011 §4). The token endpoints are `documentOnly` synthetic operations in this document (§2) with a form-encoded body the generated client serialises as `application/x-www-form-urlencoded` and `security: []` so the client never bearer-authenticates a token request; the client's authentication call is therefore generated too, and types-only consumers of `openapi-typescript`/`openapi-fetch` see it as well.
- What this package ships stays a leaf: documents and the validation harness. The Zod output, the client, and the ajv boundary middleware live in ADR-0011's packages; this package gains only a test that `@hey-api/openapi-ts` consumes `dist/hdf-api.oas.json` without warnings (Phase 3), so the pipeline downstream is guaranteed an input.
- **A companion document this package does not generate.** Organization, team, member, OAuth-client, and API-key management are better-auth's endpoints, outside the MCP golden and therefore outside this document by construction. ADR-0011 §2 publishes them as a **second document**, `hdf-auth.oas.json`, produced by better-auth's `openAPI` plugin plus the service-owned auth routes, served at `/api/auth/reference`, and the client gains a second generated namespace from it. The two documents share the bearer scheme and the problem-details conventions; nothing from the auth document is merged here (Alternative L).

## Reviewer challenge points

Will's review — and any agent review he runs — should specifically challenge or verify: (a) **generating the API from the MCP contract** versus deferring it to an `hdf-serve` ADR (ADR-0003 precedent) — chosen because the typed source exists, at the cost of three prerequisite cards; (b) whether the **binding-table grammar** (closed key set, `bodyRef`/`fullResponse` by name only, mechanical no-fragment AC) keeps the table a mapping and not the API in disguise; (c) **HTTP as the canonical full shape**, inverting ADR-0007's token-budget framing; (d) the **opaque-uuid + ETag** identity model versus content-hash ids; (e) the `202`/jobs contract (`Location` + `Retry-After` + a job resource, no `303`) now that ADR-0013 is the producer; (f) one convention-owned `insufficient-scope` problem `type` for every scope failure (revision 4's `about:blank` + custom title was non-conforming) rather than extending the `mcperr` taxonomy; (g) **§7's derivation pipeline** — Zod generated from this document by `@hey-api/openapi-ts` rather than hand-written in Hono routes or derived from the JSON Schema bundles, with document bodies registered as raw components and validated by ajv; (h) **producer parity by the projection P plus the un-projected inventory/security assertion** as the drift gate, versus Alternative K (validate the running service against this document) or making the service the source; (i) the **synthetic-operation rule** (§2) — four operations here (ingest, delete, two `documentOnly` token operations) and ADR-0013's routes under the same rule, with shapes registered through the reflection hook and never inline; (j) the **HTTP conventions adopted from the standards pass** (§3): `RateLimit` headers, a declared `500`, hosted types for 413/415/429, RFC 9745/8594 deprecation signalling, no path versioning, sha256 as the idempotency key; (k) the **companion auth document** (§7) rather than one merged document.

## Alternatives Considered

### A. Hand-authored OpenAPI components
Pros: no generator. Cons: drift across ~129 definitions; violates the generation rule. Why rejected: drift is the failure the architecture prevents.

### B. Hand-authored reference API (revision-1 draft)
Pros: design freedom. Cons: the reviews showed the drafted path list was neither one-to-one with MCP nor a defensible CLI subset, and non-document response shapes became a second hand-maintained contract. Why rejected: contradicts generation; rots without a server.

### C. Defer the reference API to an `hdf-serve` ADR
Pros: ADR-0003 precedent. Cons: the typed MCP contract exists; generation is cheap once three small prerequisites land. Why rejected (narrowly) — challenge (a).

### D. Content-hash document ids
Pros: idempotent ingest. Cons: 412/409 lose meaning; cross-tenant existence oracle. Why rejected: opaque ids with sha256 as `ETag` give the integrity signal without the oracle — challenge (d).

### E. Ship inside `@mitre/hdf-schema`
Why rejected: dependency and release coupling on the ecosystem's most-consumed package.

### F. OpenAPI 3.0 with down-converted schemas
Why rejected: lossy (no `if`/`then`, `unevaluatedProperties`, type arrays).

### G. Components that `$ref` hosted schema URLs
Why rejected: network-dependent specs break air-gapped use, codegens, and CI determinism.

### H. Do nothing
Why rejected: no public issue asks for OpenAPI today (demand is anticipated by the `hdf-serve` direction), but generated artifacts cost near nothing to maintain.

### I. Zod-first — the Hono routes are the source and generate the API document
Pros: one artifact fewer; idiomatic `@hono/zod-openapi`. Cons: the typed operation source is the Go MCP contract, and Zod cannot express the document schemas, so the routes would hand-author every non-document shape and reference the bundles by hand; MCP↔HTTP parity would then be asserted against a hand-written thing. Why rejected: keeps generation-only and makes the service a checked implementer — challenge (g), (h).

### J. Derive Zod from the JSON Schema bundles
Pros: no OpenAPI in the loop. Cons: `z.fromJSONSchema` throws on 77 `unevaluatedProperties` and 7 `if` sites, returns untyped schemas, and the one maintained converter is archived; stripping those keywords first would make Zod accept what the schema rejects. Why rejected: measured, not assumed — challenge (g).

### K. Parity by validating the running service against this document
Pros: no projection to maintain; a request/response validator (`openapi-backend`/`express-openapi-validator`-class, or the ajv harness of Phase 1b) checks every contract-test exchange against this document directly, plus the same inventory/security diff. Cons: catches only exercised paths; does not prove the service's own emitted document is faithful. Disposition: **recorded fallback** if the projection P of §7 proves brittle in ADR-0011 Phase 1 — challenge (h).

### L. Fold organization and client management into this document as synthetic operations
Pros: one document, one client namespace. Cons: those operations are better-auth's, versioned with it, with no MCP derivation and no `fullShapes`; the synthetic section would grow from four hand-set operations to dozens. Why rejected: the companion document (§7) keeps this one MCP-derived and lets better-auth's own generator describe better-auth's routes.

## Consequences

Easier: API builders `$ref` HDF types; MCP and HTTP share one operation vocabulary by construction; a measured compatibility table; the service, its Zod, and its client are all downstream of one document, so a contract change is one regeneration.

Harder: schema bumps gain a regeneration step; the API document is a new public contract with its own semver; three prerequisite cards; the golden and binding table are tracked artifacts with a CI diff gate; the document now has a producer whose parity test can fail a service PR for a contract-only reason.

Risks and mitigations: tool lag → measured baseline; components drift → semantic conformance with negatives; API drifts from MCP → build fails on unbound tools/resources, parity compares names/enums/shapes after the fixed rewrite map, golden regenerate-and-diff in CI; hand-authoring creeps in → mechanical no-fragment AC; later `$defs` collision → build fails; partial local `dist/` → tracked-embed input + count guard. Semantic drift with unchanged names (`limit: 0 = all`, impact comparison grammar) is caught by ADR-0011's contract tests, which exercise the service through the generated client against real fixtures (§7).

## Implementation Plan

### Scope
IN: the package; components transform with guards; the extended golden and sync; API generator, binding grammar, conventions; lint/codegen matrices with tracked baseline; conformance, parity, example tests; site publication with archive; release/CI wiring; the three prerequisite cards.
OUT: any server (ADR-0011); the Zod output, the client SDK, and the ajv boundary middleware (ADR-0011, generated from this document); auth implementation and the authorization server (ADR-0011 §3); `202`/async; OpenAPI for non-HDF payloads.
Delivery: **two PRs** — PR A = Phases 1a, 1b, 4 (components + site); PR B = Phases 2–3 after the prerequisites land. All five ADRs (with the ADR-0012 overview) land together in the design PR first.

### Quality Standards (inherited by every card)
- Generation only; the binding table obeys its closed grammar (mechanical AC).
- OpenAPI 3.1, 2020-12 dialect; Redocly **and** Spectral zero errors; `operation-security-defined` and the 413/415 rule enforced.
- Codegen matrix diffs against a tracked baseline; diffs fail.
- Every example validates with a 2020-12 engine; examples from hdf-fixtures or schema `examples`, never fabricated; `hdf-comparison` gets a root example (owned here).
- Three-artifact rule; `publint` + `attw`; TDD, >90% coverage on generator/test code; zero lint warnings; repo gauntlet.
- No commercial downstream consumers referenced anywhere.
