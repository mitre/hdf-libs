## Context

Three surfaces read and write HDF documents, and each has its own I/O today:

- **The MCP server** (`hdf-cli/internal/mcp`, Go, ADR-0007) reads through exactly one function, `resolveSource(src handle.Source, ldr *loader.Loader, slot string)` (`tools/source.go:93`), which resolves `HDF_MCP_ROOT`-relative paths with `SafePath` and calls `os.ReadFile`; it writes through exactly one function, `writeArtifact` (`tools/writegate.go:48`, gated by `HDF_MCP_ENABLE_WRITES`, `O_EXCL` unless `overwrite`, `dryRun`). Every tool calls those two directly; the only injected dependency is a concrete `*loader.Loader` (`loader/loader.go:62`: a byte-bounded LRU keyed by content SHA-256 sized by `HDF_MCP_CACHE_BYTES`, `LoadByHash` for empty-path handles, and the validation-error degradation in `degradedErrors`). Handles are self-encoding (`{path, size, contentSha256, docType, engineSchemaVersion}`, `handle/handle.go:26`), deliberately not server-side keys. There is **no store or repository interface, no session state beyond a transcript, and no corpus concept** — related documents are always caller-supplied paths (`hdf amend apply`, `hdf diff`). The nine-tool surface is a tracked golden owned by ADR-0007.
- **The CLI** (Go) reads through `cmd/input.go` (`readInputFile`/`readInput`: path-or-stdin, BOM strip, size guard) — a separate path from the MCP seam.
- **`hdf-engine`** (TS + Go) is bytes-in, whole-typed-document thereafter: `Load(data []byte, maxSize)`, `Filter(ctx, results hdf.HDFResults, opts)`, the compliance functions take `hdf.HDFResults` by value; the single injected I/O seam is `evidence.FetchFunc`. The engine deliberately has "no cache, no I/O policy". Its functions **cannot run over rows**; they need a materialised document.
- **There is no HTTP server anywhere in the repo**; `net/http` appears only in fetcher clients.

ADR-0009 now gives those surfaces a relational + vector store with `importDocument`/`exportDocument`/`reprojectDocument`, deletion semantics, four exemplar queries, tenancy predicates, and an `embeddings` table that something must fill. ADR-0011 adds a TypeScript HTTP service. ADR-0008 fixes the wire identity (opaque `uuid` per ingest, `sha256` as `ETag`, tenant-scoped uniform `404`). ADR-0013 adds an audit ledger that every mutation must feed. Without a shared layer, the Go MCP, the Go CLI, and the TS service would each wire storage, tenancy, audit, and the exemplar queries independently — three implementations of "which prior adjudications apply to this finding", drifting.

Two facts from the round-6 spikes (run, not read) shape the Go side: a pgx pool whose `AfterConnect` registers pgvector types fails to connect **before the extension exists**, so the pool that runs migrations and the pool that serves queries are different objects; and a bound `model_id` parameter loses the partial HNSW index after five executions under a generic plan, so the similarity query inlines a validated literal (ADR-0009 §11). A third fact from the gap analysis: pipelines should not hold database credentials, so the CLI needs a way to reach a **hosted** store over HTTP.

Constraints inherited from the repo: dual-language with shared-fixture parity wherever Go is a consumer (ADR-0007); real fixtures only; canonical timestamps; no content in errors or logs (ADR-0009 canary); the release workflow stamps every workspace package with the repo tag (`release.yml`), so a `0.x` package needs the exclusion ADR-0009 Phase 6 introduces.

## Decision

### 1. Package, languages, boundary, pool ownership
Create **`@mitre/hdf-data`** (TypeScript) and **`github.com/mitre/hdf-libs/hdf-data/go`** (no `/v3` suffix while `0.x`, the ADR-0009 §1 rule; the package joins ADR-0009 Phase 6's tag-stamp exclusion and `next` dist-tag policy). Dependencies: `hdf-engine`, `hdf-validators`, `hdf-utilities`, and `hdf-db-schema` (ADR-0009) for the database backend; `hdf-fixtures` in tests. **`hdf-db-schema` is imported by this package only**: an ESLint `no-restricted-imports` guard in the **root** flat config (the `scripts/eslint-*-guard.mjs` pattern) and a `depguard` rule in **every Go module's** `.golangci.yml` (the nine that exist plus a new one for `hdf-engine/go`, listed in Phase 0) fail any other workspace package that imports it — the tables are an implementation detail of this layer. The MCP server, the CLI, and `hdf-serve` depend on `hdf-data`, never on `hdf-db-schema`.

**Database handles.** In TypeScript the consumer constructs the handle and passes it in (`createStore({backend: 'db', db})` takes a Drizzle instance), so a process that also runs better-auth (ADR-0011) shares one PGlite instance or one pool. In Go this package **owns the pool**: `hdfdata.Open(ctx, cfg)` builds a `pgxpool.Pool` whose `AfterConnect` registers the pgvector codecs and whose `MaxConns`/`MaxConnLifetimeJitter` are set from `cfg`; `hdfdata.OpenWithPool(pool)` accepts a caller-built pool and verifies at first use that the codecs are registered (`UNSUPPORTED_BACKEND` otherwise). **Migrations never run on that pool**: `hdfdata.Migrate(ctx, url)` opens a plain, codec-free connection, applies ADR-0009's embedded ledger, and closes it — measured: a codec-registering pool cannot connect until `CREATE EXTENSION vector` has run. Layering: above `hdf-engine`, beside `hdf-diff`; `hdf-utilities` gains no dependency. The TypeScript and Go surfaces are **mirrored by hand and proven by the shared-fixture parity suite** (§7) — no interface generator.

### 2. Principal and interfaces (identical shapes in both languages)
- **`Principal`** `{ organizationId: string | null, teamId: string | null, subject: string | null, scopes: Set<'hdf:read' | 'hdf:write' | 'hdf:admin'>, requestId: string | null }` is an **explicit argument to every call** — never ambient context, never a global, never derived from document content (ADR-0009 §8). A `null` organization means *unowned, never global* and is **constructible only by local callers** (CLI flags, stdio environment, tests) — ADR-0011 §3 never builds one from HTTP. Local principals carry all three scopes; the MCP's `HDF_MCP_ENABLE_WRITES=false` removes `hdf:write` from its principal, so the two write gates are one rule. A missing required scope is `FORBIDDEN_SCOPE` before any I/O. `requestId` is attached by `hdf-serve`'s request-id middleware (ADR-0011 §1) and is `null` for the CLI and the stdio MCP; it flows into the audit event of every mutation.
- **`DocumentStore`**: `put(bytes, {principal, importContext, retainBytes = true}) → {id, sha256, docType, created, retained}` — validates with `hdf-validators` first, is idempotent per `(organization, team)` on `sha256` through ADR-0009 §8's unique constraint (`created: false` returns the existing id, ADR-0008 §3; team scope is part of identity, so the same bytes may exist once per team and once organization-wide; the `sha256` is the idempotency key, no header), reports `retained` because retention is fixed at first import for that key (a later `retainBytes: true` on a non-retained row returns `created: false, retained: false`; changing it is `delete` + `put`), and takes the explicit import context ADR-0009 §3 requires; `get(id, principal, {form: 'original' | 'assembled' | 'any'}) → {bytes, meta, form}` (`form: 'original'` without retained bytes is `NOT_RETAINED`, never a silent fallback — ADR-0009 §6); `head(id, principal) → meta` (includes `validated_against`, `stale_schema`); `list(filter, principal) → {items, next}` with `filter ∈ {docType, systemKey, packageId, since, sha256, stale}` and an opaque keyset cursor over `(created_at, id)` (`BAD_CURSOR` on tampering); `delete(id, principal)` — requires `hdf:admin`, tenant-scoped, refused while ADR-0013's legal hold is set (`HELD`), runs ADR-0009 §5's `deleteDocument` transaction (owner cascade, reference RESTRICT → `DELETE_RESTRICTED` naming the citing document only within the caller's tenant); `reproject(id, principal)` (ADR-0009 §12, `hdf:admin`); `resolveRefs(id, principal)` (ADR-0009's `document_refs`, resolution already tenant-restricted at import). Ids on the `db` and `http` backends are **opaque** strings callers never parse; the Go file adapter's ids are the existing self-encoding handle (§3) and never reach HTTP.
- **Audit**: every mutating call (`put`, `delete`, `reproject`, `Indexer.rebuild`) writes one row through an injected **`AuditSink`** in the same transaction — the table, its schema, and its immutability are ADR-0013 §1's; this layer only guarantees that no mutation commits without its event (planted: a sink that throws rolls the mutation back).
- **Engine bridge**: `open(id, principal) → LoadResult` returns the whole typed document via `hdf-engine.Load`, memoised in the byte-bounded LRU keyed by `sha256` that today lives in the MCP loader (its size limit, `LoadByHash`, and validation-error degradation move here unchanged), so **every existing `hdf-engine` function runs unchanged** over stored documents. Nothing in this layer re-implements query/compliance/diff logic.
- **`AdjudicationQuery`**: the four ADR-0009 exemplars as typed calls — `carryForward(target, opts)`, `similarSystems(system, control, opts)`, `packageScope(packageId, query, opts)`, `similar(input: {vector} | {text}, opts)` — each taking `principal`. Their row types are **owned here**: `PrecedentRow` (target requirement id/baseline, prior override carrier/type/status/justification, `appliedAt`/`expiresAt`, `appliedBy`, origin document id, system-link method, `aliasOnly` flag), `SimilarSystemRow` (system key, method, shared baseline, overlapping component kinds, the precedent rows), `SimilarRow` (subject kind, subject document id and row id, model, distance) — TS types and Go structs with fixture parity. ADR-0008 prerequisite (b)'s registration hook lets the ADR-0007 amendment reflect them into the MCP golden, so MCP, HTTP, and CLI return identical rows. `opts` carries `asOf` (RFC 3339), `applyCompatible`, `limit`, `packageId`, `modelId`. Every row carries the ids needed to `open()` its source documents. Cross-document reporting queries for viewers (`findings`, `complianceSeries`) are **a follow-on ADR**, not this surface (Alternative D).

### 3. Backends, selection, environment
- **`file`** (Go only) — today's MCP behaviour, extracted: a root directory, `SafePath` resolution, the existing self-encoding handle as the id, the content-hash LRU, `put` writing with `O_EXCL` unless `overwrite`, `dryRun` preview. **Single-tenant by construction**: it accepts only a principal with `organizationId: null` unless constructed with `allowAnyPrincipal` (test aid). `AdjudicationQuery`, `delete`-by-id, `reproject`, and the indexer are **not implemented** on `file` (`UNSUPPORTED_BACKEND`, asserted); its audit sink is a no-op logger. There is no TypeScript file backend.
- **`db`** (both languages) — `hdf-db-schema` via Drizzle (TS) and `pgx` + `pgvector-go` (Go). Every call is **one transaction** that first sets `hdf.tenant_ctx = '1'`, `hdf.organization_id`, and `hdf.team_id` with `pg_catalog.set_config(…, true)` from the principal (an absent organization or team is passed as `''`), so ADR-0009's generated RLS applies whether or not the deployer enabled it; the application predicate `organization_id IS NOT DISTINCT FROM $1` (and the team predicate) is still applied in every query (defence in depth: the negative tests run with RLS off *and* on). Ids are the `documents.id` uuid. `put` is `importDocument` with the ownership argument; `get(form: 'original')` returns `source_bytes`; `get(form: 'assembled')` returns `exportDocument`'s assembled form. Behind a connection pooler in transaction mode the transaction-local `set_config` is the only tenant mechanism that works, and pgx's statement cache needs the pooler's prepared-statement support (or `QueryExecModeSimpleProtocol`) — documented, not configured here.
- **`http`** (Go only, v1) — the same interface over a **hosted** `hdf-serve`, so `hdf` and the stdio MCP can use a store without database credentials. The client is generated with `oapi-codegen` v2.8 from a **client projection** of ADR-0008's `dist/hdf-api.oas.json` (`scripts/project-go-client.mjs`, tracked output): the eight roots become `{x-go-type: json.RawMessage}` with nothing beneath them and every other HDF definition is excluded, so detection and validation stay in `hdf-validators` — necessary, not stylistic, because v2.8.0's 3.1 support fails on the multi-type unions the bundles contain (`type: ["string", "array"]` in two extension definitions; fixed upstream after 2.8.0, unreleased as of 2026-09-02). The generated code is tracked under `go/http/gen/` with a CI diff gate, the same discipline as ADR-0011's `src/contract/`; the recorded fallback if generation regresses is a hand-written `net/http` client for the dozen operations (not `ogen`, which has the same 3.1 exposure). Credentials: `HDF_CLIENT_ID` + `HDF_CLIENT_SECRET` (OAuth `client_credentials` with the required `resource`, the default) or `HDF_API_KEY` (the exchange endpoint); the token is cached until `exp − 60 s` and never logged. The `Principal` is whatever the token carries — the backend passes no tenant of its own, which is exactly why this backend is tenant-safe without pinned database roles. `AdjudicationQuery` over `http` works once ADR-0011 Phase 7's operations exist; before that those calls return `UNSUPPORTED_BACKEND`. Problems map back to `hdfdata.Code` through the §6 table's `type` column.
- **Environment contract** (shared by the CLI, the MCP, and `hdf-serve`; ADR-0011 appends its own rows):

| Variable | Default | Meaning |
|---|---|---|
| `HDF_STORE` | `file` (CLI, MCP); `hdf-serve` refuses `file` and `http` | `file` \| `db` \| `http` |
| `HDF_STORE_ROOT` | `HDF_MCP_ROOT`, else cwd | root directory of the `file` adapter (`HDF_MCP_ROOT` stays as the documented alias) |
| `HDF_DB_URL` | unset (required when `HDF_STORE=db`) | PGlite's own URLs `memory://`, `file://<dir>`, or `postgres://…` |
| `HDF_DB_SSL` | `require` for `postgres://` (`verify-full` in the container) | `require` \| `verify-full` \| `disable` (the container refuses `disable`) |
| `HDF_DB_MAX_CONNS` | `max(4, NumCPU)` | Go pool size |
| `HDF_API_URL`, `HDF_CLIENT_ID`, `HDF_CLIENT_SECRET` / `_FILE`, `HDF_API_KEY` / `_FILE` | unset (required when `HDF_STORE=http`) | hosted store and its credential |
| `HDF_ORG_ID`, `HDF_TEAM_ID` | unset (NULL principal) | local principal for stdio/CLI on `file`/`db`; see §5 for the multi-tenant rule |

### 4. Embedding provider and indexer
- **`EmbeddingProvider`** `{ name, dims, embed(texts: string[]) → Float32Array[] }`. **No provider is configured by default**; `similar({text})` and `Indexer.rebuild` return `PROVIDER_UNAVAILABLE` until one is. The **one built-in provider** speaks the de-facto standard `POST /v1/embeddings` request/response shape over HTTPS, so local open-source model servers and hosted ones alike work without the layer naming a vendor; the response is validated with a Zod schema (shape, count, `dims`) before use. Registration calls ADR-0009's `hdf_register_embedding_model()` once per `(name, dims)`; a response whose vector length differs from the registered `dims` is `DIMS_MISMATCH` before any write; the credential is never logged and is redacted from errors.
- **`Indexer.rebuild(id, principal)`** selects the subjects for a document by ADR-0009 §11's subject vocabulary and text fields, computes `text_sha256`, skips unchanged subjects, batches `embed()` calls (`HDF_EMBEDDINGS_BATCH`, rate-limit-aware retry), and writes the `embeddings` rows in one transaction per document (ADR-0009 §5 rebuild rule) with its audit event. It is **explicit, never implicit on `put`** — indexing sends document text to whatever endpoint is configured, and the package README says so in its first paragraph; ADR-0013's job runner is how a hosted deployment schedules it. `Indexer.buildIndex(modelId, {concurrently})` is the owner-run index path of ADR-0009 §11, exposed for `hdf db embed --index`. Subject text is never logged; the canary test covers the provider client. Scanner output embedded here is data, not instructions; what an agent does with a `similar()` row is ADR-0007's concern.
- `similar({text})` embeds the query with the same provider and model it was indexed with; `similar({vector})` accepts a caller-supplied vector for callers that embed elsewhere (`UNKNOWN_MODEL` if `modelId` is not registered).

### 5. Wiring the three consumers
- **MCP server** (Go): `resolveSource` and `writeArtifact` become calls on an injected `hdfdata.Store`; the `*loader.Loader` dependency is replaced by the engine bridge, which carries the loader's cache bound and degradation behaviour so the eval-harness golden and every tool test pass unchanged on the `file` adapter. `HDF_STORE=db` + `HDF_DB_URL`, or `HDF_STORE=http` + `HDF_API_URL` + a credential, selects the backend. The self-encoding handle gains an optional **`id`** field (empty `path`, backend-issued id, `contentSha256` kept for `HANDLE_STALE`), so existing handles stay valid and stored documents get one without a server-side registry (ADR-0007 §8 preserved). On `db`, the stdio server's principal comes from `HDF_ORG_ID`/`HDF_TEAM_ID` (or `null`), documented as ambient-credential per the MCP spec — and because that value is **self-asserted**, stdio against a **multi-tenant** database is supported only with a **pinned database role** (ADR-0009 §8's `hdf_tenant_roles` table and restrictive `hdf_role_pin` policy, owned and generated there); with a shared role it is documented as single-tenant. On `http` the tenant comes from the credential, which is the recommended shape for a multi-tenant deployment. **Exposing `AdjudicationQuery` as MCP tools** (`hdf_precedent`, `hdf_similar`) changes the nine-tool golden and is an **ADR-0007 amendment carded separately in two parts**: `--transport http` (ADR-0011 §6, no dependency here) and the precedent tools (after Phase 3 here; registers the §2 row types through ADR-0008 prerequisite (b)'s hook and adds the `bindings.yaml` entries so ADR-0008 regenerates). This ADR ships the queries; the amendment ships the tools.
- **CLI** (Go): `hdf db migrate | import | export | list | get | delete | reproject | precedent | similar | embed [--index [--concurrently]] | audit | jobs` (the last two read ADR-0013's `audit_events` and `jobs_meta` through this layer; `pgboss`'s own tables are never read by the CLI) — thin subcommands over the same store, with `--org`/`--team` flags feeding the principal (all scopes) on `file`/`db`, and the credential-derived principal on `http`; `hdf db migrate` applies ADR-0009's embedded migrations with the Go applier on the codec-free connection (ledger parity).
- **`hdf-serve`** (TS, ADR-0011): every route calls `hdf-data` and nothing else for storage; the guard in §1 makes a direct `hdf-db-schema` import in the service a lint failure; the service constructs the database handle (§1) and refuses `HDF_STORE=file` and `http`.

### 6. Errors — the one table
`hdfdata.Code` is closed and **this table is the single mapping** ADR-0008's conventions and the MCP consume (a test in `hdf-openapi` and one here assert agreement):

| Code | Raised by | HTTP status | RFC 9457 `type` | `mcperr` |
|---|---|---|---|---|
| `DOCUMENT_NOT_FOUND` | get/head/delete/open | 404 | `…/problems/document-not-found` | same |
| `HANDLE_STALE` | open with a stale `sha256` | 412 | `…/problems/handle-stale` | same |
| `TOO_LARGE` | put; evidence `put` over `HDF_BLOB_MAX_BYTES` | 413 | `…/problems/payload-too-large` | same |
| `SCHEMA_INVALID` | put | 422 (+ `errors[]`) | `…/problems/schema-invalid` | same |
| `WRONG_DOC_TYPE` | queries on the wrong type | 422 | `…/problems/wrong-doc-type` | same |
| `NO_CONVERTER`, `AMBIGUOUS_FORMAT` | not raised here (MCP convert) | 422 | `…/problems/<kebab-code>` | same |
| `CACHE_MISS` | `file` adapter only | never | — | same |
| `OUTPUT_EXISTS`, `PATH_DENIED`, `WRITE_FAILED` | `file` adapter only (`PATH_DENIED` reports the relative path only) | never | — | same |
| `TRUNCATED` | never (dead in MCP too) | never | — | same |
| `UNSUPPORTED_DOC_TYPE` | put on a non-core type (ADR-0009 §2) | 422 | `…/problems/unsupported-doc-type` | new |
| `UNSUPPORTED_BACKEND` | queries/indexer/delete on `file`; queries on `http` before Phase 7 | never (internal) | — | new |
| `FORBIDDEN_SCOPE` | any call | 403 | `…/problems/insufficient-scope` (ADR-0008 §3) | new |
| `NO_ACTIVE_ORGANIZATION` | raised by ADR-0011 before the store | 403 | `…/problems/no-active-organization` (ADR-0008 §3; no `WWW-Authenticate`) | new |
| `NOT_RETAINED` | `get(form: 'original')` or `reproject` without bytes | 409 | `…/problems/not-retained` | new |
| `DELETE_RESTRICTED` | delete of a cited document | 409 | `…/problems/delete-restricted` | new |
| `HELD` | delete under a legal hold (ADR-0013) | 409 | `…/problems/held` | new |
| `BLOB_NOT_FOUND` | evidence `get`/`head` (ADR-0013 §4) | 404 | `…/problems/blob-not-found` | new |
| `QUOTA_EXCEEDED` | put over an organization quota (ADR-0013) | 429 | `…/problems/quota-exceeded` | new |
| `BAD_CURSOR` | list | 400 | `…/problems/bad-cursor` | new |
| `UNKNOWN_MODEL`, `DIMS_MISMATCH` | similar / indexer | 422 | `…/problems/<kebab-code>` | new |
| `PROVIDER_UNAVAILABLE` | similar({text}) / indexer | 503 | `…/problems/provider-unavailable` | new |
| `STORE_UNAVAILABLE` | database or hosted store unreachable | 503 (`Retry-After`) | `…/problems/store-unavailable` | new |

The `type` column is the site-hosted URI prefix plus the kebab-cased code; ADR-0008's conventions read this table, and the `http` backend maps a problem's `type` back to its code. Messages carry no document content, no absolute paths, and no driver `DETAIL`/`HINT`.

### 7. Parity and tests
Both languages on the `db` backend with shared fixtures (`hdf-fixtures` and ADR-0009's Phase 0 corpus): every `DocumentStore` operation and every exemplar produces byte-identical canonical results across TS and Go. The Go `file` adapter is proven against the pre-refactor MCP: the eval-harness golden and every tool test unchanged. The Go `http` backend is proven against a running `hdf-serve` in the ubuntu job (the same fixtures, the same rows as `db`). Go database tests use one container per package in `TestMain` with `Snapshot`/`Restore` per test (ADR-0009 §9). Planted failures: a store call without a `principal` (compile error in Go; a type error in TS, plus an ESLint rule that flags any store method call whose first argument is not a `Principal`-typed expression, `scripts/eslint-principal-guard.mjs`), a tenant leak through `list` and through `similar`, a direct `hdf-db-schema` import outside this package, a partial child `DELETE`, a mutation whose audit sink throws (must roll back), a provider response with the wrong `dims`, subject text appearing in a log, and the **bound-parameter regression** (a variant of the similarity query with a bound `model_id` is shown to stop using the index by its sixth execution, by `idx_scan` count).

## Reviewer challenge points

Will's review — and any agent review he runs — should specifically challenge or verify: (a) **a Go-only `file` adapter behind the same interface** with `AdjudicationQuery`, indexing, and `delete` database-only — is `file` worth keeping in the interface at all, or should the MCP simply require the database; (b) **explicit `principal` on every call** versus a context-carried principal (Go `context.Context` values, TS `AsyncLocalStorage`) — chosen for testability and grep-ability at the cost of verbosity; (c) the **MCP handle `id` field** and splitting the ADR-0007 amendment into transport and precedent tools; (d) the **`/v1/embeddings`-shaped built-in provider** as the only one, with no default model and explicit (never implicit) indexing; (e) **backend-issued ids** (opaque uuid on `db`/`http`; the self-encoding handle on `file`, never on HTTP); (f) the **package boundary** (only `hdf-data` imports `hdf-db-schema`) enforced by lint in both languages, and Go pool ownership inside this package versus the TypeScript consumer-constructed handle; (g) whether this layer belongs **inside `hdf-engine`** (Alternative A); (h) **`delete` in v1** under ADR-0009 §5's cascade/RESTRICT semantics, requiring `hdf:admin`; (i) **local principals with all scopes** and the pinned database role as the multi-tenant stdio story for `db`, versus `http` as the recommended multi-tenant shape; (j) the **row types owned here** flowing into the MCP golden through a registration hook rather than living in `hdf-cli`; (k) the **`http` backend in v1** (Go only, oapi-codegen 2.8 on a 3.1 document with `json.RawMessage` bodies) versus deferring it; (l) the **audit sink** as a per-mutation transactional obligation of this layer with the table owned by ADR-0013.

## Alternatives Considered

### A. Fold the store into `hdf-engine`
Pros: one fewer package. Cons: the engine's documented contract is "no cache, no I/O policy"; tenancy, transactions, providers, and backends are all policy; every engine consumer would inherit the database dependency. Why rejected: the engine stays pure and runs unchanged over `open()` — challenge (g).

### B. Fold the store into `hdf-db-schema`
Pros: import/export already lives there. Cons: the `file` adapter, the engine bridge, the MCP handle logic, and the provider have nothing to do with the schema; every consumer would import the tables and the boundary in §1 would be unenforceable. Why rejected: ADR-0009 stays a schema package with a narrow API.

### C. A repository per document type
Pros: type-specific ergonomics. Cons: eight repositories in two languages; the exemplar queries cross types; the surfaces want documents, not types. Why rejected: one store with `docType` in metadata and the engine's typed `LoadResult`.

### D. A general cross-document query surface now (GraphQL, a filter language, or viewer-shaped `findings`/`complianceSeries` calls)
Pros: a viewer could render "control X across systems" in one call. Cons: a second public contract beside ADR-0008; tenancy and scope enforcement would move into resolvers; the row shapes depend on ADR-0009 Phases 2–5 existing. Why rejected for v1: the exemplars are the query surface; the viewer queries are a **follow-on ADR** with a demand behind it, sized at about sp13 by the gap analysis.

### E. Each surface wires storage directly
Pros: no new package. Cons: three implementations of tenancy, identity, audit, and the exemplars; the service and the MCP would return different rows for the same question. Why rejected: it is the drift this layer exists to prevent.

### F. Implicit indexing on `put`
Pros: embeddings always fresh. Cons: silently sends document text to an external endpoint on every import; couples import latency to a model server. Why rejected: explicit `embed`/`rebuild`, scheduled by ADR-0013's runner where needed — challenge (d).

### G. A TypeScript file backend and a generated interface description (revision 1)
Pros: symmetric backends; one machine-checked interface. Cons: no TypeScript consumer reads a directory; the description was a third artefact for ~15 methods that the fixture parity suite already polices. Why rejected in revision 2: cut on review.

### H. No deletion in v1
Pros: nothing to cascade. Cons: an assessment store that cannot remove a mis-imported or expired document is unusable in practice. Why rejected: ADR-0009 §5 now defines the semantics — challenge (h).

### I. No `http` backend; pipelines hold database credentials
Pros: one fewer backend and no generated Go client. Cons: every pipeline runner gets a database credential and needs a pinned database role to be tenant-safe; the CLI cannot use a hosted store at all. Why rejected: the generated client costs sp13 once and removes database credentials from every pipeline — challenge (k).

## Consequences

Easier: the MCP server gains a database mode and cross-document queries by swapping one dependency; `hdf db` is thin; `hdf-serve` never touches tables; the exemplar rows are identical on every surface; tenancy is set in one place per language; deletion is safe by construction; every mutation is audited by construction; pipelines reach a hosted store without database credentials.

Harder: a new dual-language package with its own parity suite plus a Go `http` backend proven against a running service; the MCP refactor touches every tool (mechanically, through two functions); the handle format gains a field; the precedent tools wait on an ADR-0007 amendment; explicit principals make every signature longer; the provider is one more configuration surface to document; multi-tenant stdio on `db` needs pinned database roles.

Risks and mitigations: the interface leaks backend details → unsupported operations are explicit codes, not silent no-ops; principal forgotten at a call site → compile-time in Go, type-level plus the ESLint guard in TS; text exfiltration via the provider → off by default, HTTPS by default, host allowlist, explicit rebuild, documented, canary-tested; SSRF through `HDF_EMBEDDINGS_URL` → deployer-controlled, HTTPS-only by default, host allowlist, response cap and timeout; MCP behaviour changes under refactor → the eval-harness golden and every tool test run unchanged against the `file` adapter before the `db` backend is added; self-asserted stdio tenant → pinned database roles or `http`; codec registration before the extension → separate migration connection (measured); bound-parameter plan regression → literal model id plus the `idx_scan` regression test; oapi-codegen 3.1 gaps → document bodies as `json.RawMessage`, unions resolved by `hdf-validators`, the generated client diff-gated; Windows → the Go `file` adapter and engine bridge run everywhere, Go `db`/`http` tests follow ADR-0009 §9 (ubuntu, counted skip on windows).

## Implementation Plan

### Scope
IN: the TS package and Go module; `Principal`, `DocumentStore` (incl. `delete`, `reproject`), the audit-sink obligation, engine bridge, `AdjudicationQuery` with its row types, `EmbeddingProvider` + built-in HTTPS provider with response validation, `Indexer` incl. the owner-run index path; the Go `file` adapter, the `db` backend in both languages, the Go `http` backend; Go pool ownership and the codec-free migration connection; the environment table; the error table; the boundary and principal guards; MCP wiring (two functions + handle `id`, loader behaviour carried); `hdf db` subcommands; parity suite; docs with executed examples.
OUT: the tables and migrations (ADR-0009); the HTTP service and auth (ADR-0011); the audit table, jobs, quotas, holds (ADR-0013 — this layer only calls them); new MCP tools and HTTP transport (ADR-0007 amendment, two cards); any embedding model; viewer-shaped cross-document queries (follow-on ADR); a TypeScript file or http backend; caching beyond the content LRU.
Delivery: **one epic**, two PRs — PR A = Phases 0–1 (interfaces, Go `file` adapter, MCP refactor with unchanged behaviour); PR B = Phases 2–7 (database backend onward), sequenced behind ADR-0009's and ADR-0011's phases as listed. The ADR-0012 overview lands with the design PR.

### Verification Strategy
The parity suite (both languages × shared fixtures on `db`; Go `file` adapter against the MCP golden; Go `http` against a running service) is the spine; each phase closes only when its operations agree across languages, its negatives pass, its mutations audit, and the MCP golden is unchanged. Live test before close: run the MCP server against the database with a real fixture imported through `hdf db import`, call `hdf_query` and the carry-forward exemplar through the CLI, delete the document and show the cascade and the audit row, then repeat the read path through `HDF_STORE=http` — and paste the outputs in the card notes.
