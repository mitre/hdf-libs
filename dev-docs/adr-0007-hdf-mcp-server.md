## Context

Agents are becoming a primary consumer of assessment data, and HDF is currently unusable to them. The governing constraint is size: real HDF results documents in this repo run **2–5 MB** (`hdf-fixtures/inspec/wrapper.json` is 5.0 MB; the `nessus-to-hdf` expected output is 1.0 MB), roughly 500k–1.5M tokens. No agent can read one. Today an agent's only options are to shell out to `hdf` and parse prose, or to load a document and immediately exhaust its context.

The forces at play:

- **Documents are far larger than any context window.** Any useful design must put a filtering and aggregating layer between the agent and the document. The agent must never see raw HDF at document scale. This constraint governs every other decision here, and it applies to *anything* the server hands back — including schemas (see §9, where the first draft of this ADR violated its own premise).
- **HDF is an eight-document ecosystem, not one file format.** `hdf-results`, `hdf-baseline`, `hdf-system`, `hdf-plan`, `hdf-amendments`, `hdf-evidence-package`, `hdf-comparison`, and `hdf-requirement-change-event` (added in v3.5.0 per ADR-0005 — the conmon change-event stream, NDJSON-carried and validated by `hdf-validators`). Real questions cross documents ("which plan baselines have no results?"), so a results-only surface answers a minority of them.
- **Models do not know HDF's schema and will confabulate it.** Not speculative: the authors of `awslabs/mcp-server-for-oscal` state they built it because "most AI agents/LLMs alone produced inconsistent results related to OSCAL." HDF is smaller, younger, and less published than OSCAL — the confabulation risk is strictly worse.
- **We already document thirteen real user workflows.** `site/docs/guides/cli-user-story-examples.md` frames each as a **Story** ("A CI pipeline enforces compliance regression detection"). Those are the validated use cases; the agent-facing surface should serve them rather than re-expose CLI flags.
- **The consumer is a non-interactive agent invoked from a pipeline.** Not a human at a keyboard. That removes the human-approval guardrail MCP clients normally provide, and makes determinism, timeouts, and machine-readable errors load-bearing. It does **not** mean the server replaces deterministic pipeline steps — see §12.
- **The MCP specification is mid-transition.** The 2026-07-28 revision — a release candidate at the time of writing, not yet ratified, though nothing at issue in it affects this ADR — removes protocol sessions and the initialize handshake in favour of stateless requests and explicit handles passed as ordinary tool arguments (SEP-2567, SEP-2575); deprecates Roots, Sampling, and Logging (SEP-2577); and adds `ttlMs` / `cacheScope` list caching (SEP-2549). Deprecated features are guaranteed ≥12 months (SEP-2596), and the current ratified revision, `2025-11-25` — which most deployed clients speak today — remains supported. Resources remain healthy; prompts are current and actively developed. (MCP labels revisions by finalization date; the rest of this document refers to the 2026-07-28 revision in the present tense.)
- **HDF documents carry sensitive operational content.** `code`, `message`, and `codeDesc` routinely contain raw command output: hostnames, internal addresses, configuration fragments. This server's function is to stream selections of that to a model API.
- **Most of the engine already exists — but not all in the same place.** `hdf-validators/go` exposes `Validate(data, SchemaType)`, per-type validators for all eight document types, and `SchemaBytes(schemaType)`, and is import-clean. Worst-wins roll-up, effective-status, and severity math are now exported from `hdf-utilities/go/status.go` (`WorstStatus`, `GoverningOverrideIndex`, `ComputeEffectiveStatus`, `ImpactToSeverity`) since #193 unified them — the MCP imports these directly. The remainder this server needs — document type detection, the query engine, compliance *counting*, path confinement, the converter registry — still lives unexported in `package cmd` alongside cobra and console output, and is extracted into the new dual-language `hdf-engine` library (with path confinement going to `hdf-utilities` and the registry to `hdf-converters`). See the extraction manifest in Consequences.
- **Repo invariants:** TS↔Go parity for schema types/parsers/converters, real fixtures only, canonical trimmed-UTC RFC3339 timestamps, no fabricated fixture data, >90% coverage.

No prior art exists in the MITRE SAF ecosystem — there is no MCP server for SAF CLI, Heimdall, InSpec, or OHDF. This would be first.

## Decision

**Ship a single Go MCP server, exposed as `hdf mcp`, whose tools are shaped by the thirteen documented user stories rather than by the CLI's command surface — and which never lets the model author HDF JSON directly.**

1. **Workflow-shaped tools, derived from the documented user stories.** The surface maps to `cli-user-story-examples.md` §1–13, consolidated into nine tools (contract below). It is explicitly *not* a 1:1 mirror of `hdf` subcommands, and explicitly *not* a per-document-type family of query/list pairs.

2. **The model supplies prose and selection; the server supplies structure and validation.** The agent never emits HDF JSON. It chooses *which* requirements are affected and writes the *justification text*; a tool builds the schema-valid envelope and validates it before returning. This is the most important clause in this ADR. It is given force by an explicit **field-authority manifest** — a principle without a manifest is decoration:

   | Field | Authority | Rationale |
   |---|---|---|
   | Requirement selection (which controls) | **Model** | Genuine judgment over assessment content |
   | `reason` / justification prose | **Model** | Genuine judgment; the thing a model is actually good at |
   | Override `type` (`waiver` / `falsePositive` / `riskAdjustment` / …) | **Caller**, with a model *recommendation* field | Governance-bearing: per ADR-0002's two-axis model this decides whether a finding is suppressed or stays actionable. Not prose. |
   | `expiresAt`, human `appliedBy` | **Caller** | Policy and accountability, not inference. As of v3.5.0 (#195) `expiresAt` is **schema-required on every override**, so the caller must supply it — including on the `from_vex` path; the model never infers an expiry, and the server does not fabricate a default (that would be policy invented by code). A `create` call without it is rejected by the write-tool validation of §13 rather than emitting an open-ended override. |
   | document envelope, `$schema`, ids | **Server** | Deterministic |
   | `appliedAt` | **Server** | A real *when-applied* accountability timestamp, stamped in canonical trimmed-UTC form. It reflects the actual application instant, so it is deliberately **not** reproducible: two identical judgment-path authoring calls fold a different `appliedAt` into the document, and thus a different `sha256`/handle. This is the one intentional exception to output determinism (§12). |
   | `appliedBy.type` | **Server: `"agent"` for the judgment path, `"system"` for `from_vex`** | A deterministic VEX mapping is `system` per the `Identity.type` enum (CI/cron/scanners); only model-judgment authoring is `agent`. Keeps the agent-override count honest — see §3, §4 |

3. **Authoring writes by default; `dry_run` is the opt-in preview; amendments are additive by construction.** The base case is that the human wants the agent to do the work, so write tools *write* by default and take a `dry_run` flag to preview instead — the inverse of a review-first default, and the right base case for a pipeline consumer (§12). This is safe to default-on because of how HDF models overrides:

   - **Creating an amendment is additive; applying one never overwrites — but additivity buys forensics, not safety.** Overrides live in `hdf-amendments`, a *separate document type*; `hdf_author` (with `docType: amendments`) emits a new document and never touches the results file, and `hdf_apply_amendment` computes derived `effective*` state into a **new** results file, never overwriting its input. What that guarantees is that the *original evidence survives intact for comparison* and the decision is captured as a separate, attributed, revocable artifact — good document-model hygiene. What it does **not** guarantee is safety: the applied file is *new evidence*, and it lands in the same `HDF_MCP_ROOT` tree a pipeline harvests — user story §11 assembles evidence by glob (`evidence build --results "…/*.json"`), so an agent-applied result set with laundered `effectiveStatus` can be swept in automatically. Additivity makes an agent-authored verdict *auditable*, not *prevented*; that residual risk is what the detective and deployer-side controls below address.
   - **The server provides no *preventive* control — and in the autonomous-pipeline base case there is no *in-job* preventive control at all.** `dry_run` and the `HDF_MCP_ENABLE_WRITES` gate are a caller-preview convenience and a deployer ceiling (§12), not authorization. The usual deployer-side controls only partly cover this threat: branch protection and review requirements gate a *git merge*, and signing runs *after* production (it certifies whatever the agent produced) — neither stops a result set that is created, applied, and consumed by a `validate threshold` gate **inside a single CI job**. The one deployer control that does bite is a job token without write access to the evidence store — which is the `HDF_MCP_ENABLE_WRITES`-unset / Alternative-F case, the exception rather than the base case. So for an autonomous pipeline the honest position is: the in-job safeguard is **entirely detective plus out-of-band audit**; a *preventive* stance means either withholding write access (Alternative F) or reviewing before apply (preview-first). v1 deliberately accepts the detective-only posture — see Open Q1 — rather than treating it as an oversight. (An earlier draft proposed a CLI `--accept-machine-drafted` flag; dropped, because any actor that can invoke `hdf amend` can pass it, so it gates nothing.)
   - **The enforceable controls are detective, they travel in the data, and they survive application.** Judgment-authored overrides carry `appliedBy.type = "agent"`; deterministic `from_vex` overrides carry `"system"` (§2, §4) — the `Identity.type` distinction auditors rely on, and keeping `from_vex` out of the agent count is what keeps that count meaningful. Crucially, the attribution **survives the apply step**: `Evaluated_Requirement` in `hdf-results` retains `statusOverrides[]` (each with `appliedBy`) alongside `effectiveStatus`/`disposition`, so `hdf_compliance`, `hdf validate threshold`, and `hdf_validate` count agent-attributed overrides **on the applied results file itself**, without back-tracing to the amendments document — *"this package carries 12 agent-attributed waivers moving compliance 71% → 84%."* `hdf_apply_amendment` reports the before/after delta against its specific target; and because one amendment applies to many result sets (create-once / apply-many), a single bad agent judgment fans out across every target — the count and delta are how that fan-out is caught. **Because default-write makes autonomous authoring the base case, these surfaces are the primary safeguard and must ship and be eval-tested before the authoring tools do** (see Phases).
   - **The one deployment where the read/write split is preventive.** If this server is the agent's *entire* capability surface — a sandbox with no shell and no other tools — then a deployer who leaves `HDF_MCP_ENABLE_WRITES` unset genuinely prevents the agent from writing (the least-privilege principle). v1 does not assume that deployment, and does not claim its guarantees for the pipeline case.

4. **Deterministic transformations are code, not model output.** Applying a VEX document as amendments is a mechanical mapping from VEX status onto `Override_Type`. It belongs in a deterministic code path, not in model-authored JSON: `hdf_author` (with `docType: amendments`) produces an amendments document either from model judgment (selection + prose) *or*, when given a `from_vex` source, deterministically from the VEX document with no model prose (and stamped `appliedBy.type: "system"`, not `"agent"` — §2 — since no agent judgment is involved) — and either output flows into `hdf_apply_amendment`. The underlying VEX→`Override_Type` mapping is implemented as `hdf amend --from-vex` in the CLI, which the server exposes. Only genuinely judgment-bearing content comes from the model.

5. **Library calls, never CLI shell-out.** The server depends on the `hdf-*` packages directly. It must not exec the `hdf` binary or scrape its stdout. (`containers/kubernetes-mcp-server` treats "not a kubectl wrapper" as its defining quality.)

6. **The MCP *application* is Go-only; the *engine library* it stands on is dual TS+Go.** ADR-0001 §9 binds schema types, parsers, and converters to dual TS/Go implementation, and that parity **extends to the new `hdf-engine` library** (detect/query/compliance) — landed TS+Go together per engine, as `hdf-diff` already is. What stays Go-only is the *application layer*: `hdf-cli` and the `hdf mcp` server (`internal/mcp`) are Go artifacts built on those dual-language libraries — a TypeScript MCP port would duplicate the adapter, not the engines. So "extract the engine, then write a thin Go adapter" replaces the earlier framing of "the engines exist only in Go": the engines become dual-language in `hdf-engine`; only the server wrapper is Go-only.

7. **`hdf mcp` subcommand; implementation in `hdf-cli/internal/mcp/`.** One artifact for CI to install, and `goreleaser` distribution is already solved. The package depends on the shared `hdf-*` libraries — `hdf-engine` (detect/query/compliance), `hdf-diff`, `hdf-validators`, the `hdf-converters` registry — and **must not import cobra command internals** — enforced by an import test — so it can be lifted to its own module later without a rewrite. Because the engines live in `hdf-engine` rather than `hdf-cli/internal/*`, both the CLI and the MCP are thin adapters over the same library, not two callers of CLI-private code. (Prior art is mostly separate repos, but each is a vendor shipping a server for a hosted product they don't otherwise ship a CLI for; Codex's `codex mcp-server` is the applicable precedent.)

8. **Self-encoding handles, and `source` accepts a path *or* a handle.** Every document-taking tool accepts `source: {path: string} | {handle: string}`. A handle is base64 of `{path, size, contentSha256, docType, schemaVersion}` — **self-describing**. When it carries a non-empty `path` it survives process death (essential, since in CI the server is typically a short-lived child process), serializes into pipeline state, and doubles as a staleness check — a content-hash mismatch returns `HANDLE_STALE` rather than silently re-reading changed content, which would violate §10's determinism guarantee.

   **Content-addressed resolution for unwritten documents (option a; SEP-2567).** A tool that produces a document but writes no file — the default posture, since `HDF_MCP_ENABLE_WRITES` is off unless a deployer opts in, and also under `dry_run` — mints a handle with an **empty `path`** and registers the produced bytes in the byte-bounded document cache (below), keyed by `contentSha256`. Such a handle resolves from that in-memory cache, so the advertised `hdf_author → hdf_apply_amendment → hdf_compliance` composition works with **zero disk writes**; persistence stays gated on `HDF_MCP_ENABLE_WRITES`, composition does not. This is the MCP 2026-07-28 SEP-2567 pattern: server-minted handles carry cross-call state as ordinary tool arguments while the protocol itself stays stateless. It is a deliberate, **bounded-lifetime** exception to "handles are pure path references": a cache-backed handle resolves only until its entry is LRU-evicted, after which resolution returns the `CACHE_MISS` taxonomy code (`"the authored document expired from the in-memory cache — re-author it, or set output to persist it to disk"`) — never `PATH_DENIED`/`DOCUMENT_NOT_FOUND`. Content is re-verified against `contentSha256` on every cache resolve, so a handle never resolves stale bytes. (This also dissolves the empty-path `PATH_DENIED` misdiagnosis that the earlier "path reference only" design produced for unwritten documents.)

   `hdf_open` is therefore **optional, not a mandatory first hop**: a one-shot call passes a path and costs one round trip; a multi-question session calls `hdf_open` once to amortize detection, validation, and the headline summary. The in-process document cache serves two roles — a parsed-document optimization (repeated reads skip re-parsing) and the content-addressed store that backs empty-path handle resolution above — and is bounded in **bytes** (`HDF_MCP_CACHE_BYTES`, default 256 MB) rather than document count, since a parsed 5 MB HDF document is a large multiple of its file size on the Go heap; entries also retain the raw bytes so a cache-backed handle resolves to its exact content.

9. **Schemas are served as slices; catalogs and enums as whole resources.** The bundled schemas measure 102 KB (`hdf-amendments`) to 240 KB (`hdf-comparison`), with `hdf-results` at 200 KB — roughly 50–60k tokens each. (These figures were measured pre-v3.5.0; that release moved the schemas to v3.5.0 and added fields — `externalReferences`, `effectiveChecksum`, and the whole `hdf-requirement-change-event` type — so the slices are now larger and are re-measured against real fixtures before acceptance per Verification. The slicing decision holds regardless; the numbers only got worse for whole-schema serving.) `{doc-type}` ranges over all eight types, including `hdf-requirement-change-event`. Serving one whole would violate this ADR's founding constraint. Therefore:
   - `hdf://schema/{doc-type}/{def}` — a single `$defs` type (e.g. `.../hdf-amendments/Override`). The expected agent path.
   - `hdf://schema/{doc-type}/{def}?view=examples` — only the `examples` array. Per this repo's schema-examples convention every `$def` carries realistic examples with a `$comment`; for an agent these are higher-value than the constraint text and much cheaper.
   - `hdf://schema/{doc-type}` — the whole schema, retained for tooling, documented as expensive.
   - `hdf://catalog/converters`, `hdf://enum/{name}` — whole; both are small.

   We do **not** use MCP prompts in v1 — **not because they are deprecated** (they are current and actively developed, having gained `ttlMs`/`cacheScope` caching and multi-round-trip `InputRequiredResult` support in this revision) but because they fit neither this consumer nor these workflows. Prompts are **user-controlled** by the spec's own definition: server-provided conversation starters a *user* explicitly selects, canonically as slash commands. v1's consumer is a non-interactive pipeline agent — there is no user to select one. And a prompt cannot carry a procedure: its arguments are untyped strings (tools get full JSON Schema), its messages are `user`/`assistant` only (no system role), and it cannot name or sequence the tools a workflow needs. Our generative workflows (draft attestations, apply VEX) are procedures, so guidance ships as a **Skill** — the mechanism this repo already uses (`build-converter`, `release`). Sampling is separately unused (deprecated, SEP-2577). The prompts decision is scoped to v1; see Open Questions on revisiting discovery-oriented prompts if an interactive analyst becomes a primary consumer, since zero-install discoverability is the one affordance a Skill lacks.

10. **Every response is token-bounded, budgets are measured in tokens, and truncation states its remedy.** Caps are enforced on **serialized size**, not row count — one HDF requirement can carry multi-KB `descriptions[]` and `code`, so "50 rows" is not a budget. `verbosity: concise | full` (named to avoid collision with the CLI's `--detail <section>`, which selects *which* section rather than how much): `concise` ≤ 2k tokens, `full` ≤ 10k. Rows are dropped to fit the budget. A truncated response must state what was dropped and name the narrowing parameter to use next. Silent truncation is a defect. `tools/list` carries `ttlMs` and `cacheScope: "public"` (SEP-2549) — the tool list is fully static.

11. **Encoding, and where tokens are actually spent.** Tokens are consumed at exactly one boundary: when text enters the model's context. On-disk format, parsing, and canonicalization are all *server-side* of that boundary and cost **zero** tokens — the model never tokenizes a document at rest; it tokenizes what a tool **returns**. Every choice below follows from that.
    - **Tool arguments — JSON only.** Mandated by JSON-RPC 2.0. Not a design choice.
    - **Tool responses — `encoding: json | toon`, defaulting to `json`.** The response is the only surface that costs tokens, so it is the only place token efficiency is available. TOON's strength is uniform arrays of objects (a claimed 30–60% fewer tokens), which was expected to be the shape of an `hdf_query` concise result, an `hdf_compliance` rollup, and an `hdf_diff` summary. The eval harness's measurement rule was: below ~20% on `hdf_query`, drop it. **UPDATE (2026-08-14, bead hdf-libs-4908.14 — TOON deferred by measurement.)** The real-tokenizer delta on actual HDF fixtures came in far below the assumption, because HDF rows are not uniform enough to tabularize (optional fields force per-row keys) and TOON's structural overhead loses on nested/object/small-array shapes: concise `hdf_query` **+17.3%** (below the ~20% bar), full `hdf_query` **−3.4%**, `hdf_diff` changes **−18.6%**, `hdf_compliance` rollup **−24.5%** (its groups array **−37.9%**) — i.e. TOON makes the diff and compliance responses *larger*. By this section's own rule, TOON is not wired into any tool. The `toon-go` codec and the delta eval (`TestTOON_DeltaByShape`) are retained as the measurement record; a future response-shape flattening could revisit it. Had it been kept, the either/or would be real: MCP's typed `structuredContent`/`outputSchema` are JSON, so a TOON response rides in text content and forgoes machine-typed output — hence `json` default. Go encoder: `github.com/toon-format/toon-go`, version-pinned (spec still evolving, v4.x).
    - **The token win must not be clawed back on the return trip.** An agent that receives a cheap TOON response but then has to *re-emit* that payload as a JSON tool argument would pay full JSON price going back. The handle design (§8) prevents this by construction: agents pass **handles**, never document bodies, back to tools. This is a requirement, not an incidental property.
    - **Documents read from disk — JSON and LDJSON/NDJSON**, auto-detected (consistent with the repo's NDJSON input detection and its NDJSON export, ADR-0002/0004). **TOON on input is near-zero value for the token goal** and is accepted only as low-priority interop: a document at rest is never tokenized, so a TOON-on-disk file saves no reasoning tokens — the server parses it to structs either way. (This is deliberately the opposite of a first instinct to prioritize TOON input; the tokenization boundary is why.)
    - **TOON is a codec, not a converter.** TOON↔HDF is a lossless encoding of the JSON data model, the parallel of NDJSON — not a scanner→HDF converter, and it never enters `hdf-converters` or the registry. There is no "TOON schema"; validation is always decode-to-JSON then validate against the existing schema. A CLI-level `hdf convert --to toon` is out of v1 scope.

12. **CI posture — a non-interactive agent invoked from a pipeline, not a pipeline step.** For any *deterministic* pipeline step the CLI wins outright: `hdf validate threshold results.json -I "{compliance.min: 90}"` is one line with an exit code, no JSON-RPC hop, no schema-loading cost, and no model. **This server does not replace those, and should not be used for them.** Its value is where the next question depends on the previous answer — "the gate failed; what changed since last week, which failures are new, and which are already covered by an unexpired waiver?" — which is not expressible as a fixed CLI invocation, and is where both write-shaped evals live. (An analyst using an IDE agent against a 5 MB HDF file is served identically at no extra design cost, and is the likelier first real user.)

    Concretely: stdio transport only in v1. `HDF_MCP_ENABLE_WRITES` is the deployer ceiling on whether this deployment may write to disk at all; within a write-enabled deployment, write tools **write by default** and take `dry_run: true` to return the artifact they *would* write (summary plus path — never a megabyte body; §13 / Tool contract) without touching disk. In a writes-disabled deployment a write call returns that same preview plus an explicit `WRITES_DISABLED` notice, rather than silently doing nothing. Output is deterministic — canonical trimmed-UTC timestamps, stable key ordering — with **one deliberate exception**: the judgment path stamps a real `appliedAt` (the *when-applied* accountability timestamp of §2), which reflects application time rather than input, so an authored amendments document's `sha256`/handle are not reproducible across calls by design. Read tools, `hdf_diff`, `system`/`plan`/`evidence` authoring, and VEX-derived (`system`) writes carry no such wall-clock and are byte-reproducible. Tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) are set correctly because clients use `readOnlyHint` for parallel dispatch, but they are **advisory, not a safety control** — in CI there is no approver, and the spec directs clients to treat annotations from untrusted servers as untrusted.

13. **Reads degrade gracefully on invalid documents; writes refuse them; integrity is always over canonical JSON.** The schemas are `unevaluatedProperties`-strict and third-party HDF fails validation routinely. If `hdf_open` hard-failed, the agent's most common real task — *"why won't this file validate, and what's in it?"* — would be impossible through the server and the agent would fall back to shelling out, defeating the design. Therefore: `hdf_open` and all read tools succeed in **degraded mode**, returning `valid: false`, the detected type, and the first N validation errors with line numbers (the CLI already produces these, user story §2); every response over unvalidated content carries the flag. **Every write tool refuses invalid input.**

    Hashing, signing, and schema validation always operate on the **canonical JSON serialization**. Any TOON or LDJSON input is decoded and re-canonicalized (via the repo's deterministic serializer) before any of those; TOON is never the artifact of record and never carries an integrity hash of itself. This is a server-side correctness rule and has no bearing on token economics — it sits entirely on the zero-token side of §11's boundary.

    All paths are confined to `HDF_MCP_ROOT` (default: process working directory), returning `PATH_DENIED` otherwise. This must be configured explicitly because MCP **roots** — the primitive that would conventionally supply this context — is exactly what SEP-2577 deprecates.

14. **Logging to stderr only; nothing in the reachable dependency tree may write to stdout.** On a stdio transport, any stray write to stdout corrupts JSON-RPC framing and surfaces as an unparseable-message failure that is miserable to diagnose. `hdf-validators`, `hdf-parsers`, `hdf-diff`, and `hdf-converters/shared` are currently print-clean; `package cmd` is not, which is a further reason the extraction (Consequences) is load-bearing. Structured logs to stderr, level via `HDF_MCP_LOG_LEVEL`. No OpenTelemetry in v1. Enforced by a lint check plus a smoke test asserting stdout contains only JSON-RPC frames.

15. **A closed, machine-readable error taxonomy, where every error names the next call.** §10's truncation rule generalizes: an error that does not tell the agent what to do next causes a retry loop. Codes: `DOCUMENT_NOT_FOUND`, `PATH_DENIED`, `TOO_LARGE`, `WRONG_DOC_TYPE`, `SCHEMA_INVALID`, `HANDLE_STALE`, `NO_CONVERTER`, `TRUNCATED`, `AMBIGUOUS_FORMAT`, `OUTPUT_EXISTS` (a write refused because the output path already exists; pass `overwrite`), `WRITE_FAILED` (a filesystem write failure — permission-denied, no space, or a missing parent directory — distinct from `PATH_DENIED`, which is an outside-root confinement rejection), and `CACHE_MISS` (a cache-backed empty-path handle whose bytes have been LRU-evicted; re-author the document or set `output` to persist it — §8). All are returned as **tool results with `isError: true`** and a structured payload — they are recoverable and the model should retry differently. Only malformed calls surface as JSON-RPC protocol errors — including caller-argument mistakes (conflicting or unknown arguments), which return a code-less `{error, nextCall}` result and never borrow one of the document codes above. `WRITES_DISABLED` is deliberately **not** in this set: a write call in a writes-disabled deployment returns a *successful* response carrying the would-write preview plus a `writesDisabled: true` notice (§12) — the agent cannot enable writes, so there is nothing to retry and an `isError` would only invite the loop this taxonomy exists to prevent.

16. **All v1 tools are synchronous, with declared per-tool timeouts and honoured cancellation.** Handlers respect the SDK request context so client cancellation actually stops work (implemented for the heavy read ops — `hdf_query`/`hdf_diff` — in the `feat/mcp` branch). Any operation measured above 10 s against the largest fixture is deferred to a follow-up built on the Tasks extension (`tasks/get` / `tasks/cancel`, stateless polling in this revision) rather than blocking.

    **Measured timings (2026-08-11, `hdf-libs-huzc.1`).** Against real converter-output HDF results (`grype-to-hdf` expected, 14.2 MB / 1621 requirements — larger and better-formed than the originally-cited `wrapper.json`, which is InSpec *source*, not HDF) and a 2.95 MB / 534-requirement doc:

    | Operation | 14.2 MB / 1621 req | 2.95 MB / 534 req |
    |---|---|---|
    | full-verbosity `hdf_query` (Filter + project all) | 0.020 s | 0.007 s |
    | temporal `hdf_diff` (`DiffHdf`) | 0.003 s | 0.001 s |
    | emit comparison (marshal + schema-validate + sha256) | 0.260 s | 0.050 s |
    | `hdf_validate` schema (5–14 MB) | 0.106 s | 0.022 s |
    | `hdf_convert` (grype, 7.9 MB source) | 0.181 s | — |

    **No single-document op approaches 10 s** — the slowest (emit at 0.26 s on a 14 MB doc) is ~38× under the threshold. The two multiplicative paths were then measured directly:

    | Fan-out op | scale tested | time | extrapolated to 10 s |
    |---|---|---|---|
    | fleet `hdf_diff` (`DiffHdf` ModeFleet) | 100 / 500 systems × 534 req | 0.099 s / 0.490 s | ~10,000 systems |
    | evidence-package checksum fan-out (`VerifyChecksums`) | 100 / 500 files × 14.2 MB | 0.540 s / 2.624 s | ~1,900 files × 14.2 MB (~28 GB referenced) |

    **Neither reaches 10 s at any realistic scale.** A fleet would need ~10,000 systems; an evidence package would need ~1,900 large referenced files. The durable-task machine (a durable store + a custom `tools/call` dispatch shim) is therefore **not justified by current or extrapolated realistic HDF workloads** — it is a spec-completeness / far-future investment, not a present need. The Tasks-extension buildout (`hdf-libs-huzc`) is re-scoped on this evidence; core-spec `ctx` cancellation (this clause) is shipped independently.

17. **Contract versioning and advertised spec revisions are explicit.** SDK pinned to `github.com/modelcontextprotocol/go-sdk` v1.7.x — note its support for the 2026-07-28 revision is pre-release/experimental (the `v1.7.0-pre.1` line), so any reliance on revision-specific surface inherits pre-release churn. This is a further reason v1 treats the ratified **2025-11-25** as its build baseline and the 2026-07-28 revision as forward-compatible rather than required; **nothing in v1 hard-depends on an unratified feature** (the stateless-handle design of §8 is just "use tool arguments" and works under either revision). The server advertises both revisions, asserted by test. The tool surface is a public API: additive-only within a major version, renames get a deprecation window, response shapes are golden-tested, and `serverInfo.version` tracks the CLI version.

### Tool surface

| Tool | Serves user story | Write? | `readOnlyHint` |
|---|---|---|---|
| `hdf_open` | entry point (optional) — detect type, validate, headline summary, mint handle | no | true |
| `hdf_inspect` | §3, §6, §10, §11 — document-level structure and metadata | no | true |
| `hdf_query` | §4 — requirement filtering (the *only* path to requirements) | no | true |
| `hdf_compliance` | §12 — percent compliance, status/severity rollups, threshold verdict | no | true |
| `hdf_diff` | §5 — temporal and system-drift comparison | no | true |
| `hdf_validate` | §2, §11 — schema / checksum / completeness verification | no | true |
| `hdf_convert` | §1 — source tool output → HDF | gated | false |
| `hdf_author` | §6, §8, §10, §11 — author a document by `docType`: `system` / `plan` / `evidence` (create) or `amendments` (judgment or from-VEX; additive) | gated | false |
| `hdf_apply_amendment` | §8 — apply an amendments doc to a result set → new results + compliance delta | gated | false |

**`hdf_inspect` versus `hdf_query` — a bright line, because overlapping tools are the top cause of wrong-tool calls, and here the line also tracks the engine's real capability boundary.** `hdf_inspect` returns document-level structure and metadata **only** — baselines present, component inventory, plan assessments, evidence contents, change-event envelope/sequence metadata, counts — for all eight document types, and never returns a requirement collection. `hdf_query` is the only path to requirements, and today it *filters* only requirements in results/baseline documents (see Known constraints). `hdf_inspect`'s description states this explicitly ("to list requirements, use `hdf_query`").

### Tool contract

Caps are serialized-size budgets per §10. All tools accept `source` per §8 and `encoding` per §11.

- **`hdf_open`** — args: `source`. Returns: `{handle, docType, schemaVersion, valid, validationErrors[], summary}` where `summary` is type-specific (results: baseline count, requirement count, status breakdown; system: component count by type; plan: assessment count). Cap: 1k tokens. Annotations: read-only, closed-world.
- **`hdf_inspect`** — args: `source`, `section?` (enum per document type), `verbosity`, `page?`. Returns type-specific structure; never requirements. Cap: concise 2k / full 10k.
- **`hdf_query`** — args: `source`, and the nine extracted filters (`status[]`, `severity[]`, `impact`, `cci[]`, `nist[]`, `id`, `tag[]`, `search`, `baseline`), plus `verbosity`, `limit`, `page`. Returns `{total, returned, truncated, nextPage?, requirements[]}`. `concise` returns id/title/status/severity/impact only. **Applies to results and baseline documents only** — the filter engine is requirements-scoped today. A system, plan, evidence, or comparison document returns `WRONG_DOC_TYPE` pointing at `hdf_inspect`. When the shared query engine gains cross-document filtering (deferred; see Known constraints), `hdf_query` dispatches by detected document type and its applicability widens **additively** (§17) with no change to existing calls. Cap: concise 2k / full 10k.
- **`hdf_compliance`** — args: `source`, `groupBy?` (`baseline` | `severity` | `nistFamily`), `threshold?` (inline object or path). Returns `{compliance: float, counts: {status × severity}, agentOverrides: {count, complianceDelta}, thresholdVerdict?: {pass, failures[]}}`. The `agentOverrides` block is the detective surface of §3. Cap: 2k.
- **`hdf_diff`** — args: `from`, `to` (each a `source`), `mode` (`temporal` | `system-drift`), `verbosity`, `page?`. Returns a summary plus bounded change list. **Emits a schema-valid `hdf-comparison` document when `output` is given** — the diff result is a first-class HDF artifact, not a bespoke shape. Cap: concise 2k / full 10k.
- **`hdf_validate`** — args: `source` *or* `content` (inline candidate), `docType?`, `mode` (`schema` | `checksums` | `completeness`). `checksums` and `completeness` cover user story §11's `evidence verify` — the highest-value read in the evidence workflow, which the tool table would otherwise drop; both also report agent-attributed override counts (§3). Returns `{valid, errors[{path, line, message}], mode}`. Cap: 2k.
- **`hdf_convert`** — args: `source` *or* `content` (inline source-tool output), `from?` (auto-detected, incl. NDJSON), `output?`, `overwrite?`, `labels?`, `componentId?`, `dryRun?`. Returns a **summary only** — `{outputPath, sha256, docType, baselineCount, requirementCount, valid}` plus a handle — **never the converted artifact**, which is routinely megabytes. `dryRun: true` returns the same summary with `outputPath: null`. Ungated when `output` is omitted (pure computation). HDF→SIEM export is **out of scope**; ADR-0002/0004 own that direction.
- **`hdf_author`** — one `docType`-dispatched authoring tool (the shipped collapse of the former `hdf_build_document` + `hdf_create_amendment`). Args: `docType` (`system` | `plan` | `evidence` | `amendments`, **required**), `name` (**required**), `content?` (per-`docType` structured body — components / assessments / evidence contents, or an overrides array for `amendments`), `source?` (a VEX document for the amendments `from_vex` path), `expiresAt?`, `output?`, `overwrite?`, `dryRun?`. Per-item shapes come from the compact `hdf://schema/{docType}/{def}` slices, not the whole schema. Output that does not validate is refused. For `amendments` the server holds field authority: the judgment path (`content[]` of overrides) stamps `appliedBy.type = "agent"` + `appliedAt` and **requires `expiresAt` on each** (schema-required on every override as of v3.5.0/#195 — a missing expiry is rejected up front); the `from_vex` path (`source` + `expiresAt`) derives overrides and stamps `appliedBy.type = "system"` (§2, §4). Additive — never touches `source`. Returns a per-`docType` summary (e.g. `{outputPath, overrideCount, valid}` for amendments) plus a handle to the authored document; `dryRun` previews without writing.
- **`hdf_apply_amendment`** — args: `amendments` (source/handle), `results` (source/handle), `output?`, `dry_run?`. Applies the overrides to produce a **new** results document with `effectiveStatus`/`effectiveImpact`/`disposition` computed — **never overwrites `results`**. The applied file retains `statusOverrides[]` with `appliedBy`, so attribution and override counts survive on the results artifact itself (§3), not just in the amendments doc. Deterministic (the CLI's `hdf amend apply`, §5). Returns `{outputPath, projectedCompliance: {before, after}, thresholdVerdictChange?, changedRequirementCount, valid}`. `dry_run` returns that compliance delta and change count without writing — the create-once / apply-many check-before-commit.

### Known constraints

- **Filtered querying is requirements-only today.** `hdf query` filters requirements in results/baseline documents; it cannot yet *filter* systems, plans, evidence packages, or comparisons. (Structural *listing* of those is `hdf_inspect`'s job and is fully covered — the gap is filtering, not visibility.) This is sufficient for the v1 eval set: none of the six evals need cross-document filtering. Expanding the shared query engine to filter other document types is deferred to its own card (`hdf-libs-yamp`), dispatching by detected document type (the fingerprinting already exists in the CLI); when it lands, `hdf_query` widens additively (§17). The MCP does **not** implement cross-document query logic of its own — that would be exactly the engine/adapter drift §5 forbids.
- **Status vocabulary is effective, not raw, across every read tool (lj0g.4).** All status-reporting MCP tools — `hdf_open`, `hdf_inspect`, `hdf_compliance`, `hdf_query` — report a requirement's status by its canonical *effective* status (`hdfutil.ComputeEffectiveStatus`: `impact==0 → notApplicable`, governing overrides honored, worst-wins roll-up), via the single seam `countByEffectiveStatus`. The raw result-status roll-up (`CountControlsByStatusSeverity`) is **not** used by the read tools. The CLI threshold path (`hdf validate/generate threshold`) was corrected to the same effective-status seam (lj0g.8): it now routes through `CountControlsByStatus`/`MapControlIDsByStatus` with the effective-status resolver, so a CLI gate and `hdf_compliance` agree on one document and impact-0 controls count as `no_impact` rather than `skipped`. This was landed with explicit sign-off and a CHANGELOG behavior-change call-out because it changes CI-gate pass/fail outcomes on container-heavy corpora (measured ~+30 compliance points). `CountControlsByStatusSeverity` (raw) is retained for callers that explicitly want raw result-status counts. `hdf_compliance.counts` uses the SAF threshold-file vocabulary (`skipped`/`no_impact`) — deliberately, because `hdf_compliance`'s own `threshold` input and the CLI threshold files it must stay compatible with are keyed that way; renaming those keys would break a published format. The other read tools (`hdf_query`/`hdf_open`/`hdf_inspect`) use the HDF schema vocabulary. **The canonical mapping, stated here and in the `hdf_compliance` tool description so an agent never has to infer it: `skipped` == `notReviewed`, `no_impact` == `notApplicable`** (`passed`/`failed`/`error` are spelled the same in both). No third vocabulary exists on the tool surface, and both spellings are never emitted in one payload (lj0g.7).
- **Output payload schemas are typed only as far as the token ceiling allows (lj0g.3).** `hdf_compliance.counts` (top-level and per-group) is typed `object → object → integer` (value-typed) rather than left `additionalProperties: true`. It is NOT typed with the fully named status/severity keys: the concrete `StatusCounts` schema measured ~1212 tokens for `hdf_compliance` — roughly 2× the 600-per-tool ceiling — so the named-key shape is documented in prose (the description + this section) instead of in the schema. `hdf_query.requirements[]` and `hdf_diff.changes[]` items stay `additionalProperties: true`: their rows are heterogeneous (concise vs full) so a concrete item schema needs `oneOf`/a superset, and both tools already sit near the ceiling. This is a deliberate fidelity-vs-token-budget trade, re-open if the ceiling is ever raised.
- **Severity is explicit-STIG-tag-first, impact-derived as fallback — one rule for query and compliance (lj0g.5).** A requirement's severity is its explicit `tags.severity` when present, else `ImpactToSeverity(impact)` (zero band → `none` for SAF-threshold compatibility). This single rule (`deriveSeverity`) is shared by the compliance counts **and** the query/`Filter` row severity, so the two tools never disagree (an impact-0 control tagged `medium` reads `medium` in both, not `informational` in one). Threshold gating is unchanged (`deriveSeverity` was already explicit-first); the change is on the query side, which also means `hdf query --severity high` now correctly matches a `high`-tagged impact-0 control.
- **CLI/MCP reflection is a per-change decision, going forward.** Every future card that extends the CLI must decide whether the addition needs to surface in the MCP. The default expectation is *no* — most CLI additions are deterministic operations that belong to the CLI (§12) — but it must be checked per change, not assumed either way. The query-expansion card above is the first instance and does reflect into the MCP (additively).
- **Two v3.5.0 command families are out of v1 scope, applying the rule above.** `hdf enrich <results> <source>` (overlay a STIX bundle as inert External_Reference context, ADR-0006) and `hdf events derive|fold|apply` (the requirement-change-event stream, ADR-0005) both postdate the first draft. `enrich` is a deterministic transformation with no model judgment — per §12 it stays a CLI operation (v1 OUT), and if an agent ever needs enriched context it consumes the already-enriched results through the read tools. `events` derive/fold/apply is deterministic diff-adjacent computation over the 8th document type; it is a plausible *future* read-side tool (its `fold` output is an `hdf-comparison`, which `hdf_diff` already emits), but v1 neither implements it nor blocks it — the read tools must merely *tolerate* a change-event document as input (return `WRONG_DOC_TYPE` from `hdf_query`, structural metadata from `hdf_inspect`) rather than erroring opaquely. Reflecting either into a dedicated MCP tool is a separate decision, not v1.

## Alternatives Considered

### Alternative A: Mirror the CLI one tool per subcommand
Expose `hdf_query`, `hdf_list`, `hdf_diff`, `hdf_amend`, … matching the binary, flags as parameters.
- **Pros:** Trivial to build and document; automatic feature parity.
- **Cons:** CLI flags are tuned for humans who read `--help`. `query` alone would carry nine filters plus output controls, past the ~8-parameter guidance, and the surface grows unboundedly with the CLI.
- **Why rejected:** The documented user stories, not the flag surface, are the validated unit of work, and they give a contract that survives CLI churn.

### Alternative B: Per-document-type tool families (the OSCAL model)
A `query_*` + `list_*` pair per document type plus child-element tools for requirements, findings, components, overrides.
- **Pros:** Complete and mechanical; mirrors the schema; `awslabs/mcp-server-for-oscal` proves it ships.
- **Cons:** That server exposes ~50+ tools whose schemas load on every request regardless of use — the largest cost the design carries, and directly contrary to the fewer-tools consensus.
- **Why rejected:** Take that project's architecture — bundled schemas, validation as a first-class tool, document caching — without its tool count.

### Alternative C: Separate repository, plugin-installed (the Trivy model)
Own repo, own release cadence, plugin install.
- **Pros:** Matches dominant prior art (`terraform-mcp-server`, `semgrep/mcp`, `trivy-mcp`, `mcp-server-for-oscal`); clean isolation; independent versioning.
- **Cons:** Each of those precedents is a vendor shipping a server for a hosted product, and each adds an install step. For a CI consumer a second artifact is friction, and it splits CI, fixtures, and release across repos while the server depends on modules already wired through `go.work`.
- **Why rejected:** The isolation benefit is obtainable through the package boundary in §7 without the distribution cost. Revisit if the server grows a network transport and its own security surface.

### Alternative D: TypeScript implementation for npm reach
Build in TS to match how the wider MITRE SAF ecosystem distributes (`saf-cli` is npm).
- **Pros:** `npx` is the most common MCP install path; reaches the existing SAF audience; more mature SDK.
- **Cons:** The query engine, compliance math, threshold logic, and detection exist only in Go. TS would duplicate them — creating exactly the drift the parity invariant exists to prevent — or shell out, which §5 rejects.
- **Why rejected:** Real duplication cost for a distribution channel this consumer does not use.

### Alternative E: Shell out to the `hdf` binary
Thin wrapper that execs `hdf query --json` and forwards stdout.
- **Pros:** Fastest to build; zero duplication; automatic parity.
- **Cons:** CLI output is a presentation layer, not a stable API; no way to bound response size before serialization; errors degrade to exit codes and stderr scraping; process spawn per call.
- **Why rejected:** `containers/kubernetes-mcp-server` treats "not a kubectl wrapper" as its defining quality, and the libraries are right there — though see Consequences for how much extraction that actually requires.

### Alternative F: Read-only v1, defer all authoring
Ship inspection, query, compliance, diff, and validate; postpone every write.
- **Pros:** Smallest blast radius; matches the "start with read-only servers" consensus; `hdf_validate` is nearly free given `hdf-validators`. **It is also the only option that provides a *preventive* governance stance** — by not building the authoring capability, there is nothing for an agent to misuse.
- **Cons:** Two of the six target evals are writes, and they are where the differentiated value sits.
- **Why rejected (sequenced, not declined on merits):** Overridden by the project scope decision. The governance risk it names is real; §3 answers it with *detective* controls plus deployer-side preventive controls, not with a preventive control in the server. If team review judges detective-only insufficient, this alternative is the fallback — see the first Open Question.

### Alternative G: Let the agent author HDF JSON, then validate it
Expose schemas as resources and a `hdf_validate` tool; let the model write documents and retry on failure.
- **Pros:** Maximum flexibility; no per-document authoring tools.
- **Cons:** Burns tokens on retry loops, and produces plausible-but-wrong documents that pass schema validation while being semantically wrong — a waiver with a valid shape and an incoherent justification. Makes output quality a function of model temperament.
- **Why rejected:** Structure is the server's job (§2). Schema-valid is a floor, not a goal.

### Alternative H: Do Nothing
Agents keep shelling out to `hdf` or loading documents directly.
- **Pros:** Zero cost; no new surface to maintain, secure, or version; the MCP spec is mid-transition and some churn is certain.
- **Cons:** Leaves the size problem unsolved — a 5 MB document is simply not consumable. Cedes ground in an ecosystem where OSCAL, Trivy, Semgrep, and Terraform all ship servers.
- **Why rejected:** The gap is real and the engine cost is low relative to the value — though the extraction is larger than first estimated. The churn argument is weaker than it looks: 2025-11-25 remains supported and deprecated features are guaranteed ≥12 months (SEP-2596).

## Consequences

**Easier after this decision:**
- Agents can answer questions about multi-megabyte assessment data without loading it.
- Compliance percentage and threshold gating become agent-callable, serving the CI workflow the repo already documents.
- Schema confabulation drops, because schema slices are served authoritatively rather than recalled.
- The nine-tool surface is a stable contract that survives CLI flag churn.
- **The `hdf-engine` library below is independently valuable.** Pure, importable, dual-language detect/query/compliance engines are testable in isolation and reusable by any future consumer (CLI, MCP, external Go/npm); today they are reachable only through cobra.

**Harder after this decision:**
- A new workspace library (`hdf-engine`) to version, publish, and keep in TS↔Go parity — plus a second consumer (the MCP) of the shared libraries, so refactors gain another caller to satisfy.
- Spec churn: the SDK is pinned and two revisions are advertised (§17), but this will need maintenance.

### The `hdf-engine` library + extraction manifest (this is the real cost, and it is Phase 1)

The first draft of this ADR described this as "lifting `detectHDFDocumentType` — a small but real refactor." That was wrong by roughly an order of magnitude, and the destination has since been decided (2026-08-03 engine-library revision): the schema-typed operation engines move into a **new dual-language workspace library `hdf-engine`**, not `hdf-cli/internal/*`.

**Layering.** `hdf-schema` (types) → `hdf-utilities` (schema-free primitives: `WorstStatus`, `ImpactToSeverity`, `ComputeEffectiveStatus`, and — new — `safePath`) → **`hdf-engine`** (schema-typed engines: detect, query, compliance) and its sibling `hdf-diff` (diff / change-events / amend) → the two thin adapters, `package cmd` (CLI) and `hdf-cli/internal/mcp` (MCP). Both adapters import `hdf-engine`; neither owns the engines. `hdf-engine` may depend on `hdf-diff` if a future engine needs it (one direction, no cycle); today it does not.

**What goes where** (not everything trapped in `package cmd` belongs in `hdf-engine`):

| Capability | Current location | Destination + work |
|---|---|---|
| `detectHDFDocumentType` | `cmd/hdf/cmd/detect.go:14` (relocated to `hdf-cli/internal/hdfdetect` by w913.1) | **`hdf-engine`** (Go + new TS port). Relocate the shipped Go package out of `hdf-cli/internal`; add the TS implementation for parity; CLI + MCP delegate. |
| Query engine (`buildFilters`, `findMatches`, filter helpers, query-only `safematch.go`) | `cmd/hdf/cmd/query.go`, `package cmd`; **`buildFilters()` reads package-level flag globals** | **`hdf-engine`** (Go + TS). Refactor to a pure `Filter(results, Options)` (concurrency-safe, no globals); status resolution injected so the engine is display-convention-agnostic. |
| `calculateCompliance`, `countControlsByStatusSeverity` (+ threshold verdict) | `cmd/hdf/cmd/threshold.go` | **`hdf-engine`** (Go + TS) as pure functions. Roll-up/severity math is already in `hdf-utilities` (`WorstStatus`/`ImpactToSeverity`, #193) — import it; `overallStatus` is a not-yet-migrated duplicate of `hdfutil.WorstStatus` (`hdf-libs-ixhx`), fold it in here. |
| Document loader (`parseHDFResults` / `parseHDFBaseline` + detect + size/degraded validation) | `cmd/hdf/cmd/input.go` | **Split.** The schema-typed parse/detect/validate core → `hdf-engine`; the MCP-specific byte-bounded cache + degraded-read envelope → `internal/mcp` (it wraps the engine core). |
| `safePath(baseDir, relPath)` | `cmd/hdf/cmd/input.go:151` | **`hdf-utilities`** — it is generic path confinement with **no schema types**, so it belongs in the schema-free layer, not `hdf-engine`. Caller supplies the base dir (`HDF_MCP_ROOT`, §13). |
| Converter registry (map + `registerHDFConverter` across per-converter `init()`s) | `converter_registry.go`, `package cmd` | **`hdf-converters`** — converter plumbing belongs with the converters, not the engine library. Lift to an importable package both `cmd` and `internal/mcp` register against (needed for §9's `hdf://catalog/converters`, and to keep cobra/console out of the stdio process, §14). |

The CLI is refactored onto `hdf-engine` in the same phase as each extraction, so there is one implementation per engine (Go and TS), not two. **Dual-language parity lands in the same PR per engine** — the Go and TS implementations of an engine, plus their parity tests, are one card, never split.

**Risks:**
- **Governance (highest).** An agent creating and applying waivers in an automated pipeline — the default-write base case (§3) — is a compliance hazard, and **this server provides no preventive control** against it: the additive amendment model, `dry_run`, and the write gate are correct-modeling, caller-preview, and deployer-ceiling respectively, none of them authorization. The mitigations are **detective and live outside the server**: agent attribution that travels in the data and survives into the applied results file, first-class agent-waiver counts surfaced to whoever holds the apply privilege, and the apply-time compliance delta. Note the blast-radius shape: because one amendment applies to many result sets (create-once / apply-many), a single bad agent judgment fans out across every target it is applied to, so the worst case is "one bad waiver, everywhere," not "one bad waiver." The named deployer-side preventive controls (permissions, branch protection, signing) mostly gate a *different* threat (repo and transit integrity) than the in-job case where a gate is satisfied by agent-manufactured pass-state within a single job — for which there is no in-job preventive control (§3). **This is what team review should scrutinize hardest**; if detective-only is judged insufficient, the fallbacks are a separate `HDF_MCP_ENABLE_APPLY` gate on the adjudicative apply, flipping the default back to preview-first, or Alternative F (build no authoring capability at all — the only fully preventive stance).
- **Extraction regression.** Refactoring the CLI onto `hdf-engine` risks behaviour change in shipped commands. Mitigated by doing it first, with the existing CLI test suite as the contract.
- **Dual-language drift.** The TS side of `hdf-engine` has no in-repo consumer today (the CLI/MCP are Go), so its TS implementations of detect/query/compliance could silently diverge from Go — the exact risk the parity invariant exists to prevent. Mitigated by landing Go+TS together per engine (one PR) with cross-language parity tests, exactly as `hdf-diff` does; this is a real ongoing maintenance cost accepted for ecosystem reach and parity consistency.
- **Semantically-valid-but-wrong output.** Schema validation cannot catch an incoherent attestation. Mitigated by keeping structure server-side and by the compliance delta making impact visible; not eliminated.
- **Token budget drift.** Mitigated by the `tools/list` ceiling and golden file (Verification).
- **Sensitive content exposure.** `verbosity: full` responses carry raw command output; they are annotated as such, and deployment guidance states that document content reaches the model provider.

## Implementation Plan

### Quality Standards (inherited by every card)

- **Framework-first:** use `modelcontextprotocol/go-sdk` idioms (typed structs, `jsonschema` tags). Do not hand-roll JSON-RPC, transport, or schema generation.
- **Existing patterns:** reuse `hdf-validators`, `hdf-engine` (detect/query/compliance), `hdf-diff`, and the lifted `hdf-converters` registry. New logic in `internal/mcp` is a defect unless justified — this is an adapter over `hdf-engine`.
- **No CLI shell-out** (§5) and **no cobra imports in `internal/mcp`** (§7). Both enforced by test; a card that violates either fails verification.
- **Nothing on stdout** (§14), enforced by lint plus smoke test.
- **Token bounding is an AC**, not a nicety: default cap, pagination, and a truncation notice naming the narrowing parameter, on every collection-returning tool.
- **Test strategy:** table-driven unit tests per tool; golden-file response shapes; eval-transcript integration tests. Real fixtures only — no fabricated documents.
- **Security by design:** all paths confined to `HDF_MCP_ROOT`; `ValidateJSONSize` on every read; writes gated by `HDF_MCP_ENABLE_WRITES` (default-write within a write-enabled deployment, `dry_run` opt-in preview); `hdf_author` (amendments) is additive and `hdf_apply_amendment` never overwrites its input; no secrets in output or logs.
- **Determinism:** canonical trimmed-UTC timestamps; stable key ordering; byte-reproducible output for read tools, `hdf_diff`, and `system`/`plan`/`evidence` + VEX-derived (`system`) writes. The one deliberate exception is the judgment path's `appliedAt` — a real *when-applied* action timestamp (§2/§12) that makes an authored amendments document's `sha256`/handle vary across calls; the response-golden strips those two content-integrity values for author/apply precisely because they fold in `appliedAt` (this exception is documented, not silently masked). Any future-dated fixture uses `2099-12-31T00:00:00Z` per repo rule.
- **Coverage:** >90%. `pnpm check` and `golangci-lint run` must pass.

### Scope

**IN:** the nine tools with the contract above; schema-slice, catalog, and enum resources; stdio transport; JSON/LDJSON input and JSON/TOON output; the default-write / `dry_run`-preview model, the `HDF_MCP_ENABLE_WRITES` gate, agent attribution, and the agent-override counts surfaced in compliance/threshold/evidence readouts; `hdf_author` (amendments) / `hdf_apply_amendment` (create-once / apply-many) including `from_vex` creation and the underlying `hdf amend --from-vex`; the new dual-language `hdf-engine` library and the extraction manifest (engines dual TS+Go with parity per PR; `safePath`→`hdf-utilities`, registry→`hdf-converters`); eval harness; a guide page and a usage Skill.

**OUT:** Streamable HTTP transport; authentication and multi-tenancy; MCP prompts and sampling; HDF→SIEM export (ADR-0002/0004 own it); user stories §7 (labels/componentIds) and §9 (InSpec profile generation) — both are one-line deterministic CLI invocations, which per §12 is exactly what should stay in the CLI; §13 (`fetch` — credentials and `openWorldHint: true` warrant their own decision); `hdf enrich` (STIX CTI overlay, ADR-0006 — a deterministic CLI transformation per §12) and `hdf events` derive/fold/apply (the change-event stream, ADR-0005 — a plausible future read-side tool, deferred; see Known constraints); a TypeScript implementation; a CLI-level `hdf convert --to toon`; cross-document query filtering (its own card); any change to the eight schemas.

**Future:** Streamable HTTP with auth if a Heimdall-adjacent deployment materialises; Tasks-based async for any operation measured over 10 s (§16); the evidence-package "what will draw an assessor's attention" rollup (eval 5), which needs its own design.

1. **Extraction and foundations** — scaffold the `hdf-engine` dual-language library, then the manifest: detect/query/compliance into `hdf-engine` (Go + TS parity per engine, same PR), `safePath` into `hdf-utilities`, the converter registry into `hdf-converters`, and the loader split (engine core in `hdf-engine`, cache/degraded envelope in `internal/mcp`). CLI refactored onto the extracted libraries with its existing tests green; `hdf-cli/internal/hdfdetect` (w913.1) relocated into `hdf-engine`. Scaffold answers `tools/list` with an empty set; eval harness runs. *This is the highest-risk phase and carries the most cards.*

3. **Analysis** — `hdf_compliance` (with threshold verdict and agent-override counts), `hdf_diff` (emitting `hdf-comparison`), `hdf_validate` (all three modes, covering `evidence verify`). §2, §5, §11-verify, §12.

6. **Authoring (default-write, gated)** — `hdf_convert`, `hdf_author`, `hdf_apply_amendment`. §1, §6, §8, §10, §11. Every card carries the default-write/`dry_run`, agent-attribution, additive-create / never-overwrite-on-apply, and apply-time compliance-delta ACs.

### Verification Strategy

**The six target evals**, executed as recorded tool-call transcripts with assertions on the final answer *and* a token budget per transcript; a transcript that regresses on tokens fails:

1. Summarize the components in an HDF system document.
2. Find `notReviewed` results in an HDF results document and draft attestation amendments from existing system knowledge.
3. Summarize the changes represented by an HDF diff document.
4. Parse an HDF plan document and suggest testing tools to implement it.
5. Identify the single biggest issue in an HDF evidence package that will draw an assessor's attention. *(Stretch — may defer; see Future.)*
6. Apply a VEX document as HDF amendments to an HDF results document.

Plus one transcript per covered user story.

- **Token budget.** `tools/list` ≤ **4,500 tokens** total, ≤ **600 for any single tool**, hard fail at 6,500, measured on the marshalled `ListToolsResult` with a pinned tokenizer (O200kBase). **Shipped nine-tool measurement: 4,216 tokens total, ≈468-token average, no violations.** The three schema-heavy tools concentrate the budget and are where the per-tool ceiling bites — `hdf_diff` (596), `hdf_author` (595, the discriminated `docType` union), `hdf_compliance` (580); `hdf_query` (501, nine filters) sits just below them. The `outputSchema`-vs-`structuredContent` decision (§11) matters most for exactly these — decide and record whether typed `outputSchema` is emitted per tool, since the SDK infers it from result structs and it can cost as much as the input schema. The whole `tools/list` JSON is **golden-filed**, so growth surfaces in code review rather than silently consuming headroom.
- **TOON measurement.** Encode the `hdf_query` concise response for a real fixture both ways and record the delta. Below ~20%, drop TOON.
- **Golden responses** for every tool from real fixtures.
- **Write-gate tests.** `HDF_MCP_ENABLE_WRITES` unset → every write tool returns a preview plus a `WRITES_DISABLED` notice and touches no file. Enabled → default writes; `dry_run: true` previews and touches no file. Assert `hdf_author` (amendments) never touches its `source` and `hdf_apply_amendment` never overwrites its `results` input, in any mode.
- **Agent-attribution test.** Every override from `hdf_author` (amendments) carries `appliedBy.type = "agent"` and the model cannot override it; `hdf_compliance` and the threshold/evidence readouts report agent-attributed override counts, and `hdf_apply_amendment` reports the before/after compliance delta against the target.
- **Determinism test.** Same inputs twice, byte-identical output.
- **Protocol tests.** stdout carries only JSON-RPC frames; both advertised spec revisions negotiate; timings for every tool against `wrapper.json` recorded and compared to the §16 threshold.

## Open questions for team review

1. **Uniform default-write is a deliberate posture; the team should ratify or reject it.** All four write tools write by default (with `dry_run` opt-in), **including the adjudicative `hdf_apply_amendment`** — the owner's decision, taken with the understanding that the autonomous-pipeline base case then has **no in-job preventive control** (§3): the server cannot stop an agent-created amendment from being applied within a job, only make it visible (attribution in the data that survives to the applied file, agent-override counts, the apply-time compliance delta), backed by out-of-band audit and whatever write access the deployer grants. The reviewed alternatives were considered and set aside in favour of maximal autonomy: (a) a separate `HDF_MCP_ENABLE_APPLY` gate on the adjudicative tool only — letting a deployer permit autonomous *drafting* for review while forbidding autonomous *application*; (b) defaulting `hdf_apply_amendment` alone to `dry_run`; (c) preview-first globally; (d) Alternative F (no authoring — the only fully preventive stance). **The team should confirm uniform default-write is acceptable for the intended deployments, or adopt one of (a)–(d).** This is the decision review should focus on.
2. **Process model in CI** — one server per pipeline run, per step, or per tool call? §8 is designed to be indifferent, but cold-start cost (embedded schemas, registry `init()`) should be measured before Phase 1 closes.
3. **Should the extraction be its own epic**, landed and released before any MCP card starts? It is independently valuable and independently risky.
4. **Does the server accept piped stdin documents?** CI often has a stream, not a path. Not currently in the `source` union.
5. **Type mismatch behaviour** — valid HDF, wrong type for the tool (a `system` document passed to `hdf_query`): return `WRONG_DOC_TYPE` (current design), or detect and answer anyway once cross-document filtering lands?
6. **Is `hdf amend --from-vex` in this ADR's scope**, or does it deserve its own ADR given it defines a VEX→`Override_Type` mapping with governance meaning?
7. **Prompts revisit.** If an interactive analyst (IDE agent against a local HDF file) becomes a primary consumer, revisit a small set of discovery-oriented prompts — zero-install discoverability is the one affordance a Skill lacks (§9).
