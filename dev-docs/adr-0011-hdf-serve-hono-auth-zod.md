## Context

ADR-0008 defines the HTTP contract and ADR-0010 the storage and query layer; nothing serves them. ADR-0007 built the agent surface as a Go stdio MCP server and put Streamable HTTP, auth, and multi-tenancy out of scope "until a deployment materialises". Three requirements now exist that ADR-0007 deferred: an HTTP API for pipelines and viewers, an authentication/authorization layer with organizations and teams, and Zod-typed request/response handling with a client SDK.

**The language question.** The repo's tools (CLI, MCP) are Go; its libraries are dual TS + Go. A Go `hdf serve` would reuse the nine MCP handlers and ship in the existing binary — the smallest change today. But every component the service must integrate is TypeScript-native: the Zod pipeline (ADR-0008 §7) and the reference identity/organization stack (better-auth). A Go service would run better-auth as a second process and confine Zod to the client. The service is a hosted, multi-tenant web service with users, organizations, OAuth clients, and a client SDK — a TypeScript stack is where that lives. The decision is therefore **TypeScript (Hono) for the service; Go stays the CLI and the local/pipeline MCP**, with one shared data layer (ADR-0010) and one shared token-verifier contract so the two never diverge on storage or identity. This is reviewer challenge (a), and its costs are listed honestly below and in Consequences.

**What "wiring over existing TS libraries" is true of, measured.** Five of the nine MCP operations have TypeScript twins today (open/inspect via `hdf-engine` load and detect; query via `hdf-engine` filter; compliance via `hdf-engine`; diff via `hdf-diff` `diffSystems`/`systemDrift`; validate via `hdf-validators` + `hdf-engine` evidence). Four do **not**: `hdf_apply_amendment` calls `amend.MergeAmendments` (`hdf-diff/go/amend/amend.go`, no TS twin); `hdf_author` builds system/plan/evidence/amendments documents in `hdf-cli/internal/hdfdoc` (Go, CLI-internal, including `AmendmentsFromVex`); `hdf_convert` uses the pair-keyed Go registry (`GetConverter(source, dest)` in `hdf-converters/registry/convert`), while TS exports only per-converter functions and fingerprint detection. Those are **ports, not wiring** — four ports in three prerequisite cards of this ADR (Implementation Plan).

## Decision

### 1. Package, runtime, service structure
Create **`hdf-serve`** (`@mitre/hdf-serve`): a library exporting `createApp(config)` (a Hono app) and `startServer(config)`, plus a `bin` (`hdf-serve`, with subcommands `start` (default), `migrate [--index [--concurrently]]` (both ledgers, the `pgboss` schema and grants, ADR-0009 §11's owner-run index path), `bootstrap`, and ADR-0013's `audit verify`). There is no `hdf serve` Go subcommand; the CLI docs say "run `hdf-serve`". Hono 4.13 on **Node ≥ 24** via `@hono/node-server` 2.1.x; TypeScript only (the service is a consumer of the dual-language layers, not one of them). Dependencies: `hdf-data` (ADR-0010) for all storage and queries, `hdf-openapi` (ADR-0008) at build time, `hdf-validators` for boundary validation, the TS engine/diff/converters libraries (plus the ports below), better-auth with `jwt`, `organization`, `twoFactor`, `bearer`, `openAPI`, `@better-auth/oauth-provider`, `@better-auth/api-key`, `@better-auth/mcp`, `@better-auth/cimd`, `@hono/zod-openapi`, `zod` 4.5.x, ajv 8 (2020 build), `jose`, `nodemailer`, `pino`, and ADR-0013's job runner (`pg-boss`). **The service constructs the one database handle** — a PGlite instance (with `pglite-pgvector`) or a `pg` pool from `HDF_DB_URL` — runs both migration ledgers **before** constructing better-auth or the store, and hands the handle to `hdf-data`'s `createStore({backend: 'db', db})`, to better-auth's `drizzleAdapter`, and to the job runner; it refuses `HDF_STORE=file` and `http`.

**Structure, from Hono's guidance**: one `OpenAPIHono` per resource (`documents` — incl. evidence and hold —, `query`, `compliance`, `diff`, `validate`, `precedent`, `audit`, `jobs`, `organizations`, `webhooks`, `health`) mounted with `app.route()`; `createFactory<Env>()` with `Env = {Variables: {principal, requestId, logger}}` for shared handlers; a **fixed middleware order** — `requestId` → logger (pino through a thin middleware; no `hono-pino`) → `secureHeaders` (defaults; `Cross-Origin-Resource-Policy` relaxed only on the two OpenAPI documents) → `cors` (`HDF_CORS_ORIGINS`, the same list as better-auth's `trustedOrigins`; `exposeHeaders: ['ETag', 'Retry-After', 'RateLimit', 'RateLimit-Policy', 'Deprecation', 'Sunset']`) → **auth** → `bodyLimit(HDF_MAX_BODY_BYTES)` → ajv → route. Auth precedes the body limit deliberately: auth reads headers only, and Hono's `bodyLimit` buffers a chunked body in memory before calling the next handler, so an unauthenticated request must never reach it; the heap bound is `HDF_MAX_BODY_BYTES × in-flight requests`, stated in the posture doc. The order is registered once in `createApp` and asserted by a test that reads the middleware stack; **graceful shutdown** in `startServer`: flip readiness, `server.close()` + `closeIdleConnections()`, a bounded 10 s drain, then close the job runner and the database handle. Configuration is one Zod-validated object read from `HDF_*` environment variables (ADR-0010 §3's table plus the rows in §5 here); the process refuses to start on an invalid configuration. The service is **published two ways**: the npm package, and a container image built by the release workflow (`gcr.io/distroless/nodejs24-debian12`, digest-pinned, non-root, read-only filesystem with one writable mount for `file://` PGlite mode, signed with cosign, SBOM attached, scanned) — the workflow gains an image job (Phase 8). Because distroless has no shell, the entrypoint is `src/entrypoint.ts` (§3's role checks run there). **Posture**: TLS terminates at a reverse proxy — the npm `start` binds loopback by default (`HDF_BIND`) while the container entrypoint defaults to `0.0.0.0:8080` so a proxy outside the container can reach it; the service trusts `X-Forwarded-*` only from `HDF_TRUSTED_PROXIES`, and the container defaults `HDF_DB_SSL` to `verify-full` and refuses `disable` (ADR-0013 §6).

### 2. The service implements ADR-0008's document; it never authors it
- **Routes** are declared with `@hono/zod-openapi`'s `createRoute` using Zod schemas **generated** from `@mitre/hdf-openapi`'s `dist/hdf-api.oas.json` by `@hey-api/openapi-ts` (exact-pinned) into `src/contract/` (tracked `*.gen.ts`; `pnpm gen:contract` runs inside `build` so pnpm's topological order builds `hdf-openapi` first; a CI diff gate). The generator run carries ADR-0008 §7's `~resolvers` setting so path and query parameters are pre-processed from strings (run in the round-6 spike: without it `GET /documents?limit=5` is a 400; that probe's output was not retained and Phase 1's stub repeats it). Path/query parameters, envelopes, problem details, and the `fullShapes` responses come from that output. HDF document bodies follow ADR-0008 §7 exactly: the eight root schemas are registered as raw components, the media-type schema is a `$ref`/`oneOf` (non-Zod, so the route validator skips it — the skip is a one-line guard in `@hono/zod-openapi` 1.6.2's source, and the spike exercised it), and an **ajv 2020 middleware** registered before the route dispatches by `hdf-engine`'s detector and validates the one matching root.
- **Parity** is ADR-0008 §7's projection **P** plus the un-projected inventory/security assertion, run against `getOpenAPI31Document` — **measured to hold with zero residual on a representative sample**. `src/contract/extra-paths.ts` carries two lists: `extraPaths` — served by the service but absent from the document (`/healthz`, `/readyz`, `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, and the rest of `/api/auth/*`, which is mounted outside the registry) — and `documentOnlyPaths` — present in the document but served by better-auth, not by a registry route (`/api/auth/oauth2/token`, `/api/auth/api-key/exchange`); the inventory assertion exempts both lists explicitly. Alternative K of ADR-0008 is the recorded fallback.
- **Every operation** is a thin function: authenticate → derive `Principal` → validate → call `hdf-data` (store, engine bridge, or query) → run the same engine/diff/converter function the Go MCP tool runs → shape the canonical full response. The **conventions of ADR-0008 §3** are middleware: opaque ids + `ETag`, `If-Match` → 412, uniform tenant-scoped 404, 413/415 with the advertised cap, `<!DOCTYPE` rejection for XML inputs, cursor pagination with `limit` coerced to its maximum, `RateLimit`/`RateLimit-Policy` on every response, 429/503 with `Retry-After`, a declared 500 with a request id and nothing else, RFC 9745 `Deprecation` + RFC 8594 `Sunset` on deprecated operations, `x-hdf-schema-version` on every response, RFC 9457 bodies from ADR-0010 §6's table.
- The **four synthetic operations** of ADR-0008 §2 are covered here: ingest (`put`, `hdf:write`) and delete (`delete`, `hdf:admin`) as registry routes; the two `documentOnly` token operations by better-auth (§3). ADR-0013's `202` + `/jobs/{id}` pair is added when that ADR's Phase 1 lands.
- **The companion auth document — strictly `/api/auth/*`.** Organization, team, member, OAuth-client, and API-key management are better-auth's endpoints and stay outside ADR-0008's document. The service publishes **`hdf-auth.oas.json`**, produced by better-auth's `openAPI` plugin (`auth.api.generateOpenAPISchema()`) merged with the service-owned plugin endpoints under the same mount (§3: client creation, API-key creation and exchange, revocation), served at `/api/auth/reference`, sharing the bearer scheme and problem conventions; it is not P-compared (better-auth authors it), but its route inventory is asserted against a tracked list so an upgrade that adds or drops an endpoint fails a test. Every HDF-owned route — including ADR-0013's export, usage, hold, and webhook routes — lives in the main document under ADR-0008 §2's synthetic-operation rule, never here. The client (§4) gains a second generated namespace from this document.
- **Contract tests** call the running app through the generated client (§4) against real fixtures for every operation, including the semantic cases ADR-0008 could not test without a producer (`limit: 0 = all`, the impact comparison grammar).
- Operations that do not exist in the MCP golden do not exist in the main document. The precedent/similarity operations arrive **only after** the ADR-0007 amendment adds `hdf_precedent`/`hdf_similar` (with the row registration and `bindings.yaml` entries) and ADR-0008 regenerates (Phase 7).

### 3. Authentication and authorization
- **Default issuer — better-auth in-process** (`HDF_AUTH_MODE=builtin`), mounted at `/api/auth/*` on the shared database handle, `cors()` registered before the mount, `trustedOrigins` required. Plugins and their roles:
  - `jwt` — EdDSA/Ed25519 by default, **ES256 when `HDF_FIPS=true`** (OpenSSL's FIPS provider does not enable Ed25519); **`issuer` set to `<HDF_BASE_URL>/api/auth`** so that jwt-plugin and `signJWT` tokens carry the same `iss` as OAuth-provider tokens (measured: they otherwise differ) — one issuer per deployment, pinned by both verifiers; the fallback, if a plugin refuses the setting, is an explicit two-entry issuer allowlist in the verifier description; `exp` 15 min; `jwks.rotationInterval`/`gracePeriod` set and the rotation schedule documented alongside `HDF_AUTH_SECRET` rotation; `disableSettingJwtHeader: true`; `definePayload({user, session})` — which receives only the user and session — closes over the shared database handle, reads `session.activeOrganizationId`, queries `member` for that user's role in it, and emits `org`, `team`, `role`, `scope` (space-separated), `jti`; no membership → no `org` claim → `403` (below). A `databaseHooks.session.create.before` hook seeds `activeOrganizationId` from the user's last active organization so a fresh session is not organization-less.
  - `organization` — teams enabled; `sendInvitationEmail` wired to the mailer (§5). Access-control statements exist **only to feed one tracked role→scope table** (`src/auth/scopes.json`): `document: [read, write, delete]`, `organization: [manage]`; roles **member** → `hdf:read`, **admin** → `hdf:read hdf:write`, **owner** → `hdf:read hdf:write hdf:admin`. There is no second permission vocabulary on the API.
  - `twoFactor` — **required for owner and admin roles**: assigning either role to a user without a verified second factor is refused, and a token for such a user carries `amr: ['pwd', 'mfa']` — derived in `definePayload` from `user.twoFactorEnabled`, because better-auth records no per-session completion flag (a session exists only after the challenge passes) (ASVS 6.3.3, IA-2(1)). Sign-in **lockout**: a `sign_in_attempts(user_id, failed_count, window_start, locked_until)` table; after 10 consecutive failures for one account within 15 minutes the account is locked for 15 minutes (800-63B-4's bound is 100), reset on success and on password reset; every failure and lockout is an audit event (ADR-0013); the second-factor step has better-auth's own `failedVerificationCount`/`lockedUntil`. Password policy: 15-character minimum, a breached-password blocklist check, no periodic rotation.
  - `@better-auth/oauth-provider` — **the default machine path**: a pipeline is an **OAuth client**. Because the public create-client endpoint drops the scope ceiling (measured), the service owns **`POST /api/auth/clients`** (in the companion document): after its own organization-owner check it calls the server-only `auth.api.adminCreateOAuthClient` with `clientPrivileges` configured, `referenceId` = the owner's active organization, `clientCredentialsScopes` = the requested subset of that organization's scopes (never `hdf:admin`), and links the client to both resources; `redirect_uris` is a placeholder for `client_credentials`-only clients. `clientRegistrationDefaultResources: [HDF_BASE_URL, HDF_MCP_RESOURCE_URL]`. The client obtains a token with `client_credentials` at **`/api/auth/oauth2/token`** with RFC 8707 `resource` **required** — a `hooks.before` on that endpoint rejects a `client_credentials` request without `resource` with `invalid_target`, because only then is the token a JWT (`typ: at+jwt`, `aud` = the resource; measured: without `resource` the provider issues an opaque token the verifiers cannot check); a plugin `init` calls `extendOAuthProvider(ctx, {claims: {accessToken: ({client}) => ({org: client.referenceId})}})` so the token carries `org` (measured); `sub` is the provider's reserved bare `clientId` (also present as `client_id`/`azp`), and ADR-0009 `created_by` records that `sub` verbatim; `m2mAccessTokenExpiresIn: 900`. Dynamic client registration stays off unless `HDF_AUTH_ALLOW_DCR=true`.
  - `@better-auth/api-key` — **the fallback "when OAuth is not possible"** (a pipeline runner that cannot perform a token request, or an integration that only carries a static header). Organization-owned keys created by the service-owned `POST /api/auth/api-keys` (server-only `auth.api.createApiKey` after the owner check), `keyExpiration: {minExpiresIn, disableCustomExpiresTime}` so expiry is mandatory, `permissions` = a scope subset (never `hdf:admin`), per-key rate limit, hashed at rest. Because better-auth has no key→JWT exchange, the service ships one **better-auth plugin endpoint** (`createAuthEndpoint`, so it has the plugin context `signJWT` needs — measured) at **`/api/auth/api-key/exchange`** (key in the body, never in a query string): `auth.api.verifyApiKey` → `signJWT(ctx, {payload, header: {typ: 'at+jwt'}})` with `sub = 'apikey:<keyId>'`, `client_id = <keyId>`, `org` = the key's `referenceId`, `scope` ⊆ the key's `permissions`, `exp = min(15 min, key.expiresAt)`, `aud` from the same **required** `resource`; rate-limited per IP and per key with better-auth's database-backed rate-limit storage. Both endpoints are the `documentOnly` token operations of ADR-0008 §2. The docs present OAuth first and API keys as the exception.
  - **Revocation**: `POST /api/auth/revoke` (companion document; `hdf:admin`) revokes an OAuth client, an API key, or a single token by `jti`; revoked `jti`s go to a `token_denylist` table consulted by **both** verifiers for every builtin-issued token (an indexed `jti` read with an in-process negative cache of ≤ 60 s), so revoking a key or client takes effect within that interval, not at token expiry (ASVS 7.4.1, AC-7).
  - `bearer` — lets better-auth's own `/api/auth/*` routes accept a session token as a bearer; **the API middleware accepts JWTs only**, never session tokens.
  - `@better-auth/mcp` + `@better-auth/cimd` (`metadataProfile: 'mcp-2026-07-28'`) — the service is the **OAuth 2.1 authorization server for MCP clients** of the Go MCP over HTTP (§6), with `resource: HDF_MCP_RESOURCE_URL` beside the API resource. CIMD is configured with `@better-auth/cimd/node`'s transport wrapped with 64 KB and 5 s caps, plus `isMetadataDocumentUrlAllowed` enforcing HTTPS and public addresses — a planted `https://127.0.0.1` client id rejected before any fetch is a Phase 4 AC.
  - `openAPI` — generates the companion document (§2).
  - Sign-up is **invite-only by default** (`HDF_AUTH_OPEN_SIGNUP=false`), implemented as a `databaseHooks.user.create.before` hook that allows user creation only when a pending, unexpired `invitation` row matches the email — not `emailAndPassword.disableSignUp`, which blocks invited users too (run in the round-6 spike; Phase 4 repeats both cases); `trustedOrigins` is required in `builtin` mode (dev mode defaults it to `HDF_BASE_URL`; better-auth rejects JSON `POST`s without an `Origin` it trusts) and `disableOriginCheck` is refused; `HDF_DEV_SEED=true` is honoured only when `HDF_DB_URL` is `memory://` or `file://` and prints a random owner password once.
  - **Bootstrap**: `hdf-serve bootstrap --email <owner>` is a one-shot command that refuses to run if any user exists, creates the first owner and organization through the server-side API with the invitation hook bypassed by a process-local flag, and prints a one-time invitation URL — the production path where `HDF_DEV_SEED` is forbidden.
  - Schema and migrations: `npx auth generate --adapter drizzle --dialect postgresql --output src/auth/schema.ts` run with a **generation-only config** (no adapter, because plugins' `init` runs at generation) followed by `scripts/strip-relations.mjs` (the emitted `relations` import fails under drizzle-kit rc.4) — both found in the round-6 spike, whose generated and stripped files are retained; both tracked → `drizzle-kit generate` with `drizzle.auth.config.ts` (`out: migrations/auth`) → `migrate(db, {migrationsFolder, migrationsTable: 'hdf_serve_migrations'})` on boot, before `betterAuth()` is constructed. Never `hdf-db-schema`'s ledger, never the Go applier.
- **Token contract** (both issuers): required `iss`, `aud`, `exp`, `iat`, `sub`, `jti`; **`typ: at+jwt` and `client_id` required for every builtin-issued token** (RFC 9068; the user-session `/api/auth/token` path is not an API credential and is rejected by the API middleware); `nbf`/`iat` with ≤ 60 s skew; `alg` allowlist `EdDSA`, `ES256`, `RS256` (never `none`/`HS*`; under `HDF_FIPS=true` the builtin allowlist drops `EdDSA` so a pre-rotation Ed25519 token is refused); the same `typ`/`client_id`/denylist rules are enforced by the Go verifier from the shared description, and the companion routes accept better-auth session tokens only through better-auth's own handling, never through the API middleware; **a token without a resolvable `org` claim is `403 NO_ACTIVE_ORGANIZATION`** — HTTP never constructs a NULL-organization principal (ADR-0010 §2). `org`/`role` are the state at issuance; membership revocation takes effect within the 15-minute lifetime unless revoked (above), documented as accepted.
- **Two resources, per-resource `aud`.** The API (`HDF_BASE_URL`) and the Go MCP over HTTP (§6, `HDF_MCP_RESOURCE_URL`) are distinct RFC 8707 resources, both registered with the provider; the token endpoints issue `aud` per the request's `resource` parameter; the TS middleware's audience is the API URI, the Go verifier's is the MCP URI; a parity fixture proves an API token is rejected by the MCP and vice versa (measured for the audience check). Neither surface ever forwards an inbound token to `hdf-data`, the database, or the embeddings provider.
- **External issuer — verify-only** (`HDF_AUTH_MODE=external`): better-auth is not loaded; the service verifies JWTs from any OIDC issuer — `HDF_AUTH_ISSUER` and `HDF_AUTH_AUDIENCE` **mandatory**, `HDF_AUTH_JWKS_URL` or discovery, `HDF_AUTH_ALGS` (default `EdDSA,ES256,RS256`) — and maps claims: `HDF_AUTH_ORG_CLAIM`, `HDF_AUTH_TEAM_CLAIM`, `HDF_AUTH_ROLES_CLAIM` → the same role→scope table; a direct `scope` claim is honoured only with `HDF_AUTH_TRUST_SCOPE_CLAIM=true`; the docs state that the roles claim must be one the IdP derives from group membership, never a user-editable attribute; lockout, MFA, and revocation are the IdP's in this mode, and the docs say which ASVS controls move there. This is the enterprise-IdP path; the OSS default is `builtin`.
- **One verification contract in both languages**: the token → `Principal` rule (issuer, audience, algorithms, required claims incl. `typ`/`client_id`, skew, denylist lookup, role→scope table) is written once as `src/auth/verifier.json` and read by the TS middleware (`jose`, JWKS refetch throttled to one per minute) and by `hdf-cli/internal/auth` (`go-oidc` `NewRemoteKeySet` over a **rate-limited `http.RoundTripper` passed through `oidc.ClientContext`** — go-oidc has no throttle of its own — + `NewVerifier{ClientID: <resource>, SupportedSigningAlgs: […]}` → `auth.TokenInfo` for the MCP SDK and `hdfdata.Principal` for the store). A shared fixture of signed tokens (keys generated at test time, never committed) drives parity tests: same token, same principal or same rejection, in both languages.
- **Enforcement layering**: (1) `401` `about:blank` with `WWW-Authenticate: Bearer resource_metadata="…", scope="hdf:read"` on a missing or invalid token; (2) route scope check from ADR-0008's `security` requirements — every scope failure is ADR-0008 §3's one `insufficient-scope` 403 with the RFC 6750 header, and a token without an organization is the second convention type, `no-active-organization`, with no challenge header; (3) `Principal` (with the middleware's `requestId` attached) → `hdf-data`, which sets the tenant context (ADR-0010 §3); (4) ADR-0009 §8's generated RLS (permissive `FOR ALL` tenant policy plus the restrictive pinned-role policy) with the `tenant_ctx` flag, as a non-owner runtime role with `FORCE ROW LEVEL SECURITY` — **mandatory in the container default**, optional in dev mode. The entrypoint (`src/entrypoint.ts`) reads the ledger's table list and asserts, from `pg_roles` and `pg_class`: `NOT rolsuper`, `NOT rolbypassrls`, `NOT pg_has_role(current_user, c.relowner, 'MEMBER')` for every table (`MEMBER`, so indirect and `SET ROLE`-reachable memberships count), `relrowsecurity AND relforcerowsecurity` on every owned table, and `current_setting('row_security') = 'on'`, and exits otherwise unless `HDF_ALLOW_OWNER_ROLE=true`. `hdf:admin` is required for delete, revocation, and organization-management routes; there is no cross-tenant read for any scope. Every authentication success and failure, authorization denial, and administrative action is an ADR-0013 audit event.
- **Stdio MCP is unchanged**: no token layer, ambient credentials per the MCP spec, with ADR-0010 §5's pinned-role rule for multi-tenant databases and the `http` backend as the recommended multi-tenant shape.

### 4. Zod and the client
Zod appears in exactly five places, all listed here: generated route schemas (ADR-0008 §7, with the parameter pre-processing resolver); the service configuration object; the better-auth access-control statements; the embedding-provider response schema (ADR-0010 §4); and `hdf-client`'s generated validators. **No hand-written Zod for any HDF document shape**, and no `drizzle-orm/zod` row schema crosses the data-layer boundary (ADR-0009 §10). **`@mitre/hdf-client`** is a second workspace package at the root (`hdf-client/`) generated by one `@hey-api/openapi-ts` configuration in its **job-matrix form** — two inputs, two outputs (`api` from `hdf-api.oas.json`, `auth` from `hdf-auth.oas.json`), never the merged-input form, because both documents define `ProblemDetails` and the bearer scheme and merging renames colliding schemas — with `zod` + `@hey-api/sdk { validator: true }` + the bundled `@hey-api/client-fetch` plugin, so callers get a typed client with two namespaces (`api`, `auth`) whose response validation is the same Zod the server used — with one measured caveat handled here: the generated Zod for HDF roots is lossy, so `createClient` **wraps every document operation to validate request bodies and response documents with `@mitre/hdf-validators`** (ajv 2020), making the client exactly as strict as the server. Because the two token endpoints are `documentOnly` synthetic operations in the document (form-encoded bodies, `security: []`), the client's authentication calls are generated too; its only hand-written code is `createClient({baseUrl, credentials})`, which wires the generated token call into `client-fetch`'s async `auth` hook and **caches the token until `exp − 60 s`** (the hook is invoked per request — seen in the round-6 spike's wire log, which was not retained; Phase 1 asserts it). The service's contract tests are its first consumer. Types-only consumers use `openapi-typescript`/`openapi-fetch` against the published documents and need neither package.

### 5. Dev and test topology, email, environment
- **Dev mode** (`HDF_DB_URL=memory://` or `file://./data` — PGlite's own URL forms): PGlite + `pglite-pgvector` in-process, better-auth on the same instance, both ledgers migrated on boot, a seeded owner and organization with `HDF_DEV_SEED=true`, `HDF_MAIL_MODE=log`. Zero infrastructure; this is the walkthrough in the docs and the CI test target on **ubuntu + windows** (the ADR-0009 Phase 1a `pg` fallback clause applies if PGlite misbehaves on windows). RLS is enforced on PGlite under `SET ROLE` (measured), so the tenant negatives run in dev mode too.
- **Production shape**: `HDF_DB_URL=postgres://…` with `HDF_DB_SSL=verify-full` on `pgvector/pgvector:0.8.6-pg18` (or PGDG `postgresql-18-pgvector`), both ledgers run as the owner role by `hdf-serve migrate`, the service as the non-owner role behind a TLS-terminating proxy; a compose example ships in `examples/`; backup and restore follow ADR-0013 §6.
- **Email**: one `Mailer` interface with two built-in modes — `HDF_MAIL_MODE=log` prints the invitation URL to the log (dev, tests, and the documented air-gapped path where an admin forwards it) and `smtp` sends through `nodemailer` (`HDF_SMTP_URL`, `HDF_MAIL_FROM`); no vendor SDK. Invitation, second-factor setup, and password-reset mails are the only three templates.
- **Additional environment rows** (appended to ADR-0010 §3's table): `HDF_BASE_URL` (required; API resource URI, issuer base), `HDF_BIND` (`127.0.0.1:8080`; `0.0.0.0:8080` in the container), `HDF_TRUSTED_PROXIES` (unset → `X-Forwarded-*` ignored), `HDF_CORS_ORIGINS` (required in `builtin` mode as `trustedOrigins`; dev mode defaults to `HDF_BASE_URL`; CORS headers are emitted only for listed origins), `HDF_AUTH_MODE` (`builtin`), `HDF_AUTH_SECRET` / `_FILE` (required in `builtin`), `HDF_AUTH_OPEN_SIGNUP` (`false`), `HDF_AUTH_ALLOW_DCR` (`false`), `HDF_FIPS` (`false`; `true` selects ES256), `HDF_AUTH_ISSUER`/`_AUDIENCE`/`_JWKS_URL`/`_ALGS`/`_ORG_CLAIM`/`_TEAM_CLAIM`/`_ROLES_CLAIM`/`_TRUST_SCOPE_CLAIM` (external mode; issuer and audience required there), `HDF_MCP_RESOURCE_URL` (unset; required when the Go MCP runs `--transport http` against this issuer, §6), `HDF_MAIL_MODE` (`log`), `HDF_SMTP_URL` / `_FILE`, `HDF_MAIL_FROM` (required in `smtp`), `HDF_MAX_BODY_BYTES` (`52428800`), `HDF_RATE_LIMIT_PER_MINUTE` (`600`), `HDF_ALLOW_OWNER_ROLE` (`false`), `HDF_DEV_SEED` (`false`), `HDF_LOG_LEVEL` (`info`), plus ADR-0013's rows.
- **Tests**: unit on PGlite; contract tests through the client; auth tests in `builtin` mode (invited sign-up → organization → OAuth client via the service route → `client_credentials` with `resource` → authenticated call; API-key exchange path; a client requesting `hdf:admin` refused; a request without `resource` refused; no opaque token ever issued — every token the tests receive is decoded; lockout after ten failures; owner role refused without a second factor; revocation effective within the cache interval) and in `external` mode (a test JWKS server with a runtime-generated Ed25519 key; a token with a self-asserted `scope` claim ignored unless trusted); **tenant-isolation tests through HTTP** (two organizations, every operation, RLS off and on — the negative on every route); the no-organization token → 403; scope tests (member cannot write; a client with `hdf:read` cannot ingest; only `hdf:admin` deletes); `If-Match`/412; 413/415; `<!DOCTYPE`; rate limit with `RateLimit` headers; a declared 500 with no detail; the ADR-0009 canary through the HTTP surface (a planted sentinel never appears in a response body, problem detail, or log); the CIMD loopback plant; the companion document's inventory.

### 6. Go MCP over HTTP with the shared verifier (ADR-0007 amendment, transport card)
The Go MCP server gains `--transport http` (Streamable HTTP) guarded by `auth.RequireBearerToken` with the §3 verifier (audience = `HDF_MCP_RESOURCE_URL`, the throttled JWKS transport, the denylist lookup) and `ProtectedResourceMetadataHandler` pointing at the configured issuer (the `builtin` service or an external one). This puts the local/pipeline MCP and the HTTP service under **one identity**; serving MCP from the TypeScript process (porting nine tools) is deferred (§7). ADR-0007's "Streamable HTTP out of scope" line is amended by this ADR, and the transport card is a prerequisite of Phase 6.

### 7. Deferred, explicitly
MCP served from TypeScript; a web UI; OpenTelemetry tracing (structured logs with redaction and ADR-0013's `/metrics` ship); multi-region or read replicas; SAML; DPoP (RFC 9449). Background jobs, organization lifecycle, webhooks, evidence bytes, quotas, backup, and metrics are ADR-0013's.

## Reviewer challenge points

Will's review — and any agent review he runs — should specifically challenge or verify: (a) **TypeScript/Hono for the service** rather than a Go `hdf serve` reusing the MCP handlers — chosen for the TS-native auth/Zod stack and the hosted-service shape, at the cost of four TS ports in three cards (≈ sp21), a second implementation of the nine operations, a Node container instead of the single binary, and HTTP↔MCP parity tests; (b) **better-auth bundled as the default issuer** with the verify-only external mode; (c) **OAuth `client_credentials` as the default machine path with API keys as the documented exception**, both through service-owned creation routes because the public endpoints drop the scope ceiling, and a service-owned exchange endpoint; (d) **a container image as a release artifact** and the workflow change it needs; (e) **service-owned auth migrations** in the same database under a separate ledger table, with the generation quirks the spike found scripted rather than hand-fixed; (f) **Go MCP HTTP transport via the shared verifier** with two resource URIs and per-resource `aud`; (g) **scope derivation from organization role** (one tracked table) rather than per-user scopes; (h) **RLS mandatory in the container default** with the entrypoint role checks; (i) **`403 NO_ACTIVE_ORGANIZATION`** for tokens without an organization; (j) the **Node 24 floor** applied repo-wide; (k) the **companion auth document** generated by better-auth rather than merged into ADR-0008's; (l) the **hardening set** — required MFA for owner/admin, lockout, `jti` revocation with a ≤ 60 s window, ES256 under `HDF_FIPS`, `typ`/`client_id` required — as v1 scope rather than follow-ons; (m) **one issuer string** enforced at issuance (with the allowlist fallback) rather than a two-issuer verifier.

## Alternatives Considered

### A. Go `hdf serve` in the existing binary
Pros: reuses the nine Go handlers, one binary, no ports, no parity tests, no Node runtime. Cons: better-auth becomes a separate TS process; Zod is client-only; Go validates against the document with `libopenapi-validator` and the organization/session stack has no Go equivalent to better-auth's plugins. Why rejected: right for a pipeline tool, wrong for a multi-tenant hosted service — challenge (a).

### B. Fastify 5 + `fastify-type-provider-zod`
Pros: mature, fast. Cons: ajv on draft-07 by default so 2020-12 needs custom wiring; the Zod provider is equally Zod-first; better-auth's Fastify integration is a generic Node handler. Why rejected: no advantage over Hono for this contract.

### C. Express + `express-openapi-validator`
Pros: validates requests directly against the ADR-0008 document. Cons: no typed handlers; Express 5 ecosystem lag. Why rejected: loses the Zod typing; ADR-0008's projection P gives the same guarantee with types (measured), and Alternative K there is the fallback.

### D. oRPC with the Hey API `orpc` plugin
Pros: contract-first with Zod typing. Cons: young; the plugin's handling of 2020-12 features is unverified; a second RPC layer beside plain HTTP. Why rejected for v1: revisit if P proves brittle.

### E. Verify-only auth, no bundled issuer
Pros: smallest surface, no auth tables. Cons: no dev login, no organizations or OAuth clients out of the box, no MCP authorization server; every deployer must bring an IdP. Why rejected as the default, kept as `external` mode — challenge (b).

### F. External IdP only (Keycloak/Zitadel/Ory as a hard requirement)
Why rejected: heavy for the local and small-team case; supported through `external` mode.

### G. Serve MCP from TypeScript now
Why rejected: ports nine tools before any HTTP consumer exists; the Go MCP with the shared verifier covers HTTP transport — challenge (f).

### H. API keys only, via better-auth's session mocking
Why rejected: session mocking works only for user-owned keys and is not recommended for production; organization-owned keys have no built-in exchange. OAuth clients are the standard machine path; API keys stay as the exception with a service-owned endpoint — challenge (c).

### I. One resource URI for API and MCP
Why rejected: the MCP specification requires each server to accept only tokens for its own resource; per-resource `aud` costs one parameter — challenge (f).

### J. Merge organization and client management into ADR-0008's document
Why rejected: those endpoints are better-auth's and have no MCP derivation; better-auth's own generator describes them (ADR-0008 Alternative L) — challenge (k).

### K. Defer MFA, lockout, and revocation to a later ADR
Pros: smaller v1. Cons: ASVS V6/V7 and NIST AC-7/IA-2(1) name these as baseline controls for a system holding assessment data, and better-auth ships the primitives. Why rejected: they are configuration and one table, not a subsystem — challenge (l).

## Consequences

Easier: one service process with auth, API, Zod, and the data layer in one type system; PGlite dev mode with no infrastructure, including RLS; the client SDK is a build artifact with two namespaces; pipelines get standard OAuth clients; MCP clients get a standards-compliant authorization server; the same tenant predicate and RLS protect HTTP and MCP; the four ports close long-standing TS/Go parity gaps in the libraries; the load-bearing auth and contract claims are spike-verified before any card is cut.

Harder: four TS ports before the write operations exist; a second implementation of the nine operations; a Node container in the release workflow; two Drizzle ledgers in one database with a scripted generation step; better-auth's release cadence becomes a dependency; the Go verifier and the TS middleware must stay in parity; two resource URIs to configure; a companion document to keep in inventory; MFA and lockout to support; the Windows CI job covers dev mode only (real PostgreSQL follows ADR-0009 §9); a repo-wide Node 24 floor.

Risks and mitigations: projection P cannot be made to hold on the real document → measured on a representative sample, Phase 1's first AC on the real one, Alternative K of ADR-0008 recorded; better-auth plugin drift (the 1.7 `oidcProvider` removal, the CLI rename, the dropped scope ceiling) → exact-pinned with a smoke test of every used endpoint and `minimumReleaseAge` in pnpm; the issuer setting is refused by a plugin → the allowlist fallback; token verification differs between `jose` and `go-oidc` → the shared fixture and parity test, both verifiers measured; RLS bypass by a mis-provisioned role → the entrypoint checks; OAuth-client or API-key leakage → secrets hashed at rest, expiry mandatory, `hdf:admin` never grantable to machines, exchange endpoint rate-limited, revocation within 60 s; CIMD/SSRF → the guarded transport with a planted test; content in logs → redaction on the logger plus the canary; supply chain → image digest-pinned, signed with cosign, SBOM attached, scanned in the release workflow.

### Verification Strategy
The parity test (P plus the inventory/security assertion, and the companion document's inventory) and the contract suite through the generated client are the spine; auth and tenancy negatives run on every route in both modes; token parity runs in both languages with the cross-resource fixture; the round-6 spike scripts are promoted into the Phase 1 and Phase 4 suites rather than rewritten. Live test before close: run the container against the compose database, bootstrap the first owner, enrol a second factor, create an organization and an OAuth client, obtain a token with `client_credentials` and `resource`, ingest a real fixture with the client, query it, attempt the same read with a second organization's client and receive 404, revoke the client and see 401 within a minute, delete the document as an owner and read the audit rows — outputs pasted in card notes.
