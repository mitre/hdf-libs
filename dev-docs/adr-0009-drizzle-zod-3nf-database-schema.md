## Context

HDF documents are JSON artifacts. Consumers that need to persist, index, and query them relationally — the `hdf db` workflow in the CLI and the DB-backed mode of the HDF MCP server (both through the data access layer of ADR-0010), the `hdf-serve` HTTP service (ADR-0011), ecosystem services building assessment stores, partner tooling — each invent tables today, or store whole documents as blobs and give up cross-document querying.

The motivating queries are about **adjudication reuse**:

1. **Carry-forward** — a new scan arrives; which of its findings were already adjudicated (waived, false-positive, risk-adjusted) by a prior scan's overrides or a standing amendments document for the same target?
2. **Similar-system precedent** — how did other systems applying the same baseline, with the same component kinds, adjudicate this control?
3. **Package scoping** — run either query scoped to one evidence package (an authorization context) or across packages within the caller's tenant.
4. **Similarity** — when exact keys do not match (a renamed baseline, a different benchmark for the same control family, free-text justifications), which prior adjudications and which systems are *semantically* nearest to this finding? This is a nearest-neighbour query over stored embeddings, additive to the three join queries, never a substitute for them.

Queries 1–3 are the acceptance spine: the relational shape is right only if each is a join, and each is a test with negatives. Query 4 is proven the same way (a test with negatives) but ranks rather than matches, so it is never used to *apply* an adjudication — only to suggest one for a human or agent to confirm.

The MCP server is a first-party consumer on both sides (it drafts amendments today and cannot see across documents), and it is **Go**, as is the CLI. The HTTP service (ADR-0011) is **TypeScript**. This package is therefore dual-language from the start, following the repo's engine norm (shared-fixture cross-language parity, ADR-0007), and is consumed only through the data access layer of ADR-0010 — nothing outside that layer imports its tables.

**One store, not two.** Relational rows and vectors live in the same PostgreSQL-flavoured engine: PGlite in-process for TypeScript dev/test and embedded consumers, PostgreSQL with the `pgvector` extension for deployments and Go tests. A separate vector database is rejected (Alternative K): it would be a second store with its own tenancy model and no PGlite equivalent, and the similarity query joins straight back into the relational rows.

Realities the reviews established, which the schema is built around rather than assumed away:

- **Identity is not carried by the schema.** `Evaluated_Requirement` has no component reference; attribution exists only at baseline level via the `labels.component` convention and `hdf-system` target selectors — but `Standalone_Override.componentRef` and `inheritedFrom` exist (no shipped code honors them). `(requirement id, baseline name)` is not unique even within one document (a real fixture carries `SV-257777` twice in one baseline). `componentId` appears in 0 of 116 results fixtures, `systemRef` in 0 of 116 and in neither amendments fixture — real results reach a system only through evidence-package membership. `systemId` is optional (the two real OSCAL-derived system documents carry `identifier` + `identifierScheme` instead). "Baseline identity" spans three unrelated spaces (`Evaluated_Baseline.name`, system `baselineRefs`, plan `baselineRef` URI-references) and the corpus contains only exact-name matches. ADR-0005's change-event key is a different triple (`systemRef`, `componentId`, `requirementId`). `hdf amend apply` matches overrides on `requirementId` across all baselines unless `baselineRef` is set (exact name; absent means any baseline), ignores `componentRef`, and appends a copy of each applied standalone override into `statusOverrides` with no origin id.
- **Types the schema keeps distinct must stay distinct.** Inline `Status_Override` and standalone amendments overrides have *conflicting* validity rules. Inline `POAM` and `Standalone_Override{type: poam}` differ. `Checksum` ≠ `Integrity`. Five reference definitions exist; the schema's own `$comment` on `External_Evidence_Reference` says "Do not merge these". Root `labels` on amendments/system/evidence-package/plan is an unconstrained object; component and baseline `labels` are string maps. `tags` is arbitrary JSON and required. `Base_Component` has 13 kinds and is `additionalProperties: true`. Comparison `before`/`after` are full requirement snapshots; change-event `before` is an `Effective_Projection`, `after` a full requirement.
- **The validators do not enforce `unevaluatedProperties`** (draft-07 engines in both languages). Real fixtures carry root keys no schema defines (`targets`; the bundle results carry `platform`, `version`), and `hdf amend apply` writes a root-level `previousChecksum` onto results — and its verifier reads a root-level `previousChecksum` off the *amendments* document — neither location declared by any root schema. "Schema-valid" today means the validators' verdict, not conformance to the schema text.
- **Byte-hash integrity cannot survive re-serialization.** The shipped chain verifier hashes the *entire prior results document's bytes*; per-override `previousChecksum` has a producer (`hdf amend create`: sha256 of Go `json.Marshal` of the override) but no verifier. Signatures and evidence `Content_Reference.checksum` hash bytes. Canonical timestamp parsing truncates to milliseconds and converts offsets to UTC; 1,294 corpus `startTime` values carry microsecond precision.
- **Enums**: 44 `enum` sites, one a gating enum inside an `if`; `@mitre/hdf-schema` ships 41 generated runtime `enum` objects covering every closed enum (named and inline); the two open enums (`Bom_Type`, `External_Evidence_Format`) accept `x-` values; `Cloud_Provider` is nullable. HDF documents do **not** self-describe their schema version.
- **The fixture corpus is thin**: `hdf-fixtures` holds two results, one baseline, two amendments. The only real system/plan/evidence documents form one relative-URI *bundle* in `hdf-cli` testdata — whose `plan.json` carries an absolute machine-local `systemRef` pinned by the bundle's checksums. Two real system documents exist as `oscal-to-hdf` expected outputs. The only real scan × adjudication overlap is a converter-local twistlock output × `multi-cve-amendments.json` (CVE-2021-44228/45046/45105), and neither carries a `systemRef` or sits in a package.
- **Drizzle facts** (verified 2026-09-01): `drizzle-orm@latest` is 0.45.2; 1.0 is `1.0.0-rc.4` (rc; no GA). Only 1.x has `./zod` and the per-folder `migration.sql` + `snapshot.json` layout (`snapshot.json` is `version: '8'`, a flat `ddl` entity list, undocumented and without a stability promise). drizzle-kit has no down migrations. The 1.x migrator matches applied migrations by folder **`name`** (hash and `created_at` are recorded but not used); `hash` = sha256 of the byte-identical `migration.sql`; `created_at` = millis from the folder-name timestamp; `applied_at` defaults in the DB. A programmatic `migrate(migrations: MigrationMeta[], db, config)` exists in `drizzle-orm/pg-core` for non-filesystem consumers.
- **Runtime facts**: `@electric-sql/pglite@0.5.8` embeds **Postgres 18.3**. Go cannot embed PGlite in-process (WASI build and `libpglite` are draft/do-not-use; community Go ports are non-functional) but can connect via the official `pglite-socket` server (dev-only, no SSL, one multiplexed connection, pinned in lockstep to PGlite; the extension flag must name the package *and* export — `-e "@electric-sql/pglite-pgvector:vector"` — because the package name and the export differ). `embedded-postgres` v1.34 (Go) **cannot load `pgvector`**: its maintainer closed the request (issue #163, 2026-03-03) as needing upstream zonky binaries that only optionally add PostGIS, on Linux only; an undocumented copy-in of `vector.so` is the only path. GitHub-hosted **Windows runners cannot run Linux containers** (service or job containers require a Linux runner). This repo's CI matrix is ubuntu + windows; PGlite's own CI runs Ubuntu only. The release workflow stamps every workspace package with the repo tag and only `next`-tags `hdf-converters`.
- **Vector facts** (verified 2026-09-02): `pgvector` 0.8.6 (2026-07-29) supports Postgres 13+, PG18 since 0.8.1; official image `pgvector/pgvector:0.8.6-pg18`. PGlite ships pgvector as the separate package **`@electric-sql/pglite-pgvector` 0.0.9** (exact peer on `pglite` 0.5.8; bundles pgvector **0.8.1** with `halfvec`/`sparsevec`); the former `@electric-sql/pglite/vector` subpath no longer exists in 0.5.8. Extensions are fixed at PGlite instance construction (`new PGlite({ extensions: { vector } })`). Drizzle's `pg-core` has `vector({dimensions})`, `halfvec`, `sparsevec`, `bit`, the distance helpers (`cosineDistance`, `l2Distance`, `innerProduct`, …) and `index().using('hnsw', col.op('vector_cosine_ops'))`, identical on 0.4x and 1.0 rc; **drizzle-kit never emits `CREATE EXTENSION`** (custom migration), and its `pglite` driver constructs `new PGlite(url)` with no `extensions`, so `drizzle-kit migrate`/`push` cannot run the extension migration on PGlite — only the programmatic migrator against an instance built with the extension can. pgvector indexes require a fixed dimension; a **dimensionless `vector` column can be indexed through a typed cast expression** (`USING hnsw ((embedding::halfvec(N)) halfvec_cosine_ops)`), partial indexes (`WHERE …`) are supported, and index caps are 2,000 dims for `vector`, 4,000 for `halfvec`. `github.com/pgvector/pgvector-go` v0.4.1 registers `vector`/`halfvec`/`sparsevec` codecs on pgx v5 (`pgxvec.RegisterTypes` in `AfterConnect`; the `pgvector-go/pgx` package is a separate Go module). `testcontainers-go`'s postgres module v0.44.0 documents the pgvector image.
- **Spike facts** (round 6, 2026-09-02 — run, not read; scripts retained as the seed of the Phase 1c/4b tests): on PGlite 0.5.8 the partial expression HNSW index **builds and is chosen by the planner** at 20k rows (a 100-row table is cheaper to scan); `CREATE ROLE` + `SET ROLE` work on PGlite and **RLS is enforced there for a non-superuser role** (permissive `FOR ALL … WITH CHECK` and restrictive policies alike), so policy logic is testable on PGlite and only a separate login role needs real PostgreSQL; the `SECURITY DEFINER` registration function runs as a non-owner role on both engines and `REVOKE … FROM PUBLIC` is effective; the dims and owner-check triggers catch the NULL case; the ledger claims hold exactly — `drizzle-kit generate --custom --name extension` yields a 14-digit-prefixed folder, a hand-named `0000_extension` fails the ledger insert with `NaN`, `drizzle-kit migrate --driver pglite` fails on the extension folder, two ledger tables coexist, and a Go applier reproduces drizzle rc.4's `hash`/`created_at` byte-for-byte. **Corrections the spikes forced**: Drizzle's `vector()` column builder **requires `dimensions`** (it emits `vector(undefined)` without one), so the dimensionless column is a `customType({ dataType: () => 'vector' })`; a pgx pool whose `AfterConnect` registers pgvector types **fails to connect before the extension exists**, so the migration pool must not register them; the generated index name is 48 characters (`embeddings_hnsw_` + 32 hex); through pgx prepared statements a **bound** `model_id` is planned with the partial index for the first five executions and then switches to a generic plan that cannot match the partial predicate — driver-level `EXPLAIN` never shows this, so the acceptance test must count index scans (`pg_stat_user_indexes.idx_scan`) across eight executions rather than read a plan; `set_config(name, NULL, true)` and `''` behave identically for a custom setting; session-level `set_config(…, false)` leaks across statements in a test, so every tenant setting is `is_local = true`. `CREATE INDEX CONCURRENTLY` cannot run inside a function or transaction, so the in-function build blocks writes for its duration (875 ms at 20k rows measured).

## Decision

### 1. Package, languages, layering
Create **`@mitre/hdf-db-schema`** (TypeScript: Drizzle `pg` tables, `drizzle-orm/zod` row schemas, pure `disassemble`/`assemble`, transactional `importDocument`/`exportDocument` as the primary API) and its Go module **`github.com/mitre/hdf-libs/hdf-db-schema/go`** — **no `/v3` suffix while the npm package is `0.x`** (a `v3` module path would require tags ≥ 3.0.0; the suffix is added when the package leaves `0.x`, the one deliberate departure from the sibling modules' path convention). Go row structs are **generated at build from drizzle-kit's `snapshot.json`** by a small generator that asserts `version === '8'` and fails loudly otherwise (drizzle-kit exact-pinned); column parity is tested. Import/export runs against `pgx` with `pgvector-go` codecs registered; migrations are applied from an embedded copy. **One engine**: the package targets PostgreSQL ≥ 18 with the `pgvector` extension as its only extension, and the same migrations run on PGlite (with `@electric-sql/pglite-pgvector`) and on PostgreSQL — no engine-conditional SQL. Every phase delivers both languages with a shared-fixture parity test in the same commits. The module joins `go.work`, `hdf-cli`'s `replace` set, and the release workflow's `GO_MODULES`; the package ships a `test:go` script so the Windows matrix runs its Go tests. Layering: beside `hdf-engine` (depends on `hdf-schema`, `hdf-utilities`, `hdf-validators`, `hdf-fixtures` in tests); `hdf-utilities` gains no dependency. Packaging follows ADR-0008 §6.

### 2. Scope: core-first, all eight types committed, checkably
**v1 (core)** models `hdf-results`, `hdf-amendments`, `hdf-system`, `hdf-evidence-package`, and `hdf-baseline` in full 3NF. **Phase 7 of this ADR** adds `hdf-plan`, `hdf-comparison`, and `hdf-requirement-change-event`. Honest rationale: the exemplars need exactly the core set; comparison and change-event have no real corpus and carry snapshots needing a distinct model (`jsonb` + optional FK); a change-event table re-opens ADR-0005's external-reconciler decision. **Plan has a real corpus** (the promoted bundle) and is deferred for sequencing only — pulling it into core is cheap and is reviewer challenge (a). Mechanisms that keep the deferral honest: the package stays **`0.x` until all eight types round-trip** (independent of the `next` dist-tag, which lifts at Drizzle GA — the package may be `1.0` under `next` or `0.x` under `latest`); `documents` accepts all eight `doc_type`s from Phase 1a (bytes, hash, `validated_against`, `disassembled = false` for non-core types) and root-level **reference extraction runs for all eight regardless of `disassembled`**, so package membership and reference resolution work; `importDocument` on a non-core type returns `UNSUPPORTED_DOC_TYPE` for disassembly, asserted by a test; Phase 7 is sized with Files and a Verification command.

### 3. Identity model — from the schema outward
- Surrogate `uuid` primary keys; `ordinal` on every array child; uniqueness is `(parent_row_id, ordinal)`.
- **Requirement identity**: non-unique index on `(requirement_id, baseline_name)`; natural fields verbatim.
- **Attribution is derived, never document truth**: `baseline_component_attribution(baseline_row_id, component_row_id, method ∈ {labels.component, targetSelector, singleComponent, none})`, populated at import, never emitted by `assemble()`. `overrides.component_ref` is the natural column the schema provides; the carry-forward predicate honors it when present, and a component-scoped override can never match a target that has no `component_id` (schema-correct; stated, with a negative test). The ADR records that `hdf amend apply` currently ignores `componentRef`.
- **Component identity**: `components.component_id uuid NULL`; derived identity by `componentId` → system `targetSelector` over labels → `hostname`/`fqdn`/`name`, recorded in `component_identity_method`; never in a unique constraint. Intra-system references (`providedBy`, `inheritedBy`, data-flow endpoints) are validated at import into `unresolved_refs`, not FKs.
- **System identity**: `system_key` by `systemId` → `identifier` + `identifierScheme` → `name`, recorded with method; a derived `document_system_link(document_id, system_row_id, method ∈ {systemRef, packageMembership, manual})` gives every results/amendments document its system — for the real corpus that path is package membership (or `manual` for the standalone exemplar pair).
- **Baseline identity**: natural key `(name, version?)`; `baseline_aliases(alias, alias_kind ∈ {name, path, uri}, canonical_key, version)` populated by exact name plus an optional **curated alias input** — no fuzzy matching. A standalone override with **no `baselineRef` matches any baseline** (the `hdf amend apply` semantic), and the alias join must not drop such rows.
- **Document references**: `systemRef`, `planRef`, `Content_Reference.uri`, `derivation.seed.uri` are relative (or, in one real fixture, absolute machine-local) paths, not ids; `document_refs(from_document_id, field, raw_ref, resolved_document_id NULL, method ∈ {checksum, uriAtImport, manual}, algorithm)` resolves them — `checksum` resolution for sha256 uses `documents.source_sha256`; other `Hash_Algorithm`s compute from `source_bytes` and are unavailable when retention is disabled; unresolvable refs keep `raw_ref` with `resolved_document_id NULL`. `importDocument` takes an explicit import context (base directory / resolver).
- **Owner vs reference FKs**: every table that references two documents' rows (`document_refs`, `document_system_link`, `baseline_component_attribution`, `package_members`) declares exactly **one owner FK** (the importing side); all other FKs are **reference FKs** whose resolution at import is restricted to rows whose owning document's `organization_id IS NOT DISTINCT FROM` the importing document's. The ownership walker and RLS generator follow only owner FKs.
- **Adjudication provenance**: because `hdf amend apply` copies standalone overrides inline without an origin id, the exemplar spec dedups on `(type, requirement_id, applied_at, appliedBy.type, appliedBy.identifier)`, preferring the standalone row; `overrides.origin_override_id` is nullable, populated when the apply tool records provenance.
- **Reconciliation with ADR-0005**: results and amendments rows carry the baseline-qualified identity **and** a derived projection onto `(systemRef, componentId, requirementId)`; the mismatch is documented.
- All derived identity columns are nullable, indexed, and invisible to round-trip output.

### 4. Entity inventory — from the `$defs` graph
Phase 1a enumerates shared primitives from the `$defs` graph. Principles: one physical `overrides` table with `carrier ∈ {inline, standalone}` and carrier-conditioned CHECKs; `poams` (inline) separate from `overrides{type: poam}`; `checksums` separate from `integrity`; five reference tables, `Reference.ref` as `jsonb`; `labels` as EAV where the schema is a string map and `jsonb` for the unconstrained root form; `tags` as `jsonb` (GIN) plus a derived, rebuild-only `requirement_tag_values` projection for `nist`/`cci`; `components` once, 13 kinds via per-kind detail tables plus `extra jsonb` and an exactly-one-detail-row check; `boms` normalized per ADR-0001 (only `boms[].document` passthrough) with a polymorphic subject; `derivation` in core; snapshots as `jsonb` + optional FK in Phase 7; dead `target`/`platform` primitives not modeled; `identities` deduplicated on `(type, identifier, description)` **within one owning document only**. Families: identities/checksums/integrity/references; overrides/poams/evidence/milestones/signatures/verification_methods; cvss/epss/kev/affected_packages/remediation; inputs/supported_platforms/dependencies/generator/tool; components/boms; labels/descriptions. **Owned tables are created together with their parent** (results-scoped primitives in Phases 2a–2c, amendments-scoped in 3, system-scoped in 4); the Phase 1b family cards deliver the shared column builders, Zod fragments, CHECK expressions, and tenant-free reference-data tables, so the ownership walker is green at every phase.

### 5. Lossless round-trip contract — concrete rules
`assemble(disassemble(doc))` is deep-equal to `canonicalize(doc)` **and** conforms to the schema text, over an enumerated corpus per type. Canonicalization is the stated lossy step: timestamps parsed by schema path with the repo's `parseTimestamp`/`hdfutil.ParseTimestamp` (**truncated to milliseconds**, offsets to UTC; never a regex sweep; never inside passthrough `jsonb`), Go decoding with `UseNumber`, both languages compared on canonical forms. Rules: `ordinal` on every array; **tri-state presence** via a `presence jsonb` column per parent row recording empty-present optional collections and explicit-null fields; `double precision` for scores/impacts, `bigint` for large counts, `date` for the three `format: date` fields, `timestamptz` for instants; NUL bytes (`\u0000`, legal in scanner output, rejected by Postgres text **and** `jsonb`) escaped by a documented reversible token in both scopes, both directions, with a planted fixture; `jsonb` passthrough is value-lossless only after canonical parse; `extra jsonb` overflow on every `additionalProperties: true` object; unions kept `jsonb` unless a variant column is lossless; TS `assemble` builds objects prototype-free (`Object.create(null)`) with a planted `__proto__` key. **Documents are immutable after import** (an `UPDATE` on an owned table is rejected by trigger and test); replacement is a new import. The only exception is the class of **derived, rebuild-only tables** (`requirement_tag_values`, `baseline_component_attribution`, `document_system_link`, `embeddings`): they are never round-trip output, and a rebuild is a `DELETE` + `INSERT` for one owning document inside one transaction — still never an `UPDATE`. The trigger is installed in Phase 1a (before the first derived table exists) and Phase 1c plants an `UPDATE` on a derived table.

**Deletion** is the one destructive operation and is defined here because the FKs are. `deleteDocument(id)` (surfaced by ADR-0010 and ADR-0008) runs in one transaction that sets `hdf.deleting_document = <id>`; **owner FKs are `ON DELETE CASCADE`** (every owned row, including derived tables and `embeddings`, goes with its document); **reference FKs are `ON DELETE RESTRICT`** (`document_refs.resolved_document_id`, `document_system_link.system_row_id`, `package_members`' member reference, `baseline_component_attribution`'s component reference) — a document that another document's package, link, or attribution cites cannot be deleted until the citing document is, and the error names the citing document only when it is in the caller's tenant (otherwise the uniform not-found). The `UPDATE` rejection has one enumerated exception: the **operational columns** on `documents` — `stale_schema` (§12) and `hold` (ADR-0013 §3) — which the trigger permits by asserting `OLD.* IS NOT DISTINCT FROM NEW.*` for every other column; both are invisible to round-trip output. The immutability trigger blocks any child-row `DELETE` whose transaction has not set `hdf.deleting_document` to the child's owning document, so partial deletes are impossible by accident; the same flag is set by the rebuild transaction of a derived table and by `reprojectDocument` (§12), and the guard is a **bug guard, not a privilege boundary** (a caller that can set the flag can delete a child row — the privilege boundary is the runtime role's grants and RLS). Two PostgreSQL facts the design relies on: referential actions run as ordinary `DELETE`s on the referencing table, so child-table triggers fire during a cascade and can read the flag; and **referential-integrity checks bypass row security**, so a non-owner runtime role's `DELETE FROM documents` cascades correctly, and the RESTRICT check also sees citing rows of other tenants — harmless, because §3 restricts reference resolution to the same organization, and because the RESTRICT error's `DETAIL` is stripped and the layer re-queries `document_refs` in-tenant to name the citer. Deleting a results document that a later results document's chain cites leaves the successor's chain verification reporting the prior as absent (`NOT_RETAINED`), which is the truth. Planted tests: partial child delete rejected; delete of a cited document rejected with RESTRICT; cascade leaves zero rows for the id in every owned table.

**Strictness and legacy keys.** `disassemble` is **strict** — unknown keys outside `additionalProperties: true` scopes are rejected — except an **enumerated, versioned legacy-key list** (`targets`, `platform`, `version` at the results root; root `previousChecksum` on results and amendments) quarantined into `documents.extra` with provenance and claimed by the coverage test. The list is permanent import policy for documents produced by older tools. Two prerequisite cards fix the root causes: the validators move to 2020-12 engines in both languages, and `hdf amend apply`/`verify` record and read the chain digest at a schema-defined location (schema-ADR-sized if a field is needed). "Newer-minor" detection is exactly strict-disassemble unknown-key rejection, with `documents.validated_against` as provenance. A **schema-path coverage test** asserts every property path is claimed by a column, a `jsonb` scope, or the legacy list, and a **`$id` version-pin test** fails on a bump.

### 6. Integrity semantics
Stored `integrity`, `checksum`, `signature`, and `previousChecksum` values are preserved **verbatim, never recomputed**. `documents.source_sha256` records the ingested bytes; `documents.source_bytes` (`bytea`) is retained **by default** (disable per import) and obeys the same tenancy predicates as its document. The document-level chain verifies **only via `source_bytes` of the prior results document**; the per-override chain has a producer but no verifier and is out of scope until the schema specifies the hash input. `exportDocument` returns `{form: 'original' | 'assembled', verifiable: [...]}`; `require: 'original'` errors rather than silently falling back. Row-level tamper-evidence is out of scope. Rows are the value-level truth for querying; bytes are canonical for byte-level verification and export (reviewer challenge (c)).

### 7. Enums and versions
Every **closed** enum — named or inline — consumes the corresponding generated runtime enum from `@mitre/hdf-schema` (41 objects); a build-time walker handles only the two **open** enums with `CHECK (value IN (...) OR value ~ '^x-[a-z0-9]+(-[a-z0-9]+)*$')`. Closed → `text` + `CHECK IN (...)`; nullable → nullable column. The walker asserts the arithmetic **44 sites − 1 gating = 43 = 41 generated + 2 open**. Native `pg` enums are rejected for removability and transactional DDL; adding a value still requires a migration.

### 8. Tenancy seam — kept, with the leak analysis applied
One anchor: **`documents`** carries nullable, indexed `organization_id`, `team_id`, `created_by` (`text`; the first two follow better-auth's organization plugin names; `createdBy` is this package's convention). `systems` and `evidence_packages` are owned rows with a NOT NULL FK to their document and no tenancy columns. No auth tables, no FKs into auth. Rules: every table is **owned** (a NOT NULL owner-FK chain to exactly one `documents` row), **reference data** (tenant-free), or — the class ADR-0013 adds — **organization-anchored** (tenancy columns directly on the row, no `documents` FK, the same generated tenant predicate, excluded from every cascade; today `audit_events`, `blobs`, `outbox`, `webhook_subscriptions`, `organization_quotas`, `jobs_meta`); the walker knows all three and fails on anything else; tenant-bearing primitives are never deduplicated across documents; the ownership walker fails on any tenant-bearing table without a single owner path and on a cross-tenant reference resolution (planted); `NULL` organization means **unowned, never global**; the application predicate is `organization_id IS NOT DISTINCT FROM $1`, so a NULL caller sees only unowned rows (negative test on every exemplar) — and a NULL caller is **constructible only by local paths** (CLI, stdio), never from HTTP (ADR-0011 §3); `team_id` is an optional sub-scope that never widens; tenancy is **never derived from document content** — `importDocument` takes an explicit ownership argument; "across packages" means within the caller's tenant. **Idempotent import** rests on a constraint, not a check: `UNIQUE (organization_id, team_id, source_sha256) NULLS NOT DISTINCT` on `documents` (a table constraint, PostgreSQL 15+), so identical bytes in one tenant scope are one row and concurrent imports cannot race; team scope is part of identity, so the same bytes may exist once per team and once organization-wide; retention (`source_bytes`) is fixed at first import for that key, since a later import cannot `UPDATE` the row. RLS ships as an **optional migration generated from the ownership walker**: for every owned table, one **permissive** policy `FOR ALL … USING (<tenant predicate>) WITH CHECK (<tenant predicate>)` — `FOR ALL` and an explicit `WITH CHECK` so a generator can never leave `INSERT`/`DELETE` unpoliced — plus one **restrictive** policy `hdf_role_pin` for the pinned-role deployments below. The tenant predicate **requires an explicit context flag** so an unset context denies rather than grants: `(SELECT current_setting('hdf.tenant_ctx', true)) = '1' AND organization_id IS NOT DISTINCT FROM NULLIF((SELECT current_setting('hdf.organization_id', true)), '')::uuid AND (NULLIF((SELECT current_setting('hdf.team_id', true)), '') IS NULL OR team_id IS NOT DISTINCT FROM NULLIF((SELECT current_setting('hdf.team_id', true)), '')::uuid)` — the `(SELECT …)` form so the planner evaluates each setting once per statement rather than per row; `NULLIF` because an unset setting, a rolled-back one, and an empty string are indistinguishable otherwise; the caller passes `''` for an absent organization or team via `pg_catalog.set_config(…, true)` (transaction-local — the only form that survives connection poolers in transaction mode); a planted raw query outside the tenant wrapper returns zero rows under RLS. **Pinned database roles** (the only multi-tenant story for callers whose organization is self-asserted, ADR-0010 §5): the reference table `hdf_tenant_roles(role_name, organization_id)` (SELECT-only for runtime roles) and the restrictive policy `AS RESTRICTIVE USING (NOT EXISTS (SELECT 1 FROM hdf_tenant_roles r WHERE r.role_name = current_user) OR EXISTS (SELECT 1 FROM hdf_tenant_roles r WHERE r.role_name = current_user AND r.organization_id = NULLIF(current_setting('hdf.organization_id', true), '')::uuid))` — restrictive, never a second permissive policy, because permissive policies combine with `OR` and would widen access; planted test: a pinned role with a mismatched context sees zero rows. Tested as a non-owner role under `FORCE ROW LEVEL SECURITY` **on both engines** — on PGlite via `CREATE ROLE` + `SET ROLE` (enforced; measured), on PostgreSQL additionally as a separate login role — and documented as migrations-run-as-owner / runtime-as-non-owner. Driver errors are wrapped to strip `DETAIL`/`HINT`; query-parameter logging is asserted off; a canary test plants a sentinel value and asserts it never appears in any error or log in either language. The tenant context is set by the caller — ADR-0010's data layer opens the transaction and calls `set_config('hdf.tenant_ctx', '1', true)`, `set_config('hdf.organization_id', …, true)`, `set_config('hdf.team_id', …, true)` from the principal it was handed (ADR-0011 §3 derives that principal from the token); this package only defines the setting names and the policies.

### 9. Migrations, drivers, dependencies
Drizzle **1.0.0-rc.4** (rc; GA not released as of 2026-09-01): peer `drizzle-orm >=1.0.0-rc.4 <2`, `zod ^3.25 || ^4` (zod-v4 API), `@electric-sql/pglite` + `@electric-sql/pglite-pgvector` (lockstep, exact) and `pg` optional peers, `drizzle-kit` dev-only and exact-pinned (test-asserted). Go: `github.com/pgvector/pgvector-go` v0.4.x. The package publishes under the **`next` dist-tag** until GA — which requires the release workflow to gain a per-package dist-tag policy and to exclude this package from the tag-version stamp while it is `0.x` (Phase 6). Migrations are forward-only from drizzle-kit; **reversibility is a package convention** — hand-authored `down.sql` per folder, tested up/down. The migrations directory is in `files`, its path exported as a constant, and a `./migrations` subpath exports drizzle's **`MigrationMeta[]`** (`{name, sql: string[] split on statement-breakpoint, folderMillis, hash, bps: true}`) so non-filesystem consumers call `migrate()` from `drizzle-orm/pg-core` and land in the same ledger. The build syncs `migration.sql`/`down.sql` byte-for-byte into `go/migrations/` (embed.FS; drift test); `.gitattributes` pins `eol=lf` on both trees. **Ledger parity**: the Go applier writes drizzle-compatible rows — `drizzle.__drizzle_migrations` with the same `name`, `hash` (sha256 of the byte-identical file), and `created_at` (folder millis), leaving `applied_at` to the DB default — and a test proves a database migrated by either language is accepted unchanged by the other, pinned to the exact rc. **The extension migration** (`migration.sql`: `CREATE EXTENSION IF NOT EXISTS vector;`, `down.sql`: `DROP EXTENSION vector;`) is produced by `drizzle-kit generate --custom --name extension` **before the first schema migration**, so it carries drizzle-kit's own 14-digit timestamp prefix (the rc migrator derives `folderMillis` from that prefix; a hand-named folder such as `0000_extension` yields `NaN` and the ledger insert fails) and sorts first; the ledger-parity test pins the folder name. On PGlite it can only be applied by the programmatic migrator against an instance constructed with the extension, and the package's `createPglite()` helper does exactly that (a test asserts that the same migrations applied through `drizzle-kit migrate --driver pglite` fail, so nobody documents that path). The same ledger carries the **SECURITY DEFINER** functions of §11 and ADR-0013 §1, and **hosts ADR-0013's organization-anchored tables** (`audit_events`, `blobs`, `outbox`, `webhook_subscriptions`, `organization_quotas`, `jobs_meta`) as migrations that ADR-0013 owns and this package's build, sync, and ledger-parity rules govern.

**CI topology** (revision 5 — embedded-postgres not adopted; it never entered any `go.mod`): TS runs on PGlite + `pglite-pgvector` in-process on **ubuntu + windows**. Go runs against **real PostgreSQL 18 with pgvector 0.8.6** via the `testcontainers-go` postgres module and the digest-pinned `pgvector/pgvector:0.8.6-pg18` image on **ubuntu** — one container per package in `TestMain`, `Snapshot`/`Restore` per test, Ryuk left on, a non-default database name; the migration pool carries no type registration, and the runtime pool registers pgvector codecs in `AfterConnect` (ADR-0010 §1 owns that pool); on **windows** the Go database tests are **skipped** with an explicit, counted skip (`HDF_DB_URL` unset → `t.Skip`), because Windows runners cannot run Linux containers and no Go-embeddable Postgres can load `pgvector`. Windows keeps Go compile + unit coverage of the pure code (disassemble/assemble on fixtures, struct parity, migration file parity), which needs no database. A `HDF_DB_URL` override lets any runner (or a developer with Docker) run the full Go suite. Goldens: `SELECT version()` asserts the same major on both engines; `SELECT extversion FROM pg_extension WHERE extname = 'vector'` asserts `0.8.x` on both (PGlite carries 0.8.1, the image 0.8.6 — minor drift is recorded, not equalised). `pglite-server --db memory:// -e "@electric-sql/pglite-pgvector:vector"` is the documented Docker-free local-dev bridge for Go (`127.0.0.1`, `sslmode=disable`, one multiplexed connection, lockstep-pinned), with a Phase 6 verification line for pgx; it is never a CI path.

### 11. Vector store — `pgvector` in the same schema
- **Tables**: `embedding_models(id uuid, name text UNIQUE, provider text, dims int, distance ∈ {cosine, l2, ip}, created_at)` is reference data (tenant-free); `dims` and `distance` are immutable after insert. **`embeddings`** is an **owned, derived, rebuild-only** table: `(id, document_id → documents [owner FK, CASCADE], model_id → embedding_models, requirement_row_id | override_row_id | system_row_id | component_row_id | baseline_row_id — five nullable FKs with `ON DELETE CASCADE` and `CHECK (num_nonnulls(…) = 1)` (the §4 exactly-one pattern), embedding vector, text_sha256 bytea, created_at)`, unique per `(<subject FK>, model_id)`. A `BEFORE INSERT` trigger (a `CASE` over the five subject tables walking each owner path) asserts the subject row's owning document equals `document_id` with `IF owner IS DISTINCT FROM NEW.document_id THEN RAISE` — `IS DISTINCT FROM`, because under RLS a cross-tenant subject row is invisible to the lookup, the FK still passes (referential checks bypass RLS), and a plain `<>` against `NULL` would never raise; planted test: a cross-tenant subject id is rejected. The ownership walker treats the five subject FKs as reference FKs. It follows every §8 rule and is invisible to `assemble()`.
- **Dimensionless column, typed index per model, DDL in the ledger**: `embedding` is declared `vector` (no dimension) so one table serves any model — as a Drizzle `customType({ dataType: () => 'vector' })`, because the built-in `vector()` builder requires `dimensions` (measured). The Phase 4b migration ships a **`SECURITY DEFINER`** function `hdf_register_embedding_model(name, provider, dims, distance)` owned by the migrations role, written per PostgreSQL's "Writing SECURITY DEFINER Functions Safely": `SET search_path = pg_catalog, <hdf schema>, pg_temp`; `REVOKE ALL ON FUNCTION … FROM PUBLIC` and `GRANT EXECUTE … TO <runtime role>` in the same migration; `distance` validated against the enum and `dims` against `1..4000` inside the function; DDL built with `format('%I' / '%L')`. It inserts the model row with `INSERT … ON CONFLICT (name) DO NOTHING` and re-selects (so a concurrent second call is a no-op rather than an error) and `EXECUTE`s `CREATE INDEX IF NOT EXISTS embeddings_hnsw_<32-hex id> ON embeddings USING hnsw ((embedding::halfvec(<dims>)) <halfvec_*_ops by distance>) WHERE model_id = '<id>'` (48 characters, under the 63-character identifier limit) with pgvector's default build parameters (`m = 16`, `ef_construction = 64`). The runtime role holds `EXECUTE` and schema `USAGE` only, so registration works under the §8 non-owner rule (measured on both engines); the DDL *template* is in the ledger and only its parameters are runtime — reviewer challenge (k). A trigger rejects a vector whose `vector_dims()` differs from its model's `dims`. **Two build paths, one index.** The in-function `CREATE INDEX` runs inside the registration transaction and blocks writes to `embeddings` for its duration (under a second at 20k rows; it cannot be `CONCURRENTLY`, which PostgreSQL forbids inside a function or transaction) — the default, sufficient for the corpus sizes this store will see first. For large stores the docs give the **owner-run concurrent path**: `hdf db embed --index --concurrently` (or `hdf-serve migrate --index`) executed as the migrations role runs the same statement as `CREATE INDEX CONCURRENTLY IF NOT EXISTS` with a session-level `maintenance_work_mem`, after which the function's `IF NOT EXISTS` is a no-op; the ops note also covers `REINDEX INDEX CONCURRENTLY` after mass deletion and the pgvector ≥ 0.8.4 floor for the HNSW vacuum fixes.
- **What is embedded** is decided by the caller through ADR-0010 §4, not by this package; this package fixes the subject vocabulary (`requirement`: `title` + the `default`-labelled `descriptions[]` entry; `override`: `justification`; `system`: `name` + `description`; `component`: `name` + `description`; `baseline`: `Evaluated_Baseline.title` + `description`) and the `text_sha256` so a rebuild can skip unchanged subjects. The package **never calls a model** and ships no default model.
- **Similarity exemplar (query 4)**: nearest adjudicated requirements (rows with a governing override) to a query vector, restricted to one model, within the caller's tenant, with `LIMIT` and an optional evidence-package scope. Two planner facts shape the SQL: a partial index is matched only against a **literal** `model_id` — measured: a bound parameter uses the index for five executions and then a generic plan falls back to a sequential scan — so the exemplar inlines the uuid, parsed with the language's uuid parser and re-serialised from the parsed value, never the input string (or runs with `SET LOCAL plan_cache_mode = force_custom_plan`); and HNSW applies the tenant filter **after** the candidate scan, so the exemplar sets `SET LOCAL hnsw.iterative_scan = relaxed_order` (pgvector ≥ 0.8.0, both engines; measured: `off` returns zero rows for a three-row tenant, `relaxed_order` returns all three) and `SET LOCAL hnsw.ef_search = greatest(<limit>, <HDF_HNSW_EF_SEARCH, default 100>)`, and records that `hnsw.max_scan_tuples` (default 20,000) still bounds the fill for a very small tenant beside a very large one. The `ORDER BY` expression and operator match the index expression exactly (`embedding::halfvec(N) <op> $1::halfvec(N)`, operator by `embedding_models.distance`); a btree on `embeddings(model_id, document_id)` serves the post-scan tenant join. Negatives: another tenant's rows never rank; a different model's rows never rank; a dims-mismatched insert is rejected; a small tenant beside a large one still receives `LIMIT` rows; **index use is asserted by counting**, not by reading a plan: the exemplar runs eight times through the driver and `pg_stat_user_indexes.idx_scan` for the model's index rises by eight on both engines (a driver-level `EXPLAIN` plans one-shot and would false-pass the bound form), on a table large enough for the planner to prefer the index (≥ 20k rows, or `enable_seqscan = off` in the test).
- **Hybrid text search** stays in core Postgres: `tsvector`/`pg_trgm` are available on both engines and are the documented fallback when no embedding model is configured; no second search extension is adopted.

### 12. Schema-version coexistence — rows track the current schema
A store lives across schema releases. Rule: **rows always reflect the schema the package currently targets**; `documents.validated_against` records the version the bytes were validated against at import. A schema **minor** bump is a db-schema migration plus a **re-projection**: `reprojectDocument(id)` (a pure re-disassemble from `source_bytes` into the new shape, same transaction rules as import, derived tables rebuilt) run for every retained document by ADR-0013's job runner; a document imported with `retainBytes: false` cannot be re-projected and is marked `stale_schema = true`, excluded from the exemplar queries, and reported by `hdf db list --stale` until re-imported. `reprojectDocument` runs as the runtime role under the caller's principal, sets `hdf.deleting_document` for its owned-row and derived-table rewrite (§5), and updates only the operational columns. **The migration window**: between the schema migration and the end of `schema.reprojectAll` (ADR-0013 §2), rows carry the old shape with new columns NULL; the exemplar queries treat `validated_against <> <current>` as stale and skip those rows until re-projection updates `validated_against`, and ingest is never blocked. The `$id` version-pin test is therefore a **bump checklist item** (update the pin, add the migration, run the re-projection) rather than a permanent red test. A schema **major** requires an ADR before any migration. Reviewer challenge (p).

## Alternatives Considered

### A. jsonb document store with SQL views
Why rejected: not 3NF; no FK integrity; relational ergonomics is the point.

### B. Hybrid — 3NF rows plus the original document
Disposition: **partially adopted** — rows are value-level truth, bytes retained by default for verification/export, documents immutable (§5/§6). The revision-1 rejection was a strawman.

### C. Mechanically generate tables from JSON Schema
Why rejected: document-shaped nesting, no key design; sync enforced by coverage + round-trip tests instead.

### D. Other ORMs / raw SQL
Why rejected: Drizzle is TS-first, SQL-transparent, PGlite-native; its migrations are plain SQL the Go side consumes.

### E. TS-only v1, Go deferred
Why rejected: the motivating consumer cannot write a row — challenge (b).

### F. All eight types in v1
Why rejected: comparison/change-event have no corpus and carry snapshots; change events re-open ADR-0005 — challenge (a).

### G. Gate on Drizzle 1.0 GA, or target 0.45.x
Why rejected: unknown wait, or a forced layout rewrite; `next` on the rc with an exact-pinned parity test — challenge (g).

### H. Hand-written Go structs, or sqlc
Why rejected: hand mirrors drift; sqlc needs a query surface this package does not ship — challenge (h).

### I. Ship auth/tenancy tables
Why rejected: a seam, not a subsystem; no-ownership also rejected — challenge (d).

### J. Do nothing
Why rejected: no public issue asks for this today (anticipated by the `hdf db`/MCP direction); design cost is paid once.

### K. A separate vector database (Qdrant, Weaviate, Milvus, LanceDB, or a file-backed ANN index)
Pros: purpose-built ANN performance and filtering; no extension dependency. Cons: a second store with its own tenancy, backup, and consistency model; the similarity result must be joined back to relational rows across a network boundary; no in-process equivalent for the PGlite dev/test path; a second deployable. Why rejected: pgvector's HNSW covers the corpus sizes at issue, the rows *are* the filter, and one engine keeps the RLS story single — challenge (k).

### L. Keep embedded-postgres for Go and test vectors in TypeScript only
Pros: keeps the windows Go database matrix; no Docker in CI. Cons: the Go MCP is a first-party consumer of the similarity exemplar and would ship an untested query path; two Go engines (embedded for rows, a container for vectors) doubles the runner code. Why rejected: real PostgreSQL + pgvector on Linux with an explicit Windows skip tests what deploys — challenge (l).

### M. Fixed-dimension `vector(N)` column per model, one table per model
Pros: native typed index, no runtime DDL. Cons: a new model means a migration and a new table; queries branch by table. Why rejected: one dimensionless table with per-model partial expression indexes keeps the ledger closed and the query single, at the cost of the runtime DDL in §11 — challenge (k).

## Consequences

Easier: adjudication carry-forward and similar-system precedent become joins; similarity is one more indexed query in the same transaction and tenant; `hdf db` and a DB-backed MCP mode have a schema, migrations, validators; PGlite + pgvector serves embedded TS consumers and `hdf-serve` dev mode with zero infrastructure; the validator fix makes "schema-valid" mean conformance repo-wide.

Harder: every schema field addition forces a db-schema update; migrations and `down.sql` are a public surface; dual-language doubles implementation; source-byte retention costs storage; an rc dependency until GA; two release-workflow changes; **Go database tests need Docker** (CI: ubuntu only; developers: Docker or the pglite-server bridge); embeddings add storage per model and a rebuild step per import; `pgvector` becomes a hard deployment requirement (the plain `postgres` image no longer suffices).

Risks and mitigations: normalization misjudged late → core first, `importDocument`/`exportDocument` API, bytes allow re-projection; canonicalization ambiguity → §5 rules are tests; PGlite gaps or Windows breakage → Phase 1a AC on both CI OSes with the stated fallback (TS on a `HDF_DB_URL` PostgreSQL via `pg` there); HNSW untested in PGlite → the §11 `EXPLAIN` assertion is a Phase 4b AC on both engines, with the stated fallback (sequential scan accepted on PGlite only, recorded as a tracked constant the test asserts) if PGlite cannot build the index; small-tenant under-return → `iterative_scan` plus the positive test; embedded text leaving the deployment → the provider is caller-configured (ADR-0010), off by default, and the docs state that `embed` sends subject text to whatever endpoint is configured; corpus thin → Phase 0 promotion under the fixture policy (§ Shared Abstractions); tenant leakage → §8 classification, owner/reference FK rule, generated RLS, negative tests; ledger divergence → parity test; data sensitivity → canary test, driver-error wrapping, docs stating PGlite persists plaintext and encryption at rest is the deployer's responsibility; fixture hygiene → `lint:fixtures` (IPv4/IPv6 outside documentation ranges, non-RFC-2606 FQDNs, non-`example.*` emails, cloud ids, key-shaped strings, **absolute local filesystem paths** — with the bundle's `plan.json` as the recorded exception, since its bytes are checksum-pinned) over goldens and docs, and `hdf-fixtures/README.md` gains a `sanitized (yes/no/n-a)` column; supply chain → PGlite, `pglite-pgvector`, `pgvector-go`, and the pgvector image (by digest) pinned and goldened, no `minimumReleaseAgeExclude`.

Migrations tested up/down and ledger-parity each phase. Live test before each close: import a real fixture through both drivers in both languages and run the phase's exemplar query — output pasted in card notes.
