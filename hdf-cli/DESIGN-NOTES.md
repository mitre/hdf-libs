# HDF CLI Design Notes

This document tracks design decisions, user stories, and planned features for the `hdf` CLI tool.

## Design Principles

Based on [12-Factor CLI Apps](https://medium.com/@jdxcode/12-factor-cli-apps-dd3c227a0e46) and [CLI Guidelines](https://clig.dev/):

1. **Human-first, machine-friendly** - Pretty output by default, `--json` for scripts
2. **Composable** - Works well with pipes, standard Unix tools
3. **Forgiving** - Suggest corrections, provide helpful errors
4. **Fast** - Target <500ms for common operations
5. **Progressive disclosure** - Simple by default, powerful when needed

## Schema Integration

The CLI embeds JSON schemas from `@mitre/hdf-schema` for validation. Schemas are automatically synced during build:

- **Schema Source**: `../hdf-schema/dist/schemas/*.json` (generated by hdf-schema package)
- **Embedded Location**: `pkg/schema/schemas/*.json` (Go embed)
- **Sync Command**: `pnpm sync-schemas` (runs automatically during build)
- **Build Process**: `pnpm build` → syncs schemas → embeds at compile time

**Parallel Build Support**: When running `pnpm build` from the monorepo root, hdf-schema and hdf-cli build in parallel. The sync-schemas script polls for `../hdf-schema/dist/schemas` to appear, ensuring schemas are ready before copying. This avoids race conditions while allowing parallel builds.

## Implemented Commands

### `hdf validate <file>`
Validate an HDF file against the schema.

### `hdf info <file>`
Display summary information (generator, platform, profiles, targets).

### `hdf stats <file>`
Show assessment statistics (pass/fail/error counts, duration).

### `hdf list <type> <file>`
List controls, profiles, or targets with optional status filtering.

### `hdf version`
Print version, commit, build date, and Go version.

## Planned Commands

### `hdf query` - Search and Filter Controls

**Priority:** 1 (High)

#### User Stories

1. **As a security analyst**, I want to find all controls related to a specific CCI so I can assess compliance against a particular requirement.
   ```
   hdf query results.json --cci CCI-000366
   ```

2. **As an auditor**, I want to find all failed high-severity controls so I can prioritize remediation efforts.
   ```
   hdf query results.json --severity high --status failed
   ```

3. **As a DevSecOps engineer**, I want to filter controls by NIST control family so I can report on specific security domains.
   ```
   hdf query results.json --tag "nist:AC-*"
   ```

4. **As a system administrator**, I want to find controls by STIG ID so I can cross-reference with the official STIG documentation.
   ```
   hdf query results.json --stig-id V-230221
   ```

5. **As a compliance officer**, I want to find all controls with impact above a threshold so I can focus on critical findings.
   ```
   hdf query results.json --impact ">0.5" --status failed
   ```

6. **As a developer**, I want to search control titles and descriptions for keywords so I can find relevant controls quickly.
   ```
   hdf query results.json --search "password"
   ```

#### Acceptance Criteria
- Supports filtering by: status, severity/impact, CCI, STIG ID, NIST tag, custom tags
- Supports combining multiple filters (AND logic)
- Supports glob/wildcard patterns for tag values
- Outputs control list with ID, title, status, and impact
- Supports `--json` for machine-readable output
- Supports `--count` to show only the count of matching controls

### `hdf show` - Display Control Details

**Priority:** 2 (High)

#### User Stories

1. **As a security analyst**, I want to see full details of a specific control so I can understand what was tested and why it failed.
   ```
   hdf show results.json SV-238196
   ```

2. **As a developer**, I want to see the test code for a control so I can understand what the scanner is checking.
   ```
   hdf show results.json SV-238196 --code
   ```

3. **As a remediator**, I want to see the fix text for a failed control so I know how to resolve the finding.
   ```
   hdf show results.json SV-238196 --fix
   ```

4. **As an auditor**, I want to see all test results within a control so I can understand partial failures.
   ```
   hdf show results.json SV-238196 --results
   ```

5. **As a compliance officer**, I want to see all metadata tags for a control so I can map it to frameworks.
   ```
   hdf show results.json SV-238196 --tags
   ```

#### Acceptance Criteria
- Displays: ID, title, description, status, impact, tags
- Optional sections: `--code`, `--fix`, `--check`, `--results`, `--tags`, `--refs`
- `--all` shows everything
- Colorized output with severity-appropriate colors
- Supports `--json` for machine-readable output
- Accepts multiple control IDs: `hdf show results.json SV-1 SV-2 SV-3`

### `hdf diff` - Compare Two Scans

**Priority:** 3 (Medium)

#### User Stories

1. **As a DevSecOps engineer**, I want to compare today's scan with yesterday's so I can see what changed after a deployment.
   ```
   hdf diff yesterday.json today.json
   ```

2. **As a security analyst**, I want to see which findings were fixed between scans so I can track remediation progress.
   ```
   hdf diff before.json after.json --fixed
   ```

3. **As an auditor**, I want to see new failures introduced between scans so I can identify regressions.
   ```
   hdf diff baseline.json current.json --new-failures
   ```

4. **As a manager**, I want a summary of changes between scans so I can report on security posture trends.
   ```
   hdf diff scan1.json scan2.json --summary
   ```

5. **As a CI/CD system**, I want machine-readable diff output so I can post comments on pull requests.
   ```
   hdf diff main.json pr.json --json
   ```

#### Acceptance Criteria
- Shows: new failures, fixed issues, status changes, new controls, removed controls
- Summary statistics: +X fixed, -Y regressed, Z unchanged
- Filter options: `--fixed`, `--regressed`, `--new`, `--removed`, `--changed`
- Supports `--json` for machine-readable output
- Exit code reflects whether regressions exist (for CI)
- Handles profile/control ID matching across different scans

### `hdf check` - Threshold Validation for CI/CD

**Priority:** 4 (Medium)

#### User Stories

1. **As a DevSecOps engineer**, I want my CI pipeline to fail if less than 80% of controls pass so I can enforce security gates.
   ```
   hdf check results.json --min-pass-rate 80
   ```

2. **As a security architect**, I want builds to fail if any high-severity controls fail so I can prevent critical vulnerabilities.
   ```
   hdf check results.json --max-failed-high 0
   ```

3. **As a release manager**, I want to allow some failures but cap the total so I can balance security with delivery.
   ```
   hdf check results.json --max-failed 10 --max-error 0
   ```

4. **As a compliance officer**, I want to check against a threshold file so I can version-control our security policy.
   ```
   hdf check results.json --threshold threshold.yaml
   ```

5. **As a developer**, I want clear output explaining why a check failed so I know what to fix.
   ```
   hdf check results.json --min-pass-rate 90 --verbose
   ```

#### Acceptance Criteria
- Threshold options: `--min-pass-rate`, `--max-failed`, `--max-error`, `--max-failed-high/medium/low`
- Supports threshold file (YAML/JSON) for complex policies
- Exit code 0 = pass, 1 = threshold violated, 2 = error
- Clear output explaining which thresholds failed and by how much
- Supports `--json` for machine-readable output
- Quiet mode (`-q`) for scripts that only care about exit code

### `hdf export` - Export to Other Formats

**Priority:** 5 (Medium)

#### User Stories

1. **As a compliance officer**, I want to export results to CSV so I can analyze them in Excel.
   ```
   hdf export results.json --format csv > controls.csv
   ```

2. **As a DevSecOps engineer**, I want to export to SARIF so I can integrate with GitHub Security.
   ```
   hdf export results.json --format sarif > results.sarif
   ```

3. **As an auditor**, I want to generate an HTML report so I can share findings with stakeholders.
   ```
   hdf export results.json --format html -o report.html
   ```

4. **As a STIG assessor**, I want to export to CKL format so I can import into STIG Viewer.
   ```
   hdf export results.json --format ckl -o checklist.ckl
   ```

5. **As a security analyst**, I want to export only failed controls so I can create a focused remediation report.
   ```
   hdf export results.json --format csv --status failed > failures.csv
   ```

#### Acceptance Criteria
- Formats: `csv`, `json` (normalized), `sarif`, `html`, `ckl`, `markdown`
- Filter options work with export (e.g., `--status`, `--severity`)
- Output to stdout by default, `-o` for file
- HTML report is self-contained (embedded CSS)
- SARIF output follows SARIF 2.1.0 spec
- CSV includes configurable columns

### `hdf merge` - Combine Multiple Scans

**Priority:** 6 (Low)

#### User Stories

1. **As a security analyst**, I want to combine scans from multiple targets into one file so I can get an aggregate view.
   ```
   hdf merge web-server.json db-server.json -o infrastructure.json
   ```

2. **As a DevSecOps engineer**, I want to merge partial scans from parallel CI jobs so I can get complete results.
   ```
   hdf merge job1.json job2.json job3.json -o complete.json
   ```

3. **As an auditor**, I want to combine scans while preserving which target each finding came from.
   ```
   hdf merge --preserve-targets scan1.json scan2.json -o combined.json
   ```

4. **As a compliance officer**, I want to deduplicate controls when merging overlapping scans.
   ```
   hdf merge --dedupe scan1.json scan2.json -o merged.json
   ```

#### Acceptance Criteria
- Combines profiles and controls from multiple files
- Handles duplicate control IDs (configurable: first-wins, last-wins, merge)
- Preserves target information
- Updates statistics for merged results
- Validates output against schema
- Supports `--dry-run` to preview merge

### `hdf summary` - Executive Summary

**Priority:** 7 (Low)

#### User Stories

1. **As a manager**, I want a one-page summary of our security posture so I can report to leadership.
   ```
   hdf summary results.json
   ```

2. **As a compliance officer**, I want findings grouped by NIST control family so I can assess coverage.
   ```
   hdf summary results.json --by nist
   ```

3. **As an auditor**, I want findings grouped by CCI so I can map to RMF requirements.
   ```
   hdf summary results.json --by cci
   ```

4. **As a security analyst**, I want findings grouped by severity so I can prioritize remediation.
   ```
   hdf summary results.json --by severity
   ```

#### Acceptance Criteria
- Default: Overall pass rate, critical findings count, top failed controls
- Group by: `--by nist`, `--by cci`, `--by severity`, `--by profile`
- Trend indicator if previous scan provided: `--compare previous.json`
- Supports `--json` for machine-readable output
- Compact mode for dashboards: `--compact`

## UX Enhancements (Future)

### Pager Support
- Pipe long output through `$PAGER` when stdout is a TTY
- Respect `--no-pager` flag

### Color Coding
- CAT I / High (impact >= 0.7): Red
- CAT II / Medium (impact >= 0.4): Yellow
- CAT III / Low (impact > 0): Blue

```
hdf interactive results.json
```
- Fuzzy search controls
- Navigate with arrow keys
- Drill into control details
- Filter on the fly

### Shell Completions
- Dynamic completion for control IDs from file
- Completion for tag values from file

### Watch Mode
```
hdf watch ./results/ --command "hdf check {} --min-pass-rate 80"
```
- Monitor directory for new HDF files
- Run command on each new file
- Useful for CI artifact monitoring

## Data Model Notes

### Control Status Determination
When `overall_status` is not set, derive from results:
1. If any result has `status: error` → error
2. If any result has `status: failed` → failed
3. If all results have `status: passed` → passed
4. If impact = 0 and no results → not_applicable
5. Otherwise → not_reviewed

### Severity Mapping
Impact to CAT severity (STIG convention):
- 0.7 - 1.0: CAT I (High)
- 0.4 - 0.69: CAT II (Medium)
- 0.01 - 0.39: CAT III (Low)
- 0.0: Not Applicable

### Tag Conventions
Common tag keys to support in queries:
- `cci`: CCI identifiers (e.g., `CCI-000366`)
- `nist`: NIST 800-53 controls (e.g., `AC-2`, `CM-6 (1)`)
- `severity`: `high`, `medium`, `low`
- `stig_id` / `gtitle` / `gid`: STIG identifiers
- `fix_id`: Fix identifier for remediation tracking
